# Nora Tavern 启动器优化记录

状态：P0 实施与候选包验证中  
首次记录：2026-09-06  
测试平台：macOS arm64  
测试隔离目录：`/tmp/nora-tavern-user-test-1788682746666`

## 目标

让普通用户能够判断安装正在做什么、是否仍在运行、是否成功，以及失败后应该如何继续。界面展示的每个阶段必须来自真实安装状态，不能只展示预设流程。

## 已确认问题

### 1. 安装长时间没有进度反馈

现场表现：

- 界面长时间停留在 `Installing managed uv`。
- 实际后台已经继续下载 Node.js 26，但 Hermes 官方安装器使用静默 `curl`，没有向启动器输出下载进度。
- 启动器只转发按行输出的终端文本，因此无法展示字节数、百分比、速度和预计剩余时间。
- Node.js 下载现场检查时为 `24.1 MB / 30.4 MB`，约 `79%`，网络连接仍然有效，但用户界面没有任何变化。

### 2. 当前五步流程不是真实进度

当前界面展示：

1. 准备电脑
2. 安装酒馆
3. 配置模型
4. 连接手机
5. 开始游玩

实际情况：

- 后端目前只在开始安装 Hermes 时发送第 0 步事件。
- `准备电脑` 只能表示安装命令已经开始，不能表示环境准备完成。
- 下载 uv、下载 Node.js、克隆 Hermes、创建 Python 环境、复制 Tavern、启动服务等过程没有独立阶段事件。
- `安装酒馆` 及后续步骤没有与真实执行节点可靠绑定。
- 当前流程格不能用于判断成功或失败。

### 3. 安装是否仍在运行无法判断

- 无输出时，界面没有心跳、持续时间或“仍在下载”提示。
- 子进程存在不代表安装仍有进展；也可能在等待网络、等待输入或已经卡死。
- 当前没有“最后一次有效进展时间”。
- 当前没有阶段超时、网络超时和卡死检测。

### 4. 成功条件不明确

- 用户只能看到终端文本，无法确认 Hermes、Tavern 和本地服务是否全部安装成功。
- 安装按钮结束不应直接等同于安装成功。
- 必须同时验证 Hermes 命令、Tavern 安装标记、运行进程和 `8799` 健康检查。

### 5. 日志可读性差

- ANSI 颜色控制符直接显示为 `\u001b[0;32m` 等乱码。
- Hermes 脚本中的 `echo -e` 在当前转发方式下显示为字面文本。
- 每行统一添加 `[Nora]`，会把第三方安装器输出混成 Nora 自己的状态信息。
- 失败后没有稳定保留完整日志和明确错误摘要。

### 6. 测试入口容易混淆

- 仓库中曾同时存在旧构建和新候选构建。
- 旧构建没有隔离逻辑，曾把 Hermes 写入 `~/.hermes`。
- 启动器若依附临时终端进程运行，终端结束会导致窗口和安装子进程同时关闭。
- 测试和发布都必须使用唯一、可识别的构建产物，并由系统独立启动应用。

### 7. 候选包无法通过启动器完成测试安装

- 本次桌面测试包由 `package-release.mjs --candidate` 生成，清单被正确标记为候选发布。
- 首次安装器默认拒绝候选发布，并要求显式传入 `--allow-candidate`，这是合理的正式发布保护。
- 当前 `launcher_bridge.py` 调用首次安装器时没有传递该参数，因此 Hermes 安装完成后，Tavern 安装立即失败。
- 启动器必须明确区分正式构建和候选构建：正式构建保持拒绝候选包，测试构建只能在自身清单确认为候选时显式开启候选安装。
- 失败提示应向用户说明“测试包通道不匹配”，不能只显示退出码 1。

## 真实安装阶段草案

后端应按以下阶段上报真实状态：

1. 安装前检查：系统、架构、磁盘、网络、目录权限和端口。
2. 准备 Hermes：安装 uv。
3. 准备运行环境：下载并安装 Node.js。
4. 安装 Hermes：克隆代码并创建 Python 环境。
5. 安装 Nora Tavern：校验并解压内置载荷。
6. 配置 Nora：写入 skills、`AGENTS.md`、`SOUL.md` 和 MCP 配置。
7. 启动酒馆：启动本地服务并等待健康检查。
8. 安装完成：显示明确结果和下一步入口。

每个阶段只能处于以下状态之一：`等待`、`进行中`、`成功`、`失败`、`已取消`。

## 优化要求

### P0：发布前必须完成

- 后端提供结构化阶段事件，不再根据终端文案猜测进度。
- 下载任务展示已下载大小、总大小、百分比和速度。
- 无法获得百分比时，展示当前任务、已用时间和最近一次活动时间。
- 每个长任务提供心跳，并区分“正在运行”和“没有进展”。
- 增加取消、重试和失败后继续安装。
- 过滤 ANSI 控制符，保留原始完整日志文件。
- 只有全部安装检查和服务健康检查通过后，才能显示“安装完成”。
- 启动前校验所有写入路径必须位于 Nora Tavern 隔离根目录；越界立即失败。
- 移除或隔离旧构建，测试包必须显示版本、构建时间和候选标记。
- 启动器与内置载荷的发布通道必须匹配；候选启动器应自动携带受控的候选安装许可，正式启动器不得接受候选载荷。
- 应用必须由操作系统独立启动，关闭开发终端不能终止安装器。

### P1：体验优化

- 将技术日志默认收起，主区域只显示当前任务和用户可理解的说明。
- 显示总体阶段进度，但不伪造总百分比。
- 对下载慢、GitHub 连接失败、磁盘不足和端口占用提供明确提示。
- 安装失败时保留已经完成且可安全复用的依赖，避免每次从头下载。
- 重新打开启动器后能够恢复并显示上一次安装状态。

## 验收标准

- 用户在任意时刻都能回答：现在正在做什么、运行了多久、是否还有进展。
- UI 中完成的阶段必须能够由本地文件、进程或健康检查验证。
- 断网、下载超时、关闭窗口和重新打开都不会被误报为成功。
- 安装全过程不得创建 `~/.hermes`，所有 Hermes 与 Tavern 文件只能进入指定隔离目录。
- 成功页出现时，Hermes 可执行、Tavern 健康检查通过，且酒馆能够实际打开。

## 本次测试实时记录

- uv 已安装到隔离目录：`hermes/bin`。
- Node.js 26 下载过程没有 UI 进度反馈。
- Node.js 下载完成后，隔离目录增长到约 `527 MB`。

- Tavern 首次安装因候选发布保护失败：候选载荷未获得 `--allow-candidate` 许可。
- Tavern 安装标记不存在，`8799` 服务未启动，因此本次整合安装明确失败。

## 当前决定

已按现场结论开始实施：启动器调用 Hermes 官方阶段协议；安装状态写入隔离目录；UI 使用真实里程碑、耗时、下载进度和日志；候选启动器只对自身候选载荷传递候选许可；Hermes 命令优先使用隔离虚拟环境；macOS/Windows 进程检测使用跨平台实现。

保留的真实边界：模型配置和 ClawChat 登录需要用户本人完成，启动器只提供官方入口，并在检测到本地凭据或有效连接身份后点亮对应步骤，不伪造自动完成。
