# Nora Tavern MVU 更新格式说明

> 状态：协议改造前基线说明；当前实施状态见 `NORA-MVU-STRUCTURED-PROTOCOL-PLAN.md`  
> 审计日期：2026-09-05  
> 发布基线：Nora Tavern `v2.1.4` (`22fb102`)  
> 本地基线：`d252338`，比 `origin/main` 多 4 个提交；MVU 核心协议与发布版相同，本地额外接受“已有非空 `stat_data`、但没有 Zod Schema”的旧快照作为已初始化状态。

## 1. 文档目的

本文记录改造前 Nora Tavern 支持的两种 MVU 变量更新格式：

1. 旧卡常用的 Lodash 风格命令：`_.set(...)`，以及同类 `_.insert(...)`、`_.remove(...)`、`_.add(...)`。
2. 新卡常用的 MVU JSONPatch 方言：`<JSONPatch>[...]</JSONPatch>`。

本文回答以下问题：

- 两种格式分别长什么样。
- 模型输出后，MVU 如何解析和保存。
- 旧卡的 VWD 数据和新卡的纯值数据有什么区别。
- 开启或关闭额外模型时，谁负责输出变量。
- Zod 在哪个阶段介入，能保证什么，不能保证什么。
- 两种格式的准确性、兼容性和常见失败方式。

实施分支已经新增第三种 `nora-mvu/1` 协议，但仍保留本文件描述的两种旧格式作为兼容输入；系统不会自动把任意旧卡静默转换成新卡。

## 2. 共同基础：`stat_data`

不论使用哪种输出格式，MVU 的权威状态都保存在聊天消息的变量快照中：

```text
message.variables[swipe_id].stat_data
```

一轮对话的基本过程是：

```text
上一轮有效 stat_data
    -> 发送给模型作为当前状态
    -> 模型输出变量更新命令
    -> MVU 解析命令
    -> 修改状态副本
    -> 可选的 Schema/Zod 校验
    -> 保存为当前消息的新 stat_data
```

`<UpdateVariable>`、`<JSONPatch>` 和 `_.set(...)` 本身不是变量存储。它们只是模型告诉 MVU“本轮应当如何改变状态”的指令载体。

## 3. 格式一：旧卡 `_.set(...)`

### 3.1 基本格式

旧卡最常见的输出是：

```js
_.set('变量路径', 旧值, 新值);
```

例如：

```js
_.set('世界.时间', '08:30', '08:35');
_.set('星宫诗羽.好感度', 42, 44);
_.set('白石紬.是否已登场', false, true);
```

当前解析器也接受两参数形式：

```js
_.set('变量路径', 新值);
```

例如：

```js
_.set('世界.时间', '08:35');
```

### 3.2 三参数中的旧值到底有什么作用

旧卡提示词通常把三个参数解释为：

```text
路径、旧值、新值
```

但当前 MVU 执行器的真实行为是：

1. 第一个参数作为路径。
2. 最后一个参数作为新值。
3. 执行器自己从 `stat_data` 读取真实旧值。
4. 模型写在中间的“旧值”不会被当作严格的并发校验条件。

因此：

```js
_.set('星宫诗羽.好感度', 999, 44);
```

只要路径存在且 `44` 能被接受，当前实现仍可能把真实值设置为 `44`。模型写出的 `999` 主要用于提示词表达和可读性，不等同于数据库的 compare-and-set。

### 3.3 分号是格式的一部分

旧命令必须以分号结束：

```js
_.set('世界.时间', '08:35');
```

缺少分号时：

```js
_.set('世界.时间', '08:35')
```

当前文本命令提取器不会把它当作完整命令。

解析器使用括号和引号状态跟踪来寻找命令结尾，因此比单纯正则更能处理数组、对象和字符串中的括号，但未闭合引号、未闭合括号和缺少分号仍会导致解析失败。

### 3.4 路径语法

旧格式使用 Lodash 风格路径：

```text
世界.时间
星宫诗羽.好感度
角色列表[0].当前位置
```

路径表示对象中的层级。例如：

```js
_.set('世界.时间', '08:30', '08:35');
```

对应：

```json
{
  "世界": {
    "时间": "08:35"
  }
}
```

当前 `set` 执行前通常要求目标路径已经存在。模型拼错路径时，不应默默创建一个任意新字段，而会产生路径不存在错误。

### 3.5 旧卡的 VWD 数据

很多旧卡使用 Value With Description，简称 VWD：

```json
{
  "星宫诗羽": {
    "好感度": [
      42,
      "0 到 100 之间的好感度"
    ]
  }
}
```

含义：

```text
好感度[0] = 实际值
好感度[1] = 字段说明
```

旧卡仍然可以输出：

```js
_.set('星宫诗羽.好感度', 42, 44);
```

MVU 检测到目标是 VWD 后，会更新数组第一个元素：

```json
{
  "星宫诗羽": {
    "好感度": [
      44,
      "0 到 100 之间的好感度"
    ]
  }
}
```

字段说明不会被替换。

### 3.6 其他旧式命令

当前文本解析器还识别：

```js
_.insert(...);
_.assign(...);
_.remove(...);
_.unset(...);
_.delete(...);
_.add(...);
```

主要含义：

| 命令 | 当前用途 |
| --- | --- |
| `_.set(path, value)` | 替换已有路径的值 |
| `_.set(path, old, value)` | 替换已有路径的值；中间旧值不做严格比较 |
| `_.insert(...)` / `_.assign(...)` | 向数组或对象插入、分配或合并内容 |
| `_.remove(...)` / `_.unset(...)` / `_.delete(...)` | 删除数组元素或对象字段 |
| `_.add(path, delta)` | 对数字或日期执行增量更新 |

示例：

```js
_.add('星宫诗羽.好感度', 2);
_.insert('世界.在场角色', '-', '白石紬');
_.remove('世界.在场角色', '白石紬');
```

不同旧卡对这些命令的提示写法可能不一致。制卡时应以当前运行时真正支持的参数形式为准，不应仅根据卡片示例推断执行语义。

### 3.7 注释原因

命令后可以追加单行原因：

```js
_.set('世界.时间', '08:30', '08:35'); // 对话经过了五分钟
```

解析器会把分号后的 `//` 内容记录为命令原因，用于变化说明和诊断。注释不是写入 `stat_data` 的值。

### 3.8 完整旧卡输出示例

```text
<正文>
她接过发卡，沉默片刻后跟着你走向厨房。
</正文>

<UpdateVariable>
<Analysis>
时间推进五分钟；兑现承诺使好感度小幅增加；两人移动到厨房。
</Analysis>
_.set('世界.时间', '08:30', '08:35'); // 时间推进
_.set('星宫诗羽.好感度', 42, 44); // 兑现承诺
_.set('星宫诗羽.当前位置', '电车上', '学校厨房'); // 场景移动
</UpdateVariable>

<StatusPlaceHolderImpl/>
```

Regex 通常会隐藏 `<UpdateVariable>`，并把 `<StatusPlaceHolderImpl/>` 替换为状态栏。正文样式和变量更新格式属于两个不同层面。

### 3.9 旧格式的优点

- 对早期 MVU 卡兼容性好。
- 人类阅读直观，能看到“哪个字段从什么变成什么”。
- 模型熟悉 JavaScript 风格代码，简单命令通常能模仿。
- VWD 让值和字段说明保存在同一个变量树中。
- 不要求角色卡具备 Zod Schema。

### 3.10 旧格式的缺点

- 本质是自由文本，不是 API 级结构化输出。
- 引号、反斜杠、换行、括号和分号都可能写错。
- 三参数中的旧值不是严格状态锁，容易给人错误安全感。
- 模型必须手写完整路径。
- 模型可能漏写某条命令或创造错误路径。
- 没有 Zod 的旧卡缺少完整类型和结构校验。
- 世界书常把剧情、变量和输出格式混在同一条目中，不利于主模型与额外模型分工。

## 4. 格式二：MVU JSONPatch

### 4.1 基本格式

新卡通常要求：

```text
<UpdateVariable>
<JSONPatch>
[
  {
    "op": "replace",
    "path": "/系统/时间",
    "value": "08:35"
  }
]
</JSONPatch>
</UpdateVariable>
```

`<UpdateVariable>` 是更新块外层标记，`<JSONPatch>` 内必须是 JSON 数组。

### 4.2 当前支持的操作

Nora 当前使用的是 MVU JSONPatch 方言，不应把它与 RFC 6902 的全部细节视为完全相同。

| `op` | 必需字段 | 当前含义 |
| --- | --- | --- |
| `replace` | `path`, `value` | 替换已有字段 |
| `delta` | `path`, `value` | 对数字执行增量变化，`value` 必须是数字 |
| `insert` | `path`, `value` | 向数组或对象插入内容 |
| `add` | `path`, `value` | 当前 MVU 方言中等同插入，不是数字加法 |
| `remove` | `path` | 删除字段或数组元素 |
| `move` | `from` 加 `path` 或 `to` | 把已有值移动到另一位置 |

特别注意：

```text
数字增加使用 delta
集合插入使用 insert 或 add
```

错误示例：

```json
{"op":"add","path":"/角色/好感度","value":2}
```

这不是可靠的“好感度加 2”表达。正确写法是：

```json
{"op":"delta","path":"/角色/好感度","value":2}
```

### 4.3 `replace`

```json
{
  "op": "replace",
  "path": "/系统/时间",
  "value": "08:35"
}
```

JSONPatch 会被转换为 MVU 内部的 `set` 命令。目标路径通常必须存在。

模型只写新值，不需要重复写旧值，因此比三参数 `_.set` 更简洁。

### 4.4 `delta`

```json
{
  "op": "delta",
  "path": "/机娘编制/机娘档案库/unit_001/好感度",
  "value": 2
}
```

假设当前值为 `42`，执行后为 `44`。模型不需要自己计算最终结果，但仍需要选择正确的字段、目标 UID 和变化量。

### 4.5 `insert` 与 `add`

数组尾部追加：

```json
{
  "op": "insert",
  "path": "/机娘编制/当前对话机娘/-",
  "value": "unit_001"
}
```

`/-` 表示追加到数组末尾。

向对象插入新键：

```json
{
  "op": "add",
  "path": "/NPC档案库/npc_001",
  "value": {
    "UID": "npc_001",
    "名字": "林遥",
    "关系值": 0
  }
}
```

执行器会把路径最后一段作为数组索引或对象键，把前面的路径作为目标集合。

### 4.6 `remove`

```json
{
  "op": "remove",
  "path": "/机娘编制/当前对话机娘/0"
}
```

对于数组，最后一段通常表示索引；对于对象，最后一段表示需要删除的键。

### 4.7 `move`

```json
{
  "op": "move",
  "from": "/任务模块/当前任务/task_001",
  "path": "/任务模块/已完成任务/task_001"
}
```

当前结构化 Schema 也允许把目标字段写成 `to`：

```json
{
  "op": "move",
  "from": "/任务模块/当前任务/task_001",
  "to": "/任务模块/已完成任务/task_001"
}
```

### 4.8 JSON Pointer 路径

JSONPatch 使用斜杠路径：

```text
/系统/时间
/机娘编制/机娘档案库/unit_001/好感度
```

特殊字符使用 JSON Pointer 转义：

```text
~1 表示 /
~0 表示 ~
```

例如对象键 `A/B` 应写成：

```text
/对象/A~1B
```

解析器会把 JSON Pointer 转换成安全的 Lodash 括号路径，而不是简单用点号拼接。尽管如此，卡片自己的命名规则仍可能进一步限制键名。例如“废土机娘”禁止库存键名包含英文句点，是因为后续卡片脚本和展示逻辑仍可能使用点路径。

### 4.9 空数组

```text
<JSONPatch>[]</JSONPatch>
```

当前额外模型事务把它识别为显式的“本轮无变量变化”，而不是解析失败。

必须区分：

```text
有合法的 []          = 模型明确表示无需更新
没有 JSONPatch       = 没有解析到更新命令
JSON 格式错误        = 解析失败
有命令但状态未变化   = no-change 或校验问题
```

### 4.10 完整新卡输出示例

```text
她接过发卡，沉默片刻后跟着你走向厨房。

<UpdateVariable>
<JSONPatch>
[
  {
    "op": "replace",
    "path": "/系统/时间",
    "value": "08:35"
  },
  {
    "op": "delta",
    "path": "/机娘编制/机娘档案库/unit_001/好感度",
    "value": 2
  },
  {
    "op": "replace",
    "path": "/机娘编制/机娘档案库/unit_001/当前状态/位置",
    "value": "基地/B3_生活层/厨房"
  }
]
</JSONPatch>
</UpdateVariable>
```

### 4.11 JSONPatch 的优点

- JSON 可以被标准解析器处理。
- 每条操作的字段明确，适合 JSON Schema。
- 不要求模型重复提供旧值。
- `delta` 可以避免模型自行计算最终数字。
- 更适合额外模型的格式化输出。
- 更容易检查操作类型、必需字段和数据类型。

### 4.12 JSONPatch 的缺点

- 如果仍以普通聊天文本输出，依然可能出现坏 JSON、缺标签或正文混入。
- JSON Schema 只能保证外形，不能保证路径和剧情语义正确。
- 模型仍然需要知道完整路径和 UID。
- 卡片世界书、InitVar 与 Zod 不一致时，格式正确也会写错字段。
- 当前 `add` 的含义容易被误解为数值加法。
- 大型卡的路径很长，模型可能选错相似字段。

## 5. 普通文本 JSONPatch 与 API 结构化输出的区别

普通聊天消息中的 JSONPatch：

```text
模型自由生成文字
-> 希望它遵守 <JSONPatch> 标签和 JSON 语法
-> MVU 再从文字中提取
```

API 结构化输出：

```text
请求时向模型接口提供 JSON Schema
-> 接口约束返回对象的结构
-> MVU 把返回对象转换为 <UpdateVariable>/<JSONPatch>
```

当前额外模型支持三类应答方式：

| 应答方式 | 特点 |
| --- | --- |
| `聊天消息` | 当前 Nora 默认值；依赖提示词生成更新标签 |
| `格式化输出` | 提供 `analysis + json_patch` JSON Schema，接口必须支持 |
| `工具调用` | 通过函数调用返回变量内容，接口必须支持 Tool Calling |

当前默认仍是 `聊天消息`，所以“新卡使用 JSONPatch”不等于“已经强制使用 API 结构化输出”。

## 6. 关闭额外模型时的执行链路

关闭额外模型后，设置变为：

```text
更新方式 = 随AI输出
启用自动请求 = false
```

执行过程：

```text
EJS/世界书把当前变量和更新规则交给主模型
-> 主模型一次生成正文和变量更新块
-> MVU 从主模型回复中提取 _.set 或 JSONPatch
-> 执行并保存当前消息变量
```

对于带 `[mvu_update]` 的新卡，更新规则会留在主模型提示中。对于规则混在普通世界书条目的旧卡，原条目同样保留。

这个模式的特点：

- 只有一次常规模型请求。
- 正文和变量由同一个模型生成。
- 主模型不输出更新块时，正文仍可显示，但变量不会变化。
- 当前没有额外模型事务中的“第二次定向修复请求”。
- 输出稳定性主要取决于卡片提示词和主模型能力。

## 7. 开启额外模型时的执行链路

开启额外模型后，默认设置为：

```text
更新方式 = 额外模型解析
启用自动请求 = true
模型来源 = 与插头相同
应答格式 = 聊天消息
最大上下文 = 64000 token
最大回复 = 20000 token
```

### 7.1 能分离的新式卡

卡片使用 `[mvu_plot]` 和 `[mvu_update]` 时：

```text
主模型：接收剧情条目和当前状态，主要生成正文
额外模型：接收更新条目、当前状态、最近正文和聊天历史，生成变量更新
```

Nora 只在主模型请求阶段抑制 `[mvu_update]`，额外分析阶段仍可读取更新规则。

### 7.2 无法安全分离的旧卡

旧卡可能把剧情、输出格式和变量规则写在同一个世界书条目中。Nora 无法确认删除其中一部分是否会破坏正文，因此会保留原条目。

这意味着旧卡在额外模型模式下仍然依赖卡片自身结构，不能假设所有旧卡都实现了完全干净的“正文模型只写剧情、变量模型只写变量”。

### 7.3 额外模型安全事务

额外模型返回结果后，Nora 当前执行：

```text
保存原正文和上一份有效快照
-> 请求额外模型
-> 把更新块追加到候选消息
-> 在变量副本上解析和校验
-> 检查当前聊天和正文是否仍是原请求对象
-> 成功后一次提交正文更新块和变量快照
```

保护规则：

- 每次额外模型请求最多 120 秒。
- 第一次解析或校验失败时，最多进行一次带具体错误信息的修复请求。
- 网络错误、超时等请求阶段错误不会立即重复，以免重叠请求和重复计费。
- 更新期间如果用户切换聊天或正文发生变化，拒绝提交陈旧结果。
- 最终失败时恢复上一份有效变量快照。
- 显式空 JSONPatch 作为成功 no-op，不把无变化误报成解析失败。

这些安全事务主要保护额外模型路径，不代表关闭额外模型后的主模型路径拥有完全相同的重试行为。

## 8. Zod 在两种格式之后做什么

Zod 是卡片可选能力，不是所有 MVU 卡都具备。

当卡片注册了 Zod Schema 时，Nora 的本地 `mvu-zod.js` 会：

1. 初始化时解析 `stat_data`。
2. 应用 Schema 默认值、类型转换和卡片定义的 transform。
3. 每条解析后的命令先应用到状态副本。
4. 使用 Schema 检查结果。
5. 只接受通过校验的结果。
6. 在更新结束后标记 Schema 由 Nora 管理，并清理旧的展示增量字段。

Zod 可以检查：

- 数字、字符串、布尔值、数组和对象类型。
- 数值范围。
- 必需字段和默认值。
- 卡片定义的结构转换。
- 卡片定义的自动计算字段。

Zod 不能检查：

- 模型是否漏掉了剧情中应该更新的变量。
- 模型是否选对了角色或 UID。
- 一次关系变化是否应该加 1 还是加 5。
- 世界书的剧情语义是否合理。
- 模型是否根本没有输出更新块。

另外，Schema 中大量使用 `.default()`、`.catch()` 或 `z.coerce` 时，错误输入可能被替换为默认值，而不是直接报告失败。这是卡片 Schema 的设计选择，不是 Zod 自动提供的绝对严格性。

## 9. 两种格式的逐项比较

| 维度 | `_.set(...)` 旧格式 | JSONPatch 新格式 |
| --- | --- | --- |
| 载体 | JavaScript 风格自由文本 | JSON 数组 |
| 常见数据结构 | VWD `[值, 说明]` | 普通纯值 |
| 路径 | Lodash 点/括号路径 | JSON Pointer 斜杠路径 |
| 替换 | `_.set(path, old, new)` | `replace` |
| 数值增量 | `_.add(path, delta)` | `delta` |
| 插入 | `_.insert` / `_.assign` | `insert` / `add` |
| 删除 | `_.remove` / `_.unset` / `_.delete` | `remove` |
| 移动 | 无常用文本命令 | `move` |
| 旧值 | 模型常输出，但当前不做严格比较 | 不需要输出 |
| API JSON Schema | 不适合直接约束 | 适合 |
| 文本解析风险 | 引号、括号、分号风险高 | JSON 和标签仍可能出错 |
| 语义正确性 | 依赖模型和世界书 | 同样依赖模型和世界书 |
| Zod | 旧卡通常没有，但技术上可注册 | 新卡通常配套使用 |
| 额外模型分工 | 取决于旧世界书能否拆分 | `[mvu_plot]/[mvu_update]`可明确拆分 |

## 10. 同一剧情的两种输出

当前状态：

```text
时间：08:30
角色好感度：42
角色位置：指挥中心
```

剧情结果：

```text
经过五分钟，玩家兑现承诺，角色好感度增加 2，并移动到厨房。
```

旧格式：

```js
_.set('世界.时间', '08:30', '08:35');
_.set('角色.好感度', 42, 44);
_.set('角色.当前位置', '指挥中心', '厨房');
```

新格式：

```json
[
  {"op":"replace","path":"/世界/时间","value":"08:35"},
  {"op":"delta","path":"/角色/好感度","value":2},
  {"op":"replace","path":"/角色/当前位置","value":"厨房"}
]
```

两者最终都修改 `stat_data`。差别主要在模型表达更新的语法，以及卡片是否配套纯值结构、Zod 和世界书分离。

## 11. 当前兼容策略

Nora 当前识别以下 MVU 卡片形态：

| 协议识别 | 含义 |
| --- | --- |
| `native-split` | 存在 `[mvu_plot]` 或 `[mvu_update]`，适合拆分正文与变量提示 |
| `legacy-adaptable` | 发现旧更新内容，可以标记为更新条目 |
| `legacy-inline` | 变量引用与规则存在，但无法安全拆分 |
| `initialization-only` | 有初始化声明，但没有明确可识别的更新规则 |

当前版本的原则是保留卡片自己的更新方言：

- 旧 `_.set` 卡继续使用 `_.set`。
- JSONPatch 卡继续使用 JSONPatch。
- 不对所有模型全局强制 JSONPatch-only。
- 不因某张新卡工作正常，就宣布所有旧卡可以无损转换。

这项策略是在 `v2.1.2` 恢复的，`v2.1.4` 保留该行为。

## 12. 模型输出可靠性结论

从格式约束角度排序：

```text
自由文本 _.set
    < 自由文本 JSONPatch
    < API JSON Schema / 格式化输出
    < API 结构约束 + 路径检查 + 卡片 Zod
```

但最高一档仍然只能保证“输出结构和变量类型更可靠”，不能自动保证剧情语义完全正确。

必须把以下两类问题分开：

```text
格式错误：JSON坏了、标签缺失、路径字段缺失、类型错误
语义错误：改错角色、漏掉变化、变化幅度不合理、选择错误字段
```

JSON Schema 和 Zod 主要解决格式、类型和结构问题；角色卡世界书和模型判断负责语义问题。

## 13. 常见诊断状态

Nora 当前会区分：

| 状态/代码 | 含义 |
| --- | --- |
| `completed` | 命令成功并产生状态变化 |
| `no-change` | 有合法 no-op，或命令没有改变最终状态 |
| `no-command` | 没有解析到任何更新命令 |
| `MVU_NO_UPDATE_COMMAND` | 缺少可执行命令或更新块格式无法识别 |
| `MVU_NO_STATE_CHANGE` | 命令存在，但没有产生有效状态变化 |
| `MVU_COMMAND_VALIDATION_FAILED` | 命令被 Schema 或执行规则拒绝 |
| `MVU_RESPONSE_PARSE_FAILED` | 额外模型响应无法提取更新块 |
| `MVU_EXTRA_MODEL_TIMEOUT` | 额外模型请求超过 120 秒 |
| `MVU_CONTEXT_TOO_LARGE` | 额外模型上下文超过预算 |
| `MVU_STALE_CHAT` | 请求期间切换了聊天或正文已变化 |
| `MVU_SNAPSHOT_MISSING` | 更新前找不到有效变量快照 |

诊断观察器还会记录命令数量、是否改变状态、事务耗时、尝试次数和有限数量的校验错误，并在上报时限制内容长度、避免暴露密钥。

## 14. 当前明确没有实现的内容

截至本文基线，Nora 没有实现：

- 所有模型统一的语义事件输出协议。
- 所有模型默认强制 API 结构化输出。
- 一份同时生成 InitVar、Zod 和世界书的全局变量总表。
- 任意旧卡到新卡的自动语义迁移。
- 根据剧情自动判断所有遗漏变量的确定性程序。
- 把 `_.set` 的中间旧值升级为严格 compare-and-set。
- 让关闭额外模型和开启额外模型拥有完全相同的重试事务。

## 16. 最简总结

旧格式：

```text
模型输出 _.set(path, old, new)
-> MVU提取命令
-> 读取真实旧值
-> 使用最后一个参数写入
-> VWD字段只替换[0]
```

新格式：

```text
模型输出 <JSONPatch>[operations]</JSONPatch>
-> MVU解析JSON
-> 将 replace/delta/insert/remove/move 转成内部命令
-> 执行并接受可选 Zod 校验
-> 保存新的 stat_data
```

两种格式目前都在使用。JSONPatch 更适合现代结构化输出，但当前默认“聊天消息”模式仍然依赖模型遵守提示；`_.set` 兼容旧卡，但文本语法风险更高。
