## 3. 第一阶段：修正主分支结果判定，不改变协议

### 3.1 统一结果，而非用“数值变了”判断成功

在实际解析/执行处产生结果，由提交、观察器、UI 和诊断共同消费，不各自重算。
沿用现有 MVU 事件和 Nora 接口，不新增平行状态系统。

建议结果包括 outcome、协议/模式、消息身份、解析/接受/拒绝数量、是否有变化、
保存是否确认、失败阶段及有界错误摘要。数量应在正确阶段采集：
解析数量在 Zod 消费命令前记录，接受/拒绝结果由实际执行者报告。
不能把“没有错误日志”或“命令数组清空”直接当作成功。

| 情况 | 判定及动作 |
| --- | --- |
| 命令有效，状态发生变化且保存确认 | updated；显示已更新 |
| 命令有效、执行完成，但最终状态相同 | unchanged；不重试、不报错；仍按既有规则保留该消息应有的状态快照 |
| 协议明确表达无需更新 | unchanged；不必为此向正文追加空更新块，快照归属不能丢失 |
| 普通正文没有变量命令，且没有显式更新载荷 | skipped / no-command；仅表示本次未更新，不冒充成功，也不必一律报失败 |
| 额外模型没有有效更新载荷，或存在格式错误的更新块 | rejected；不能伪装成无需更新 |
| 保存未确认 | persistence-unknown；不宣布已更新，不自动重复增量操作 |
| 用户取消、切换世界、消息被编辑 | cancelled / stale；不得写入新消息，也不归咎于模型格式 |

第一阶段不改变现有额外模型的整批拒绝规则。部分成功语义放到第二阶段，避免修误报时顺手改变旧卡行为。
旧卡自由文本的“本轮无需更新”没有统一可靠语法，不能新增一个随意的中文文本猜测器。
某卡明确要求每轮必须给更新块时，缺失要体现为协议未满足；来源不明确则显示未观察到更新。

### 3.2 用户反馈

保留现有模型开关、来源选择、独立模型设置、状态提示及其处理函数，不重做界面。
成功/无变化仍 1 秒，失败仍 3 秒；取消/跳过不是红色失败。
正文生成、变量处理、卡片渲染是三个结果，不把 MVU 失败包装成正文生成失败。
三秒提示消失后，已有能力状态/诊断接口仍须能查到该消息的原因；若需新增详情或重试控件，
先列出现有 UI 入口及缺口取得确认，不自行扩展界面。

## 4. 第二阶段：旧卡兼容，先不接新协议

### 4.1 状态处理与 Zod

原生解析和执行器继续拥有字段处理；不按当前空对象/空数组猜一份强制 Schema。
无 Zod 是正常能力状态；有 Zod 时沿用原注册、转换、校验及事件语义。
“没有 Zod”与“卡声明了 Zod 但加载/注册失败”必须区分，后者不能静默跳过校验。
原生 MVU 的 schema/template 与 Zod 不是同一个概念，不能混为单一布尔条件。

为原卡保留原生部分更新语义需做有界差异验证：有效命令按上游实际行为处理，
拒绝项单独反馈，结果为 partial 而非“全部成功”。若候选或脚本已产生部分效果，
不得自动重跑整批增量命令；第一版不实现“只重试失败命令”的新机制。
此行为相对当前主分支更宽松，须作为独立变更验收，不伪称只是内部整理。

### 4.2 提示词、触发和原有显示

关闭额外模型：保留卡本来给正文的更新格式、世界书规则、宏和标签；不发第二次请求。
开启额外模型：采用原 MVU/卡片约定的响应格式及原生解析，不统一塞 Nora 协议。
按原支持条件处理无可用额外模型的情形；必要的原生回退必须报告“实际使用正文解析”，
不能配置上显示额外模型成功而实际没有执行它。

检查并收紧导入时按 `_.set` 等文本给整个混合条目标记为变量规则的行为：
人物设定不能因此从正文消失。优先保留旧卡内容与触发条件，以请求内投影提供变量依据，
不修改原 PNG、持久化条目或把世界书全量永久常驻。实际入口与构建需共用分类结果。
不要仅为“没有 split 标记”自动关闭原卡内容，也不能承诺没有更新规则的卡可被凭空推断玩法。

原卡若依赖正文标签触发正则，保留这些要求及正则顺序。程序不能删掉标签后假设 MVU 会自动补出美化。
未知外部脚本/API/网络依赖需报告范围；不声称支持任意第三方代码或通过放开任意远程脚本解决兼容。

## 5. 第三阶段：显式接入 Nora 协议与新卡制作

只有第二阶段验证通过后才实施，不将远端实验整体混入主分支。

### 5.1 三个维度只解析一次

| 维度 | 来源 | 不允许的推断 |
| --- | --- | --- |
| 协议 legacy / nora-mvu/1 | 当前卡绑定主世界书的专属声明 | 不因有 Zod、卡名含 Nora 或正文引用示例就切换 |
| 模式 inline / extra-model | 用户设置 | 标记不强制打开额外模型；选择供应商不替代模式开关 |
| 校验 native / zod | 实际可用且正确注册的能力 | 无 Zod 不等于禁止更新；注册失败不等于无 Zod |

形成一个请求生命周期内稳定的接入描述，供提示词、响应解析、执行和反馈复用。
若期间卡片、聊天或配置改变，结果视为过期，不混用新旧协议。

### 5.2 专属声明与路由

复用已有 `[nora_mvu/1]` 标记，不再另创一个含义相近的扩展字段。
建议技能生成一个启用、常驻的专属条目，comment 为 `[mvu_update][nora_mvu/1] 变量更新规则`。
这里只写业务条件；具体输出协议由程序提供，避免技能模板和程序分别维护两套语法。
声明从绑定主世界书的条目元数据读取，不依赖当轮关键词是否命中或是否恰好进入 token 预算；
禁用声明不启用新协议；相同版本重复声明不重复注入，冲突/未知版本明确报错，不静默降级。
复制的聊天示例、次级世界书中偶然出现标记不得改变当前卡协议。

| 卡片协议 | 关闭额外模型 | 开启额外模型 |
| --- | --- | --- |
| 无专属声明的原卡 | 原卡正文输出，原生解析 | 原卡/原 MVU 额外请求格式，原生解析 |
| 声明 Nora v1 | 正文剧情 + 单个 Nora 更新块；一次请求 | 正文与变量分开请求；变量返回 Nora envelope |

新协议共享一份操作定义，由其生成提示、工具参数和解析校验。内联和额外请求只换包装，
不维护两套操作含义。Nora 包含的旧命令字符串只是数据，不能再次被旧解析器执行。
协议错误不偷偷尝试另一套解析器；无 Zod 时仍校验 envelope、路径、值安全并用原生执行器。
有 Zod 时增加字段投影和业务校验；字段投影不能把任意自定义函数宣称为已翻译的约束。

新协议可采用候选状态整批校验、通过后提交；Nora 卡的扩展回调必须区分候选处理与持久副作用。
调用了克隆状态不代表旧脚本没有外部副作用，不能承诺所有回调天然可回滚。

### 5.3 技能职责

只修改新卡制作与检测：明确生成声明、业务定义/初值、规则和可工作的显示接口。
旧卡导入不以不符合 Nora 新卡标准为理由判运行不合格或强制改造。
技能导出后重新读取实际 PNG/JSON 检查声明和扩展保留；有标记不等于运行成功。
新卡两种模式均需检查正文、变量、正则全链及按钮。没有确定显示入口时停止该功能交付，
不再让模型自由生成一套前端代码冒充固定渲染。

## 6. 重试、持久化与资源控制

- 第一阶段保持 main 的最多两次尝试（首次 + 一次格式/校验纠正），不偷偷导入实验版三次默认值。
- 后续若调整增强协议为三次，单独说明含首次总次数、费用和延时，作为配置决策确认。
- 网络/鉴权/供应商不支持/注册缺失不靠反复请求修复；请求中止后须阻止迟到结果写入。
- 同一消息的自动触发和手动重试不能并发执行；重复事件不能让 increment 执行两次。
- 保存流程有消息和变量等多个调用。不能把“先校验后保存”称作数据库原子事务。
  需验证各保存点故障、重新读取与恢复；如确需新增后端事务接口，先报告范围扩张再确认。
- 手动重试须验证原消息、上一快照与替换范围；失败时不能删除用户原有有效状态或更新块。
- 复用现有有界诊断：身份、模式/协议、结果、错误阶段、次数和耗时；不常驻保存全文、Key、完整变量。
  成功不再误写失败日志。详细调试只按授权限时启用。
- 不自动提升回复 token、上下文上限或改思考开关；原卡不注入 Nora 协议及 Zod 投影。

## 7. 实施位置与验证顺序

实现位置：nora-mvu 上游源码补丁、mvu-zod、update-observer、runtime/index；
nora-compat 的声明/分流；必要的 UI 状态映射与有界诊断；最后是 nora/skills/creative/nora-cardforge。
遵循 ADR 0003 和 0008：ST 细节留在适配层；MVU 故障不重新激活世界、不清空正文。
不手改压缩 bundle；使用固定上游重建并更新运行资源版本，证明源码与产物一致。

每阶段先建立会失败的真实调用链回归，再改实现。静态字符串检查只能证明代码存在。

第一阶段验收：合法重复 set、显式 no-op、缺命令、坏格式、Zod 消费命令、
保存失败/过期结果分别得到正确结果；UI 与诊断一致，合法无变化不增加模型请求。

第二阶段验收：原卡有/无 Zod × 两种模式；包含元组 `[值,说明]`、动态对象、数组、
默认值/转换、部分命令失败、编辑/重生成/Swipe、重试防重、切世界及重载快照。
验证真实最终请求的世界书触发、设定未丢失，以及从原正文经过全部正则到最终脚本的显示流程。

第三阶段验收：再覆盖 Nora v1 有/无 Zod × 两种模式，形成至少八个基础组合。
缺失/禁用/冲突声明、错误的 Zod、工具不支持、重复事件、未知协议均需负面案例。
模型实测只用非性剧情，逐轮核对请求格式、执行结果、保存回读与显示；模型语义准确率单列。
不因十轮成功宣称所有模型或第三方卡零失败。

本方案不授权提交、推送、部署、真实付费模型测试或操作浏览器。
每阶段分别报告实现、技术验证、用户效果验证和部署状态；用户确认后才推进发布。
