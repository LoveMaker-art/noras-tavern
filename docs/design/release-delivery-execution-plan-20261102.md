# 更新构建上传与发布流程优化执行方案

日期：2026-11-02。状态：用户已授权实施，集中于 `codex/release-pipeline-stability-20261102`；当前实现、验证及缺口见[任务记录](../launcher-reliability-plan.md#release-pipeline-stability-20261102)。未验证首次总耗时改善。

源码审查基线：主分支 `e1c21f527c2a7fe8736cbcebc8ba354abd66246c`，产品设计 1.45。实施时重新固定当时的主分支及远端身份，不能直接把本次审查摘要当作新源码的验证结果。

## 一 目标和范围

本轮解决反复出现的测试夹具错误、流程入口错误、重复构建和重跑、未变大资源重复分发，以及缺乏可比较耗时记录的问题。普通核心更新和包含启动器变化的发布均在范围内；必须分别检查它们实际使用的工作流。

完成应体现为：夹具错误在最早适用阶段稳定发现；纯测试或发布工具修正不迫使未变产品重建或连续升版本；失败能够保留有效检查与产物；兼容条件允许时不重传未变大资源；正常发布及失败恢复的耗时和传输量可核对。一次流水线变绿或测试总数增加，不构成完成依据。

本方案只安排发布流程、测试入口、夹具、验证工具和相关文档的修改。不修改产品运行逻辑、用户配置与数据，不升级 Hermes 或用户运行环境，不恢复已删除的发布流程分支，不顺带整合其他工作区。不新增并行发布系统、跨仓架构或任意跳过检查的开关。

用户后续已明确要求按本方案实施。代码、目标环境验证、主分支与 GitHub 生效分别留证；真实测试资源的公网写入、正式切换仍遵守下文独立授权条件。不修改正式通道、覆盖历史资源或替换用户程序。

## 四 统一执行路径

统一的是计划及准入规则，核心组件与完整安装包仍使用现有两条生产路径。

| 阶段 | 执行内容 | 产出及进入下一阶段的条件 |
| --- | --- | --- |
| 计划与快速检查 | 固定源码、比较基线、历史升级基线、实际变化和平台；核对夹具及环境前提 | 计划、范围和原因可复核；便携必需检查通过，未知输入已处理 |
| 平台源码及前提检查 | 在适用平台运行对应源码组；每台新 VM 核验自身解释器、依赖和能力 | 本平台检查结果及工具身份；尚无环境时不伪称真实 Hermes 验收已完成 |
| 构建与封存 | 准备真正变化的环境、组件或 APP，复用有来源和摘要证明的旧资源 | 固定原包及资源清单；构造输入、来源和生产任务均有效 |
| 目标环境验收 | 从原包恢复隔离实例，执行本次必需用户流程和失败路径 | 报告绑定原包、测试与环境；全部必需结果通过、服务与任务正确结束 |
| 分发准备 | 核验最终消费者，封存计划，检查并补传缺失资源，逐站回读 | 所选渠道都已准备完成；不改变正式入口 |
| 正式切换 | 在独立授权后恢复原准备检查点，核对并切换渠道，再回查用户入口 | 所选渠道及用户入口全部符合原计划，才能记为已发布 |

构建前快速反馈以十分钟以内为优化目标，排队和依赖下载单独计量；它不是全流程时限，也不能成为删用例或放宽产品超时的理由。首次总时长没有先验分钟承诺。

### 组件阶段拆分

复用现有阶段交接模块，将组件路径至少分开保存源码资格、封存组件交付和各平台最终验收结果。源码资格成功后，成品验收失败不重复该资格；构建已成功时，纯验收修正不重新编译原包。

每份检查点只保存该消费者实际需要的普通文件、必要相对链接和原始证据，不归档整台 VM、运行中的进程、用户 home、完整构建依赖或重复业务 payload。每台新 VM 仍检查自身条件，不从上一阶段继承“环境一定可用”的假设。依赖真实 Hermes 的验证在恢复并核验该环境后执行。

组件环境准备是否再单独拆成任务，由前后耗时决定。若额外归档和机器准备代价大于节省的重跑，不强行新增任务；仍应保留已封存组件和完成的源码资格。不能为了阶段数量让首次执行更慢。

## 五 夹具清理和长期维护

先完整审查发布实际调用的测试闭包，包括独立 fixture 文件、辅助构造函数、内联临时目录、假进程、配置、报告、归档及间接调用。使用实际工作流与测试入口提取引用；动态生成及运行时调用单独核对，不能仅凭文本搜索无命中判定无用。不扩展到未被本次发布路径调用的第三方测试库。

清单至少记录：被保护的结果、消费者、源码／原生／成品要求、平台与能力、依赖、数据格式和来源、资源清理方法及最终处理。清单是本次核对结果；后续运行所需的平台和依赖声明集中在现有入口或辅助函数，避免维护另一份互相漂移的分类表。

| 处理 | 允许条件 | 必需验证 |
| --- | --- | --- |
| 保留 | 覆盖有效功能、支持范围或独有失败路径 | 在声明环境可执行；保护目标明确 |
| 修正 | 原保护结果仍成立，执行前提或格式已变化 | 保留原失败；按同一入口修正并验证，不能只改期望值使其通过 |
| 合并 | 相同输入、调用路径和保护断言重复 | 保留所有独有平台、并发、边界和失败场景；不能把接口不同的测试只因结果相似而合并 |
| 删除 | 功能已取消、确无有效消费者，或等价保护已存在 | 给出对应设计／调用依据及保留测试；关键保护用故障注入确认仍有效 |

历史迁移样本按原发布的格式和来源冻结，不能随着当前版本更新，不能因日期旧直接删除。当前协议和目录样本尽量经正式生产者构造，保留独立的关键断言及有意破坏输入，避免生成器和验证器一起错仍然通过。样本不包含正式聊天、Key、配对码或生产配置。

必须审查固定路径、共享端口、全机进程扫描互相干扰、继承本机环境、残留服务、固定休眠及不必要的源码文本耦合。就绪判断使用实际状态和有限截止；并发仅在目录、端口、进程和写入隔离成立时启用。必要的安全命令、来源及执行顺序断言继续保留，不一概删掉文本检查。

CI 测试工具使用可取得的固定版本组合并记录身份，优先核对现有阶段协议的 Node 24.19.0／Python 3.11.9；这是验证解释器，不是更换用户运行时。工具不可取得时先修正并验证其合同，不运行时降级或漂移到 latest。超时依据实际平台记录设定，区分测试启动、用例执行和产品业务截止；不能靠无限等待或提高产品超时使夹具通过。

失败原因依据日志和复现分类。不得把失败自动认定为过期夹具，不以重复运行到偶然通过作为修复，也不将唯一关键保护直接隔离出发布门禁。报告明确区分失败、超时、未执行及平台不适用；最后一项不能记为通过。

### 必须纳入的历史流程故障

| 场景 | 最早适用检查及保护结果 |
| --- | --- |
| Linux runner 无固定 Python 资源 | CI 使用支持该工具组合的明确镜像；工具准备前核对版本可取得，不回退浮动 latest |
| 恢复夹具先运行、引擎依赖后安装 | 从工作流消费者核对同锁依赖先于首次使用；每台新 VM 各自核验 |
| Windows 环境缺 SystemRoot、UTF-8、受管 Python 根 | 原生夹具用明确隔离环境执行最小实际子进程；保留凭据和用户目录隔离 |
| 路径、文件 URL、系统换行或 POSIX 权限假设 | 验证路径语义及实际写入行为；系统不提供的语义不伪装成已验证 |
| 原命令直接运行而实际需要交付布局映射 | 对照工作流原命令测试，不将映射入口成功冒充直接入口成功 |
| Ubuntu 执行桌面 APP 专属测试 | 根据平台与实际能力分配，保留跨平台核心检查；不在 Linux 伪造桌面资格 |
| Windows 相对脚本被进程归属检查拒绝 | 提前运行真实启动包装命令，不放宽产品进程身份校验 |
| 合法运行时链接被结果收集器递归拒绝 | 安装树与证据树分别检查；合法运行时链接可存在，证据链接及越界仍拒绝 |
| Actions 多路径上传改变报告共同父目录 | 按工作流实际上传结构生产／消费原始报告；缺状态、跨根混放和篡改仍拒绝 |
| 发布前过滤元数据导致原封装证明缺文件 | 先逐件核对原封装，再生成公开资源集合；同名平台元数据分别校验 |
| 集成夹具竞争、进程遗留及不合理等待 | 在隔离条件下验证就绪与清理；保持原业务截止，不靠提高产品超时掩盖问题 |

上述场景先使用最小有效夹具重放，不为每种错误重新构建整套产品。必须依赖真实系统或最终成品的场景仍在对应环境执行，不能承诺全部错误都能在便携预检中发现。

## 六 按实际变化选择检查

| 改动 | 重新执行 | 可复用的部分 |
| --- | --- | --- |
| 文档或纯发布工具 | 对应格式、工具行为、来源及消费者检查 | 未变产品及其仍有效的目标环境结果 |
| 测试或夹具 | 修订用例、直接关联保护及受影响环境下的原包验收 | 原构建产物；旧测试的相关绿色结果不能冒充新测试通过 |
| 普通核心业务、规则、技能 | 对应实际功能、共用接口、受影响数据与本次成品组合 | 有输入等价依据的 APP、环境及无关检查；技能不因目录名称自动获得精简资格 |
| 安装、更新、恢复、卸载、实例归属及持久化 | 受影响维护与数据保护完整相关组、对应目标环境和失败路径 | 真正未变的构造资源；完整回归不等于必须重建 Hermes |
| APP 或运行环境 | 改变平台的构造与原生验收及相应兼容组合 | 其他已证明未变的内容 |
| 无法确定影响 | 先分析；证据仍不足时执行保守相关范围 | 不自动授予快速路径 |

判断必须沿调用方、持久化及共用协议追踪，不以改动行数或 `launcher` 目录名称代替。多个范围取并集，重复文件在同一执行条件下只运行一次；真实解释器、权限或产物不同的检查不能仅凭文件名去重。

第一版不削减当前组件发布的三个桌面平台首装、运行及停止态升级组合。缩短普通核心路径主要依靠避免无关整套桌面源码回归、避免重复准备和传输。每次关键安装、更新、恢复、卸载和数据保护要求均有具体执行结果或有效复用依据，不能只写“保留”。

Linux 并行消费同一封存核心，不增加图形启动器或另一套核心构建。核心产物发布补充隔离 Linux 升级及原数据读取；涉及维护机制时追加依赖复用／真实重新准备依赖、运行／停止态、失败恢复及任务结束。使用最小测试数据和合成凭据，不调用外部模型或操作正式实例。

## 七 产品身份与验证身份

这是减少“改一份夹具就再构建三平台”的关键工作，不能只靠把大任务分开。

一般同提交阶段续跑继续沿用现有规则。对于纯测试或验收工具修正，采用现有工作流中的显式原包重新验收入口：分别记录原产品来源和当前验证来源，从可信 API 取得原产物，实际重跑受影响验证，生成新证据。它不是跨提交缓存测试成功，也不是把旧失败状态改成成功。

允许该入口必须同时满足：

1. 原产品构建生产任务成功，原包可按 API 身份、大小和完整摘要恢复。
2. 产品构造输入、依赖、目标环境资源及交付字节不变；仅“业务文件没改”不足以证明这一点，构建命令、模式和外部固定输入也需比较。
3. 新测试／验证工具及解释器、平台和原始执行结果明确记录；受影响用例实际执行，不借旧绿色结果。
4. 旧报告保持原结论；旧来源中未结束、失败或缺少的产品操作不能靠补 JSON 放行。
5. 最终消费者能够同时核验产品与新验证证据；做不到时拒绝该复用，不增加 skip 参数。

回执至少能核对原产品提交／包摘要、构建任务及 artifact 身份、验证提交与测试输入摘要、平台环境、执行任务、各场景结果和与上游的关联。具体字段沿用现有回执，必要扩展明确版本及旧来源处理，不伪装旧协议已提供新证明。

| 变化或故障 | 必要重做范围 |
| --- | --- |
| 同输入的平台验收失败 | 该平台失败验收及依赖它的最终汇总；有效源码和原包保留 |
| 源码检查失败但产品构造输入未变，修正纯夹具 | 新夹具检查及受影响验收；经上述准入保留原产品包 |
| 测试／环境条件变化 | 对应检查结果失效；未变字节仍可作为原包重新验收 |
| 产品或构造输入变化 | 重建改变内容并重验受影响流程；下游旧结果失效 |
| 仅最终汇总失败 | 沿现有受限续验，重验原始事实及原包，不重跑成功平台 |
| 上传或渠道准备失败 | 按原计划恢复对象状态并补传，不重建产品 |
| 来源、摘要、上游关联不符或检查点过期 | 阻断对应恢复；取得有效来源或重做必要生产阶段 |

前置检查完成后再冻结正式候选。使用提交／构建编号区分内部尝试；纯测试或发布工具失败不自动抬高产品版本。新字节必须有新候选身份，已发布标签和资产不移动、不覆盖，不能把候选重试设计成改写旧产物。

## 八 资源引用和兼容迁移

第一步按资源逐件区分变化组件、不变环境、不变 APP、控制元数据及真正需要的新完整安装器。下载、构建、内部归档传输和公网分发分别统计，不能将环境免构建记为已经免上传。

继续复用现有 `shared`、`asset-catalogue.mjs`、固定索引和 `component-release.json`，不创造新资源协议。只有来自可信正式版本、大小和全文摘要一致、旧入口解析兼容的资源才允许引用。新版本传新对象及控制元数据；旧对象继续按原身份存在，不重新写入旧版本目录。

启用前必须完成以下兼容核对：

| 入口 | 必须证明 |
| --- | --- |
| 当前支持的旧 APP 已有安装 | 从原检查更新入口正常接入，APP／核心顺序正确，任务可继续及恢复 |
| 已封存的旧维护计划 | 不改写计划、索引或原重试凭据；仍能恢复原来的真实状态 |
| 当前 APP 新安装 | 三个平台取得完整引用闭包，包含无本地依赖的冷安装 |
| 复用旧安装器 | 按官网／原入口取得当前目标组合，底包版本如实显示 |
| Linux 无 APP 更新及旧接入脚本 | 不要求桌面资格，能取得并校验所需核心与依赖 |
| GitHub 和极狐来源 | 正常来源、备用来源及有界失败恢复均遵守允许地址、大小和摘要规则 |

测试集合按已经承诺的支持范围和正式资产确定，纳入现有 `published-v2.4.4` 协议样本、当前正式组合及实际需要的过渡入口。保留样本不自动扩大已验收支持范围。旧客户端不支持引用时，先验证其可用的 legacy 桥接路径；不能只提高最低版本或要求用户手工删除记录。

当前 shared 实现对旧客户端和最低版本的限制是真实阻断，不能仅删掉检查。若现有过渡路径无法同时保留支持范围并减少重复分发，停止启用，列明需要的客户端／分发行为变更及影响，按变更控制确认；该项仍记未完成，不能以其他项目通过代替。兼容通过前保留 legacy。

每个平台只需自身资源的内部下载是否能进一步裁剪，先依据实际字节及关键路径决定；不先重构全部 artifact 格式。无论如何裁剪，最终汇总和发布仍核验完整交付集合。

## 九 耗时和稳定性记录

沿用工作流、检查点和对象进度记录生成统一结果，不新增常驻监控服务。每轮记录排队、环境与依赖下载、快速检查、完整相关回归、构建、归档交接、原生验收、资源准备、切换和回查。总耗时按起止时间计算，不能将并行 job 时长相加冒充用户等待时间。

至少区分以下量：新构建字节、内部 artifact 传输字节、公网新增上传字节、引用资源字节、核验读取字节、失败重传字节、缓存冷热、调用次数和恢复耗时。无法观测的网络流量标记未测，不用资源计划大小代替。每个复用结果写明来源和依据，每个重跑写明失效原因。

基线先复用已有 2.6.0、2.6.4 原始日志及有效摘要，不为收集基线再全量重建旧版本。性能对照使用同一批原始输入和同样缓存条件；历史输入不等价时只能报告参考，不能宣称准确节省比例。上传器可用同一批小型及代表性大资源分别对照，不重新构建业务。

必须报告正常小改动与公共维护变化两类路径，不能拿纯文档检查与旧完整安装包比较。对排队、传输和测试执行分别解释，不能把全部时间归给带宽。

以下结构性指标作为硬验收，不设未经测量的百分比：

| 指标 | 目标 |
| --- | --- |
| 纯夹具／发布工具修订且产品输入未变时，重复产品构建次数 | 0；受影响验证仍实际执行 |
| 同输入的最终验收恢复中，重复有效源码／封装阶段次数 | 0；原资格必须可核验 |
| 续传时，对已有完整确认对象的再次创建次数 | 0；必要回读不算重新上传 |
| shared 验收通过后，新版本下重新创建未变大资源次数 | 0；控制元数据及明确必要的新安装器另计 |
| 已知流程错误被忽略、必要场景被无依据跳过、失败被记为通过 | 0 |

## 十 实施顺序及修改位置

所有阶段集中在后续获授权建立的一个新分支；不恢复已删除分支，不直接修改正式工作区。先审查再修改，按阶段留下可审阅结果，未达准入不继续耗时构建。

| 阶段 | 主要位置 | 交付与进入下一步条件 |
| --- | --- | --- |
| 0 固定基线及记录口径 | 现有发行记录、计划与工作流日志 | 本次范围、适用基线、两条路径的已有能力、历史失败清单及耗时口径固定 |
| 1 清理夹具与核对真实入口 | `tests/helpers/`、发布相关测试、`launcher-test-environment.mjs`、实际工作流 | 保留／修正／合并／删除清单，历史失败最小重放和保护保持证明通过；无无依据跳过 |
| 2 收敛检查范围 | `release-plan.mjs`、`launcher-test-impact.mjs`、两条构建工作流 | 代表性变更分流与边界反例通过；普通业务不误走无关全组，公共维护不漏验 |
| 3 组件续跑及原包重验 | `publish-component-update.yml`、`launcher-platform-stages.yml`、`build-stage.cjs`、`component-acceptance.mjs`、`publication-source.cjs` | 同输入续跑、纯工具修订重验、错来源及变化输入拒绝通过；产品包不被重建或改写 |
| 4 固定 Linux 验收 | 现有组件工作流、生命周期／独立更新测试入口 | 隔离安装与数据、依赖两路径、升级、读取、恢复及结束证据可重复取得 |
| 5 完成资源兼容与传输优化 | 现有资源目录、系统清单消费者、发布状态与供应商模块 | 各支持入口兼容；新对象与引用明确；两渠道完整性及续传不削弱 |
| 6 一次固定候选综合验收 | 两条已有工作流、来源消费者及统一报告 | 达成下一节全部条件，输出通过、阻断及实测收益；不靠连续升号和全量重建尝试 |

耗时记录从阶段 0 开始贯穿实施，阶段 1 后即可检查选择与成本，不能等全部改完才第一次计量。阶段 5 的兼容准备可与其他代码审查并行，但未通过不得切默认分发方式。Linux 采用已有隔离运行入口，不新增另一套生命周期实现。

实际修改清单在各阶段开始时按代码依赖核对，表中是职责定位，不要求为每项新建文件。删除旧实现与新增实现一起审查，防止两套计划器、重复注册表或不断增长的专用 shell 豁免。

## 十一 验收设计

先完成无需产品构建的合同和最小夹具验证，再在固定候选上执行目标环境流程。不把每种失败注入都变成一次全量三平台构建。

| 编号 | 验收 | 必须看到的结果 |
| --- | --- | --- |
| A1 | 从干净目录按原命令运行夹具和前提检查 | 无本机残留依赖；每个目标平台均核对对应能力；资源及进程正常清理 |
| A2 | 本文列出的历史流程故障最小重放 | 旧错误可触发，新检查在最早适用阶段拒绝；正常与恶意布局均有实际断言 |
| A3 | 删除／合并关键测试的保护复核 | 注入其原来捕获的故障，剩余检查仍失败；无独有场景丢失 |
| A4 | 文档、普通核心、公共维护、APP、环境及未知输入的代表性变更 | 构建与检查选择正确，纯工具不产生产品包，未知输入不获得复用资格 |
| A5 | 同一产品包修正验证工具 | 原包摘要不变，新验证实际执行、身份分别记录；修改产品字节或缺必要证据仍拒绝 |
| A6 | 正常候选在桌面及 Linux 验收 | 所需场景和数据保护通过；失败／跳过／未执行分别记载，不以健康接口替代原数据读取 |
| A7 | 在一个平台源码资格及原包已保存后受控中断最终验收，再恢复 | 仅失败阶段和必要下游重跑；其他平台与有效前置不重做；完成完整最终验收，不拼接半条恢复事务 |
| A8 | 错误摘要、过期归档、缺报告、变化依赖／测试／上游身份 | 对应复用被拒；不能通过修改检查点或重签自填 JSON 放行 |
| A9 | 同一原包上传中断及状态恢复 | 已确认对象不重复上传；原计划和字节不变；未确认写入按原规则核对，不盲目重传 |
| A10 | 旧客户端迁移、新安装、引用资源和两来源读取 | 所有适用入口可用；未变大资源没有在新批次重新创建；旧资源仍可访问 |
| A11 | 两渠道准备和切换工具的正常／部分失败场景 | 准备不改变正式入口；不完整准备不能切换；部分成功如实记录并只恢复未完成部分 |
| A12 | 正常路径及受控续跑的统一报告 | 原始结果能重算耗时和字节，明确每项优化省掉的重复工作和新增开销 |

源码合同分别覆盖完整安装包和组件入口。真实综合验证优先使用与关键改动一致的一个固定候选，复用合法的已封存环境；不能因环境没变免除本次成品组合验证。完整安装包的封装裁剪或恢复代码一旦修改，仍需真实安装器验收，不能用组件包通过代替。代表性工具故障先用小归档及隔离传输重放，只有需要目标环境的故障才在原生任务注入。

源码卸载保护、实际删除范围验证及 NSIS 窗口交互分别记载。既有未验界面不因本轮测试清理自动变为已通过；本轮修改若直接影响卸载交接或安装器恢复，相关真实场景属于必须补验的直接影响范围。

真实 CI 和公网演练属于后续独立授权阶段。真实上传采用正式通道之外的明确测试资源；如客户端限制要求公开预发布才能验证，先说明具体对象及渠道并取得授权。模拟服务、认证草稿下载和匿名正式入口各自举证，不能互相冒充。正式 `stable`、`launcher-stable`、GitHub latest、官网缓存及用户实例在测试期间不变。

## 十二 停止条件和完成判定

以下情况停止相关阶段，保留现有有效结果，不继续改版本并重新开启全量流水线：

- 必需源码／夹具检查失败且原因未定位，或真实工作流命令尚未核对。
- 原包、测试、环境或归档的身份无法建立，或恢复需要跳过既有保护。
- shared 兼容失败、引用资源不完整或需要改变支持承诺。
- 拆阶段新增的准备和归档开销使同条件正常路径更慢；回到实际失败边界收敛，不保留无收益拆分。
- 清理导致独有保护消失，或用例只有反复重跑才偶然通过。

只停止依赖该条件的工作，可继续不受影响的分析及验证；不能以某项阻断为理由丢弃有效产物，也不能把其他项目通过代替阻断项完成。

实施完成至少需要：夹具去留清单闭合；两条发布入口按同一选择及来源规则执行；组件阶段续跑与原包重验通过；Linux 验收进入固定入口；资源引用完成兼容验证和实际传输核对；统一结果能证明重复工作及流程性返工减少。若 shared 迁移等项未通过，明确报告部分完成和阻断，不宣称六类问题全部解决。

对首次总耗时，只有同条件测量改善才能写为提速；拆阶段或补 Linux 验收本身不保证首次更快。对稳定性，可报告已知错误模式的前置发现、干净环境验证及受控续跑结果；一次成功不足以证明长期失败率已经下降。后续正式运行沿用同一口径累积记录，不为统计额外反复构建。

最终交付包括：实际代码差异与职责说明、夹具清理明细、关键验收保持对照、原始执行和复用来源、失败恢复结果、各阶段时间与实际字节、仍未验事项及启用条件。安装、更新、恢复、卸载和数据保护分别报告，测试数量不作为效果指标。

本方案与现行共同交付目标一致。实施中按已确认规则修订唯一执行文档；若涉及支持范围、客户端发现协议、最低版本或默认行为变化，先按产品变更控制确认，不能由实现或测试自动改写基线。代码、技术验证、真实流程验证、GitHub 启用和正式发布分别报告，不将本地分支通过写成正式流程已经生效。
