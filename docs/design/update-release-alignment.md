## 3 拟实现的执行流程

### 诺拉入口

1. 查询本实例适用核心目标；只有 APP 变化时不提醒核心更新，也不启动核心替换。
2. 用户授权更新后，将固定核心目标交给已实现的同一独立任务，保留真实更新器和安装资格校验。
3. 诺拉停止或会话断开后，任务继续；恢复连接读取原结果。流程不读取桌面 APP 在线状态作为执行资格，不承担 APP 替换。

### 桌面入口

1. 一次检查返回核心与 APP 各自当前／目标版本及所需阶段；目标固定后不在第二阶段偷偷追随新的 latest。
2. 用户点击原安装更新按钮后，核验资源、兼容组合与恢复条件。优先在修改前准备本次需要的资源；仅一项变化时不准备另一项替换。
3. 在现有任务和 APP 交接机制上依次执行，成功阶段留下可核验结果。受控 APP 重开后继续原协调结果，不让用户再次发起另一项更新。
4. 两项完成后分别检查实际版本、身份、运行及数据，确认实际写者和恢复均结束，展示结果并释放维护占用。
5. 某项失败时按基线 PB-06 第 4 项判断保留或恢复；正常重试只补失败项，仍重新核验成功部分。再次出现新版时，用户另行选择新目标与重试原目标分开处理。

现有主线 APP 交接可在核心替换前发生，独立分支的常规入口则先执行核心；两者不能未经核对直接拼接。选择顺序必须在写入前证明所经过的中间组合及失败退路安全。无法满足时在修改前报告具体兼容缺口，不能先更新一半再让用户承担未知组合。

协调结果引用核心和 APP 原有执行证据，不复制其事务实现。阶段成功落盘、APP 交接、调用方退出和重新查询之间的中断都要能重读；APP 替换前后的实际写者按既有锁交接，避免同时写入或依赖旧窗口存活。是否需要少量新增字段，按这些场景的最小数据需求决定。

现有操作控制器会对发生修改的失败调用恢复器；接入两项协调时，必须将真实效果与恢复范围对应到失败阶段，不能让通用失败处理把允许保留的成功核心也回退。相关改动以这条实际控制流为边界，不整体重写状态机。

## 4 兼容性与部分完成的判定依据

允许保留成功部分，至少需要三个层面的证据：

1. **支持约定**：交付合同说明适用核心／APP 组合、执行协议及所需运行环境，绑定验收产物；独立核心更新器要求与桌面 APP 要求分别表达。
2. **本机符合**：实际核心、旧／新 APP 和运行环境的身份符合上述约定，资源与恢复来源校验通过；不能只信可改写的版本文本。
3. **结果符合**：对应组合在目标平台的适用验收通过；故障现场的失败项恢复、必要运行检查、用户数据及写者结束也已确认。

APP helper 的执行协议兼容标志不能单独证明新核心配旧 APP 可用；最低版本字段只是约束的一部分，进程启动、健康接口成功也不等于全部兼容。缺少依据时按未知处理，保留证据，不能为满足“一次点击”跳过恢复安全。

组合验收在候选阶段完成并绑定产物；用户更新时核验相应依据、本机身份和必要运行事实，不在用户机器运行测试套件，也不把全量遍历聊天作为每次更新的固定前提。

部分结果的用户文案应直接说明，例如“酒馆已更新；启动器更新失败，原启动器已恢复，可重试启动器”。同时记录实际两项版本和失败原因。该文案仅适用于组合已证明兼容且恢复结束；否则显示具体未确认项及合法动作。全成功、兼容部分完成、已恢复原组合、恢复未确认四种结果必须能区分，但不要求为文案另建状态机。

程序回退仍遵守数据保护。需要回退核心时验证数据格式和恢复路径，不以覆盖维护期间产生的用户内容换取程序版本一致。发布组合若缺少可用恢复路径，应在交付／准备阶段被拦住。

## 5 验收场景与通过条件

以下保留方案确认时的验收标准。用户后续授权的实际执行状态见[实施验收记录](../reports/20261017-update-release-alignment-acceptance.md)，未覆盖项不能自动勾选通过。受控服务或错误注入用于证明分支行为，不能替代目标平台成品流程或公网下载证据。

| 编号 | 场景 | 必须取得的结果 |
| --- | --- | --- |
| A-01 | 仅 APP 变化、仅核心变化、两项变化、均未变化；stable／beta 分开 | 两个入口选中准确组件；APP 单独发布不触发诺拉核心提醒；无更新不创建替换事务、不无故重启 |
| A-02 | 无 APP、APP 关闭／旧版或已移除，核心及更新器完整 | 诺拉仍可检查、完成核心更新，断开后任务继续；缺少真实依赖时报对应缺口，不报告“必须先装 APP” |
| A-03 | 桌面两项都有新版，一次点击 | Windows x64、Mac ARM、Mac Intel 的最终 APP 分别实际执行；自动交接重开、两项验证、终态及下一次正常操作通过，用户无需点击第二次安装 |
| A-04 | 某项成功、另一项失败，剩余组合有兼容证据 | 失败项恢复且组合实际可用，显示部分完成；保留成功项；重试只执行失败项。覆盖实际执行顺序会产生的组合 |
| A-05 | 相同故障但兼容性未知或明确不兼容 | 不按部分完成放行；写入前拒绝不安全计划，或在注入故障后按已准备退路恢复安全组合。恢复无法确认时如实受限，不假报成功 |
| A-06 | 下载失败／损坏包、空间不足、权限错误、核心替换失败、APP 新程序启动失败 | 对应阶段保留原始原因；未修改、成功恢复和未恢复分别判断；用户数据保留，后续重试不被旧失败计数永久锁定 |
| A-07 | 成功阶段刚落盘、APP 交接／重开、恢复期间中断；诺拉调用方被结束 | 重连或重开读取原目标和真实效果，不重复应用成功阶段，不凭失联宣布结束；恢复完成后写者退出，能继续使用或重试 |
| A-08 | 连续点击、诺拉与 GUI 并发提交、重试时出现更新的发布 | 同实例只有一个合法维护写者；另一方查询原结果；固定目标不漂移，明确选择新目标才另行准备 |
| A-09 | 成功、兼容部分完成、失败恢复、再次更新 | 逐次检查聊天、角色、世界、配置、模型凭据、记忆及故事档案的保护清单；读回实际世界／会话并检查必要服务，凭据语义保留且不进入诊断。已成功受管程序可变化，不能把整目录完全相同当更新标准 |
| A-10 | 极狐主源、备用源以及慢源切换 | 在目标网络验证新版本信息、完整文件和适用的断点续传；切源后最终大小与摘要一致。故障注入验证策略，实际完整下载验证用户渠道，两种证据分开 |
| A-11 | 旧发布目录／v2 清单、现有启动器、历史无 APP 入口 | 保留旧协议读取和既有资源引用；2.4.2 独立部署及发行声明支持的桌面基线能接入。旧二进制缺陷与新协议分别记结果，不承诺新源码自动修好尚未升级的旧客户端，也不扩大到所有历史版本 |
| A-12 | 本地候选、最终安装包与待发布目录的身份 | 核对每份组件的版本、来源提交、平台、摘要和对应验收；引用旧产物时保留其原来源证明。GitHub／极狐引用同一封存资源，不用同版本号认证不同字节 |

现有测试优先增补 `test_update_check.py`、`launcher_releases.test.cjs`、`launcher_release_plan.test.cjs`、`launcher_controller.test.cjs`、`launcher_self_update.test.cjs`、`test_launcher_replacement.py`、操作结果／状态及发布消费者测试；独立分支已有任务测试继续复用。为真实交接和失败结果补场景，不默认再做一套测试框架，也不为文档修改运行产品全套测试。

## 6 后续实施顺序和交付边界

1. **先锁定接口差异**：在独立分支确定最小版本信息扩展、兼容组合证明及现有消费者的变化；用旧／新描述和 APP-only 批次样例证明选择一致。保留旧校验路径，避免无理由重写整个发布系统。
2. **再接协调与恢复**：复用既有核心任务、APP helper 和原生锁，补固定两项目标、部分结果、断开续接及失败项重试；原配对修复等既有授权工作保留。
3. **先验执行链路**：跑直接相关的合同、真实更新入口和中断／恢复用例，先消除明确流程失败，再固定候选。失败先定位产品、测试、基础设施或执行方法，不通过反复重打包猜原因。
4. **再验成品与分发**：后续得到构建和测试授权后，以固定候选完成 A-03 的三平台 APP、A-10 的国内完整下载和 A-12 身份核对；Linux 证明无 APP 核心入口。安装包生成不等于这些流程已通过。
5. **最后才考虑上线**：报告已实现、技术检查、实际用户流程、成品和分发各自结果；仅经另行授权才提交／合并／推送、上传或切换正式入口。

本轮三项产品选择均已明确，没有需要用户追加决定的同类问题。仍待技术证明的是协议对齐、具体兼容组合、任务交接及目标环境验收；这些是后续实施门槛，不是本次文档交付的未完成项，也不能沿用旧候选报告宣布新行为已通过。
