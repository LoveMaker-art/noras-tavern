## 1. 用户问题与修复目标

用户在“测试”世界的脚本管理界面操作“数据库本体”时，收到：

```text
Character script persistence could not be confirmed.
```

本次目标是让角色作用域的脚本保存到当前世界绑定的独立卡文件，并能准确确认保存结果。不能把关闭校验、吞掉错误或给某个脚本做特判作为解决方案。

范围：修复酒馆助手共用扩展字段保存路径、补充保存结果校验的目标保护、恢复此次误写脚本。保留其他世界、聊天、世界书、预设、图片、模型配置和既有运行权限。

## 2. 根因与直接证据

### 2.1 显示名称被错误地当作文件身份

诺拉为世界创建独立运行卡。卡的显示名称与实际文件名可以不同，两个世界也可以使用相同显示名称。

酒馆助手发布产物中的共用保存函数 `oA` 原来使用：

```js
avatar_url: i.name + '.png'
```

它没有使用卡实际携带的 `avatar` 文件名。这个假设与诺拉独立副本的存储方式不兼容。

本机检查结果：

| 对象 | 文件 | 修复前脚本情况 |
| --- | --- | --- |
| 当前世界独立卡 | `Nora_Blank_World--nora-internal--nora-4a5f85fe9d2a000f5b8d56c0.png` | 没有“数据库本体” |
| 按显示名称误写的文件 | `Nora 空白世界.png` | 存在“数据库本体” |

这证明保存目标错误，不只是界面状态显示错误。相同名字的其他卡也存在受影响的可能，但本次没有据此推断或修改所有历史数据。

### 2.2 报错来自保存后校验，不是脚本执行异常

原控制层流程：

1. 修改 Helper 的实时脚本树。
2. 调用 Helper 保存。
3. 通过 `/api/characters/get` 回读当前世界真实卡文件。
4. 对比持久化脚本树和实时脚本树的 SHA-256。
5. 不一致时抛出上述错误。

因此，此次校验确实发现了写错文件造成的不一致。它不能替保存函数选择正确目标，也不能被当作此次故障的根因。

资源发布哈希与此校验是两件事：前者用于缓存版本定位，后者用于比较保存内容。两者都不能单独保证一次写入选中了正确文件。

### 2.3 同一路径的关联风险

旧实现还存在以下行为：

- 请求成功前已修改角色内存对象。
- HTTP 保存失败只输出日志，不向调用方抛出错误。
- 内存内容与待写内容一致时提前返回，失败后的重试可能因此跳过实际写入。
- 异步加载角色期间没有固定真实文件身份。
- 多次写入完整扩展字段时缺少同一目标的串行约束。

这些问题与此次保存链路直接相关，因此一并处理；没有扩展到预设、世界书或其他存储系统的重构。

## 3. 实现变更

### 3.1 共用保存函数

在 `app/native-extensions/JS-Slash-Runner/nora-control-adapter.js` 中增加可独立测试的 `persistCharacterExtension`。发布产物中的原 `oA` 入口统一委托给它。

这不是只给诺拉按钮增加一条旁路：经过该入口的 Helper store 保存和扩展字段 API 使用同一实现。

新流程：

1. 捕获目标卡 `avatar` 和当前角色 ID；缺失真实文件名立即拒绝，不猜文件名。
2. 对待写值制作快照，按目标 `avatar` 串行处理写入。
3. 加载完整角色前后检查绑定；若目标文件或当前角色发生变化，拒绝继续。
4. 用角色副本构建请求，`avatar_url` 始终使用捕获的真实文件名。
5. HTTP 非成功状态抛出错误；不把失败结果提交到角色内存。
6. HTTP 成功后再次检查目标，再更新该扩展字段及对应 `json_data`。

没有保留“仅凭内存相等就跳过请求”的短路，确保失败重试，以及导出时临时写入后恢复原内容，仍会执行实际写入。代价是某些相同内容的保存可能多一次请求；本次优先保证持久化正确性。

同一文件的队列用于避免这一共用入口内部并发写入相互覆盖，不是跨浏览器、跨进程的全局事务锁，也不覆盖绕过该入口的其他写入者。

### 3.2 控制层保存校验

修改 `app/engine/sillytavern/public/scripts/nora-controls/runtime.js` 的 `saveHelper`：

- 保存前捕获世界 ID、会话 ID、角色 ID、真实文件名和待保存脚本树。
- 在 flush、设置保存、回读之后检查是否仍处于原目标。
- 回读固定的目标文件，与捕获的脚本树比较，不再重新选取可能已经变化的当前目标。
- 保留 `NORA_CONTROL_SAVE_UNCONFIRMED`，目标切换使用 `NORA_CONTROL_SCOPE_CHANGED`。

如果目标在请求已经发出后切换，已发出的请求仍可能完成对原文件的写入；实现保证不转写新目标、不把成功状态应用到新世界，但不宣称可以撤销已完成的服务器写入。

### 3.3 文件清单

| 文件 | 改动 |
| --- | --- |
| `app/native-extensions/JS-Slash-Runner/nora-control-adapter.js` | 共用持久化实现、目标检查、同目标写入队列、错误传播 |
| `app/native-extensions/JS-Slash-Runner/dist/index.js` | 原入口委托到共用实现，保留其调用接口 |
| `app/engine/sillytavern/public/scripts/nora-controls/runtime.js` | 捕获目标和脚本快照，固定回读与目标校验 |
| `app/engine/sillytavern/tests/nora-helper-character-persistence.test.mjs` | 实际发布函数及控制链路的回归测试 |

发布产物的接入位于已提交到仓库的 vendor bundle。未来替换上游 bundle 时必须保留接入并运行回归测试；本次未重建上游源项目。

## 6. 剩余验收与限制

尚需用户刷新启动器中的酒馆，在“测试”世界完成：

1. 打开脚本管理，确认“数据库本体”仍在。
2. 按本人意愿授权或切换状态，确认保存不再报错。
3. 刷新后确认状态保留。

本次没有打开浏览器，没有验证第三方脚本执行后的业务功能，没有自动扫描或迁移所有历史误写数据，也没有为所有存储入口提供跨进程事务保障。

## 7. 回退原则

如需回退，应先停止对应酒馆进程，按备份中的相对路径恢复本次受影响代码和编译产物，再启动并检查健康与资源版本。

卡数据不能无条件恢复旧备份：若用户在修复后继续编辑或游玩，必须先比较当前文件，仅撤回本次恢复的字段，避免覆盖新数据。PID 记录也不能直接套用旧备份，应根据重启后的真实进程重新确认。

## 8. 结论

根因是独立副本文件身份与 Helper 旧保存路径不一致。此次修复统一了共用保存入口的真实文件定位、失败传播和内存提交时机，并强化控制层的目标固定与回读校验。

源码及针对性测试已完成，本机部署和数据恢复已有正向证据；完整用户交互效果仍待刷新后的实际点击验收。
