# 酒馆 2.5.0 与 GitHub 版本差异报告

2026-10-14，北京时间。目标版本为酒馆 **2.5.0**、启动器 **2.2.0**，整理在本地 `main`。报告初始快照对应版本整理、冗余清理和技术验证。此后用户已授权推送与测试包构建，当前构建验收仍未正式发布。新版本的三平台最终安装包及旧正式版本升级仍需验收。

## 版本配置与兼容边界

`app/.tavern-release-version` 为酒馆 2.5.0；`launcher/desktop/package.json`、`package-lock.json` 顶层与根包版本为 2.2.0。依赖列表及所有第三方锁定版本保持原字节对应的数据值。SillyTavern 上游的自身版本不作为酒馆发布号改写。

原未发布 `docs/releases/v2.4.6.md` 整理为 [v2.5.0 版本说明](../releases/v2.5.0.md)。正式历史版本说明、测试里的历史版本号、脱敏故障样本及旧安装包证据保留。

当前构建工具会把生成清单的最低维护启动器版本取为随包启动器版本，因此未来 2.5.0 的清单将要求 2.2.0。旧用户能否自动完成“先升级启动器，再更新系统”的交接，必须用旧正式安装包验证；这次修改版本号没有建立该兼容结论。不能要求用户删除聊天和配置来绕过升级验收。

## 冗余清理与保留范围

本轮通过 Python AST、99 个现行 JavaScript 工具及运行文件的静态检查，再核对实际引用，清理以下内容：

| 删除或调整 | 理由 |
| --- | --- |
| 安装 bootstrap 的 `subprocess` 导入 | 该入口没有调用或外部消费者 |
| 更新 bootstrap 的 `subprocess` 导入 | 当前执行经维护 CLI；旧测试仍拦截已退出的 subprocess 路径，改为拦截当前 `ensure_operation` 入口，保留“只查询计划，不维护”的断言 |
| updater 的 `default_hermes_home`、`default_install_root` 导入 | 本文件只消费 `resolve_update_target` 等现用接口；原定义和现用消费者保留 |
| 启动器替换 helper 的 `errno`、发布 provider 的 `crypto` 导入 | 无引用的导入，现有错误和摘要实现不依赖它们 |
| UI 的 `lastStatusError` 状态及赋值 | 只有写入，没有读取；真实错误继续抛出并由现有界面与日志处理，`statusUnknown` 仍保留；`lastStatusAt` 保留成功查询时刻，失败查询不刷新它 |

最终删除 6 个未使用导入和 1 个废弃状态变量，没有移除控件、更新协议、旧恢复能力或有效验收。静态工具提示的 `planId`、`registeredAt`、消息 `type`、请求 `tag` 和历史 `startState` 排除绑定，是对象拆分的组成部分，不能按“变量未读取”误删其余对象的语义。

此前相对正式版已经清理备用 pnpm 锁与配置、两个无正式消费者的旧 UI 设计稿、独立旧索引脚本，以及无消费函数。历史恢复 worker、候选隔离协议、旧备份读取、平台卸载脚本、历史版本 fixture 和故障证据仍有职责。详见 [此前源码清理记录](launcher-source-cleanup-20261013.md) 与 [测试清理记录](launcher-test-cleanup.md)。

工作区原有 `docs/README.md` 修改和 `docs/launcher-handoff/` 未跟踪内容保留，不加入本次提交。

构建验收补正：初次整理把 `lastStatusAt` 误判为无消费状态，但 `launcher_guidance_flow` 仍验证它记录成功查询、在失败后保留的时刻，已恢复该记录。Windows 的重试断电注入遗漏了扩展路径匹配，改为使用既有 `same_filesystem_path`；断电和未知文件保护断言保持不变。原 CI 失败、实际测试机反例及修正结果分别保留。

## 验收结果和发布阻断

本轮技术验证均正常退出：

- 版本、源码布局、发布计划、版本说明与渠道 provider 的 62 项合同测试通过，无跳过。
- 安装 bootstrap、增量更新和启动器替换的 Python 回归运行 64 项，63 项通过；1 项需要真实启动器压缩包的可选验收因本轮未提供新包而跳过，不计作通过。
- 控制器的错误页面、后台状态刷新及安装—模型—配对—启动—停止交互回归 3 项通过。
- 版本配置一致、第三方依赖锁定值未变、修改文件语法及 `git diff --check` 均通过。

原始日志和源码绑定见 [本轮技术验收](../../artifacts/version-2.5.0-preparation-20261014/verification.json)。本轮没有对生产服务、渠道文件或测试机安装进行替换。

已有证据包括 Windows 默认路径限制下真实源码恢复，以及 6 种窗口尺寸的 UI 技术验收。它们对应各自当时的源码与执行环境，不代表新的 2.5.0 三个平台安装包均验收完成。完整对账见 [产品收敛记录](launcher-product-convergence.md)。

正式发布仍有三项阻断：

1. **最终三平台包验收**：最近一次 CI 的 ARM 与 Intel 构建成功，Windows 在修复前的恢复测试失败；最终 Windows 安装器缺失，Intel 原始制品尚未完整接收。原 ARM 包只含 `1cb9f1b` 源码，不含后续路径、焦点、对齐及本轮版本修改，不能当作新版本的最终包。
2. **历史版本真实升级**：最近正式版到新包的运行／停止两种状态、启动器自更新交接、用户数据保护、KEEP 后重装和 ALL 范围仍需绑定最终字节证明。源码模拟通过不能代替这些用户流程。
3. **国内公网完整下载**：代码已接入主源、备用源、慢源判断与续传；历史间歇性超时的责任层没有全部确定，新的最终资产也未做目标 Windows 环境的完整公网消费验收。版本查询或小文件成功不能证明大包更新可靠。

本次结论：本地版本标记及源码整理可以完成；正式发布放行条件尚未满足。
