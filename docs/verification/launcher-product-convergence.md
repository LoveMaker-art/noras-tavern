诊断继续使用现有 `launcher` action、事件与日志协议，没有新增接收端 schema。不同 actor 使用不同生产者身份，避免重置或并发写入 GUI 的 sequence；不额外制造 `launcher_first_seen`。原始详细日志仍受显式授权控制。

持久队列使用原生 writer lease，发送单飞，abort 后等待所有保存路径结束才释放。只有全部预期事件被精确 ACK、无丢弃或拒绝、所需日志已确认，才标记接收；HTTP 200 本身不能代表成功。撤销详细诊断时，基础事件接收与被抑制的详细证据分开记录。容量检查和创建持根目录原生锁；旧已接收证据保留至少一天，旧未接收证据保留七天，回收已知诊断文件时保留稳定锁文件。

诊断是尽力而为：操作系统拒绝写入、目录被链接重定向、存储与待删除安装根重叠、队列损坏或容量耗尽时，仍保留原操作失败及可用的本机结果。不承诺每条故障均能上传，不把未知原因伪造为网络或服务故障。

## 设计合同的定向分析结果（2026-10-12）

本节保留实施前的实现分析和隔离探针，不代表当前代码仍有同样缺口。原先“分层使用规则尚未核清”的判断已进一步收敛：轻量状态与严格验收分层本身有明确代码、测试和用途；实际需要加固的是验收记录输入校验，以及数据迁移和完整备份的准入。具体实施与验证见末尾收尾记录。

### 状态检查：保留分层，加固记录

`installation_state` 有意用于轮询和正常启动；现有用例允许用户编辑技能、配置、关闭 cron 后仍使用原安装。正常启动另经 native lifecycle 核入口、配置、进程归属和实际健康。安装、更新验收、提交后继续、设置完成等路径有 `inspect`／运行验证；CLI 维护结果还须具有执行器返回的验收标记并匹配固定版本、commit、根和端口。当前没有证据要求每次查询全树 hash，也不能把缺少 `proofLevel` 字段直接认定为缺陷。

隔离临时完整 fixture 调用实际 `nora_system` 得到：

| 场景 | 轻量 ready | 严格 ready | 判断 |
| --- | --- | --- | --- |
| 合法安装记录及文件 | true | true | 正常基线 |
| 用户修改技能 | true | false | 两层预期用途不同，不应据此禁止日常使用 |
| MCP 入口缺失 | true | false | 轻量历史状态不能解释成当前完整性已验证 |
| 当前 receipt commit 与系统验收记录不一致 | true | false | 轻量解析应拒绝相互矛盾的历史记录，不需要全树 hash |
| 四项 proof 都改成字符串 `not-confirmed` | true | true | 确定的类型校验缺口；Python truthiness 把非空字符串当成已确认 |

建议最小代码收尾：轻量与严格检查共用历史验收记录解析，proof 必须为字面布尔 true；校验支持的 schema、版本、commit 及记录间一致性、布尔字段类型。保留明确支持的旧 schema，不静默改写损坏记录，不触碰用户技能／配置／cron。严格操作仍独立核实际文件、服务及固定目标，轻量结果不能制造本次更新成功。

### 用户数据：当前保护合理，旧 ADR 应修订

后续设计记录 `docs/architecture/UPDATER-EXISTING-INSTANCE-20260910.md:38` 已明确 native 更新停服后快照、只读 WorldStore 验证、启动后校验及失败回滚，早于本次整顿。ADR0013 第 32 行的“用户数据不解析／复制／比较”已与后续决定不一致。因此应将普通程序更新的承诺表述为“不主动转换剧情内容，但备份并核对数据保护”，不能为迎合旧 ADR 删除保护。

| 路径 | 实际数据职责 | 处理建议 |
| --- | --- | --- |
| 普通 launcher-managed 更新，包括 ops／MCP／skills | `bool(managed)` 使 `runtime_changed` 为 true；停服、全量 state 快照、只读身份及字节核对、重启后验收 | 保留当前系统事务；明确停服、空间及时间成本 |
| 非 managed 的纯组件更新 | 无 app 变化或迁移时可保持 Tavern 运行，不做 state 快照 | 不把该路径的成本承诺推广到正式 launcher-managed 路径 |
| 受损安装修复 | 原状态备份、候选只读解析、严格数据清单／身份／配置保留 | 保留；程序修复不授权转换用户数据 |
| Python→native 迁移／归档 | 停服前先复制预备 state，之后才停服并切换 | 必须把权威复制与转换绑定停服后的状态 |
| 失败回滚 | 按事务和离线证明恢复程序／数据／配置，保留 failed-new | 保留，禁止以减少残留为由删恢复现场 |

`verify-worlds.mjs` 注入只读文件接口；坏 World 会使验收失败，而不是修改备份。运行中的正常 loader 可能隔离不兼容 World，因此启动副作用是完整状态备份的保护依据。

需要代码收尾的两点：

1. **旧 Python 迁移的数据时点。** `update.py:1093` 生成预备副本，`:1186` 才停服，随后切换预备 state。隔离模块探针使用真实 `fallback_python_state`、合法备份及实际 `Journal.apply_state`：副本准备后新增消息，切换后的活动目录缺该消息，旧备份仍有该消息，Journal 完整验证仍通过。此证明模块反例与控制流风险，不是整个旧客户端／GUI 故障复现，也不是用户永久丢数据证据。最小修正是停服后形成权威快照再迁移／归档；失败保留旧数据并恢复原服务。
2. **完整备份空间准入。** 现有路径没有按实际数据、候选、备份及恢复临时区所需空间做停服前容量检查；磁盘不足可能直到停服后的复制才失败。应在停服前检查目标磁盘、停服后重新核对，并保留实际 ENOSPC 处理。大小统计和检查通过不能保证其他程序之后不占用空间。

普通更新的完整快照包含全树摘要、完整复制、备份摘要，并叠加剧情资源与 World 校验，成本随数据规模增长。尚未测量真实大数据目录，不把它归为历史五六小时打包或公网下载超时原因。免停服纯组件路径、增量备份等属于另行证明数据副作用和兼容性后可做的优化，不是本轮必须采用的新架构。
