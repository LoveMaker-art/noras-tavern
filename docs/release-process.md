# Nora 发布流程

更新范围和发布策略以唯一[产品设计基线](product-baseline.md)的 PB-06、PB-09 为准；本文说明现有发布工具与协议的执行方式。核心／启动器版本信息分离、一次发起两项更新及兼容部分完成的修订已随 v2.5.3／启动器 2.2.3 正式发行；本轮成品与分发证据见[发行记录](reports/20261019-v2.5.3-release-preparation.md)。此前指定流程及其限制仍分别见[合并审查](reports/20261018-main-updater-merge-review.md)、[仅启动器发布验收](reports/20261018-app-only-publication-acceptance.md)和[查询预算验收](reports/20261018-update-query-budget-acceptance.md)，不因发布而扩大其验收范围。

设计范围及验收要求见[技术实施方案](design/update-release-alignment.md)。构建、迁移、推送和发布分别取得授权，不以文档或源码完成代替正式渠道验证。

本文规定变更判断、构建验收、制品封存、分发准备、正式切换及失败恢复的执行边界。工作流实施和本地合同验证不等于已在 GitHub 执行，也不等于正式发布成功。

## 1. 先确定必须改变的交付内容

对最近正式稳定版本与拟交付的固定提交生成计划：

```sh
node tooling/release/release-plan.mjs --base v2.4.3 --head HEAD --output /tmp/nora-release-plan.json
```

计划绑定前后提交和源码摘要，并逐项记录改变的模块、启动器、平台环境及判断理由。输出文件必须不存在。首次没有任何历史发布时显式使用 `--base EMPTY`，不能用它绕过一个已有的兼容性基线。

| 计划 | 执行范围 |
| --- | --- |
| `verification-only` | 相关工具、测试或文档验证；无需产品重构建。已有封存包仍可以独立发布。 |
| `components` | 构建变化组件，验收旧启动器、执行协议与环境兼容性，封存组件交付。 |
| `launcher` | 构建受影响启动器；仅在完整输入及实际资产证明未变时复用环境。 |
| `full` | 构建计划指明的变化环境、依赖、启动器及组件。 |
| `review-required` | 未知输入先独立审查；禁止默认复用。明确批准后采用保守完整构建，并保留审查后的计划。 |

源码相同只能证明源码输入相同。外部下载、Node/Python 版本与 ABI、平台架构、原生依赖、外部固定提交及构建来源也必须核验；计划不能代替资产的来源、内容和 SHA256 验收。

## 2. 构建与验收不发布

`build-integrated-launcher.yml` 负责原生构建和验收。独立 `preflight` 先生成计划、检查入口和工具合同，再准入昂贵的原生任务。计划默认为最近正式稳定标签，可显式指定基线。未知输入需要 `approve_unknown_inputs=true`，该选择不能豁免原生或数据保护验收。

三平台任务使用 `fail-fast: false`。平台安装、进程归属、升级恢复、完整 APP 模块闭包、真实运行环境和用户数据保护检查仍在对应平台执行。Mac 检查不能替代 Windows 原生检查；包内容检查不能替代用户可见工作流验证。

冷构建 Hermes 必须从 `tooling/runtime/hermes-bootstrap.lock.json` 读取固定官方提交、两个原始安装脚本 SHA256、Hermes 版本与 Python ABI。`prepare-hermes-bootstrap.mjs` 下载该提交的脚本并校验后才写入新临时目录；禁止实时使用浮动安装器或退回 latest。三平台安装传入同一固定提交及强制固定参数，封装前再核验真实 Git HEAD、来源、已跟踪文件、原安装标记、venv 的 Python 版本和所导入源码的归属。更新这个锁属于环境输入变化，必须重新原生验收，不能直接沿用旧环境的版本号作为证明。

新增网络门禁先在准备运行环境前启动锁定版本的原生 Electron，使用隔离 HTTPS/代理 fixture 经过真实 Chromium 网络栈。完整 APP 生成后再次从原始 `app.asar` 加载网络模块，在同一原生运行时的隔离副本中核验重定向、备用源、流式读取、取消、截止和条件缓存。副本不更改原 APP；报告绑定原 executable、ASAR 和模块摘要。此检查证明网络适配器行为，不表示生产 GUI 主入口或真实公网质量已经通过。缺少 `nora-electron-network-acceptance.json` 或证据身份不符，完整交付不能发布。

已有正式旧版的版本迁移，须另有固定旧版基线及服务运行、已停止两种状态的真实升级证明。`acceptance_baseline_tag` 默认取完整 GitHub 已发布稳定历史中的最近旧版，独立于 `runtime_source_run` 和 `launcher_baseline_tag`；正式构建入口拒绝更古老的基线，额外旧版诊断不能替代最近旧版迁移证明。未知构建输入禁止复用当前运行环境，但仍可只读取得旧包进行历史验收。原生步骤下载旧版完整系统闭包并逐件验 SHA256、大小和源码身份，不把旧环境注入新包构建。

首次例外仅在独立 GitHub API 历史查询确无稳定发布时接受 `EMPTY`；保留事实摘要和选择记录，不能凭手填初发标记绕过历史验收。独立发布入口再次读取完整正式历史、排除当前目标 tag，将原生报告的旧版提交和清单摘要绑定实际正式资产；无基线报告或缺任一服务状态即阻断。恢复部分切换时即使目标已为 latest，仍使用原来的严格旧版基线。

`publish-component-update.yml` 的名称为“Build and accept system update components”，历史文件名保留以维护来源身份。它只接受兼容组件计划，先执行相关合同及数据保护门禁，再构建、验收和上传 `nora-component-delivery`、`nora-component-acceptance`、`nora-release-plan`。

构建失败时先根据失败阶段定位产品、测试、基础设施或执行方式问题。保留日志和已构建的诊断包；源码未变时只重跑失败原生任务：

```sh
gh run rerun "$NORA_BUILD_RUN" --failed
```

旧 Windows 成品的检查使用 `target=win32-package-check` 与 `package_source_run` 独立入口。检查工具改动不得改变封存产品源码。诊断包不具备正式发布资格。

## 3. 固定已验收制品身份

双更新兼容声明必须随固定源码提供。构建默认读取 `tooling/release/compatibility/v<核心版本>.json`，也可显式选择同目录内已提交的审阅文件；空白工作流输入不再表示省略声明。声明必须包含实际核心、目标 APP、经过验证的过渡组合和准确协议。更新版本时须重新核对，不按版本号自动推断兼容。正式构建要求文件与产品提交一致；候选允许未提交文件，但不取得正式发行资格。遗漏或无效声明在准备构建前阻断，最终分发检查再使用成品中的组合判断核验目标兼容。原生升级、恢复及数据保护证据仍须独立取得。

成功构建提供四个完整交付 artifact、三个平台验收 artifact，以及新流程的变更计划。Windows 独立构建可以在同产品提交最终组装时复用，来源必须经过原生步骤、ZIP/API 摘要、资产清单及真实 APP 证据核验。

独立发布入口 `publish-accepted-release.yml` 在当前发布工具提交运行，使用 `release_tag` 解析产品提交。`source_run` 必须来自本仓库明确触发、完成且成功的规定构建工作流；其产品提交必须等于目标标签。来源报告、API artifact ID、大小和 SHA256 必须一致，ZIP 摘要错误在解压前阻断。目录链接、特殊文件、越界路径、重复成员与重复交付文件名均拒绝。

“产品提交”与“发布工具提交”分别记录。发布工具修正不要求重新构建已经验收的旧标签产品；产品输入实际变化则生成新制品和新身份。标签和已公布的不可变文件不得移动或覆盖。

`final-consumer.mjs` 在每次 `seal/prepare/promote/all` 入口读取最终三个轻量更新 ZIP 中真正封装的选择器及其 semver 依赖。它只向该选择器提供封存目录和清单字节，分别验证安装、更新六个计划；安装必须消费系统清单指定的平台实体，更新必须消费根清单。ZIP 内模块摘要必须匹配平台 payload 的 artifacts，才能与原生 APP 验收证据相连接。缺文件、错误布局、旧客户端不兼容或任何内容身份不符，在两个上传器开始之前阻断。该步骤设有 60 秒进程截止。

这个最终清单消费检查不执行其他平台二进制，也不替代安装、运行/停止两种历史升级、恢复和用户数据保留验收。原生业务流程仍使用隔离本地 payload；真实网络与最终分发清单分别检查，并用字节身份连接。仍须在发行候选的目标机器补充完整用户路径验收，不能称已证明所有公网和 GUI 场景。

## 4. 明确选择发布阶段

工作流与 CLI 默认 `seal`，不会上传或切换正式通道：

```sh
node tooling/release/publish-release.mjs "$NORA_ACCEPTED_ASSETS" "$NORA_RELEASE_TAG" "$NORA_PRODUCT_SHA" full --stage seal --state-dir "$NORA_PUBLICATION_STATE" --asset-mode legacy
```

| 阶段 | 行为与成功条件 |
| --- | --- |
| `seal` | 本地重新核验封存资产，固定发布计划、说明、时间戳、目录清单及 `planId`。 |
| `prepare` | 按封存计划的 `destinations` 检查、补传并核验不可变资源及 GitHub 草稿；所选渠道完整后标记准备完成，不切正式通道。 |
| `promote` | 只接受原计划中所选渠道的已准备状态；重新检查远端完整性、防降级条件，然后切换并逐站核验。 |
| `all` | 显式组合准备与正式切换，仍执行相同门禁。 |

首先保存 `nora-publication-state-before-transfer`，然后才准备私有凭据和开始远端写入。常规失败或取消时通过 `always()` 保存 `nora-publication-state`。状态目录仅包含公开资产的发布元数据、固定说明、来源证明和检查点；私钥、主机密钥文件及私有配置放在独立临时目录，并始终清理。

所有版本共用正式通道锁。跨站切换不能构成原子事务，须逐站记录结果；后续站点失败必须报告渠道差异并恢复剩余切换，只有计划内全部渠道核验成功才记为 `published`。国内主源为极狐时，默认选择 GitHub 与极狐；本轮显式使用 `destinations=github-jihulab`，SourceForge 不作为放行条件。

## 5. 失败恢复沿用原计划

发布失败不重打包，也不修改资产清单。已经封存计划并保存状态 artifact 时，启动新发布工作流，保留 `release_tag`、`source_run`、`delivery_mode`、`asset_mode`，填写此前的 `state_source_run`；原目录时间戳和计划身份不得改变。

若失败发生在封存之前且没有任何状态 artifact，尚不存在可恢复计划，禁止将该失败 run 填入 `state_source_run`。定位并修复实际失败后，使用同一已验收产品 tag、来源 run 和资产协议、留空 `state_source_run` 重新执行 `prepare`；这不会重新构建产品。

来源运行可为已结束的成功、失败或取消状态。优先恢复最终检查点；强制终止而没有最终 artifact 时恢复传输前固定计划。每个状态 artifact 仍须通过本仓库、本发布工作流、API 摘要和安全解压检查。

恢复时核对原始产品标签、产品提交、来源 run、资产协议、已验收 artifact ID 与摘要；固定计划、目录清单和索引的哈希不得改变。可变进度检查点不要求保持最初哈希。`--expected-plan-id` 从外部保留的 workflow 证明读取，再交给 CLI 作为独立锚点。

```sh
gh workflow run publish-accepted-release.yml --ref main \
  -f release_tag="$NORA_RELEASE_TAG" -f source_run="$NORA_BUILD_RUN" \
  -f delivery_mode=full -f asset_mode=legacy -f destinations=github-jihulab -f stage=prepare \
  -f state_source_run="$NORA_PREVIOUS_PUBLISH_RUN"
```

上述命令属于远端写入示例，需要相应授权；准备授权不包含正式发布。不要对失败发布任务直接使用“rerun”：新 runner 必须显式恢复此前固定计划。所选渠道准备完毕后，取得正式发布授权，才可用该准备 run 的状态执行 `stage=promote`。

每件对象记录当前源、阶段、大小、摘要与完成时间；下载和子进程具有截止及心跳。SourceForge 已有对象若有受信检查点记录的完整哈希收据，恢复时检查 HEAD 存在和大小，避免重复读取 GB 级内容；这依赖不可变对象未被外部覆盖，HEAD 本身不证明当前 SHA256。没有收据的旧部分对象须完整读取并验 SHA256 一次。冲突对象拒绝覆盖；失败阶段及有限诊断写入检查点，禁止将私有环境或配置写入诊断。首次完整传输仍受带宽影响，不能承诺固定分钟数。

## 6. 旧协议与跨版本资产复用

`legacy` 为默认模式。旧客户端按当前 tag 验证所有资产 URL；因此旧协议组件发布可以复用构建环境和旧完整安装器，但部分未变化的大文件仍须在当前 tag 分发。这是现有协议的兼容性约束。

`shared` 使用当前 tag 的 `release-assets.json` 固定索引，通过明确旧稳定发布标签、大小和 SHA256 引用未变资产。新的 shared 计划必须填写 `reuse_tag`；CLI 核验已正式发布的稳定基线及其产品提交。legacy 和恢复原计划时均禁止另填基线，避免改变封存身份。

只有大小和完整 SHA256 完全相同的物理字节才复用。本流程未实现可重现构建，相同源码重新打 tar 包不保证摘要相同。完整 shared 交付仍将控制清单、安装脚本、三个安装器、整包 ZIP 和轻量 ZIP 保留在当前 tag。组件交付继续用 `component-release.json` 的 `installerTag` 指向原完整安装器，不要求组件版本重新分发三个完整安装器。

shared 需要支持索引协议的启动器，并强制最低版本高于 `2.1.1`，系统最低启动器版本也不得低于索引门槛。必须先用 legacy 完整发布新协议客户端，随后才启用 shared 组件发布。旧 `2.1.1` 客户端从 shared 版本冷安装会因环境资产不在当前 tag 而失败；既有安装的热升级路径也必须在原生环境单独验收，不能由新客户端测试推断。启用 shared 前须验证旧客户端热升级与新客户端三平台冷安装。

`v2.4.4 / 2.1.1` 使用 legacy；其封存清单缺少新协议需要的部分资产大小证明，禁止改写旧制品以绕过门禁。重复 shared 发布使用 `asset-catalogue.mjs` 读取当前索引、各物理来源 tag 和原始源码清单，验证大小、摘要与独立标签提交，不能仅根据上一版本的资产名称复用。本地协议验证不能称为已部署或证明线上旧客户端迁移完成。

旧 `2.1.1` 已封存操作热升级后派生 shared 来源时，固定 tag 索引请求或旧 tag 下载经既有源切换仍失败，现有重试次数和恢复门禁继续生效；不能凭派生地址增加可信重试凭据或清零次数。须保存操作日志和 APP 备份，先通过“恢复旧启动器”处理未完成交接并核验状态，再检查固定 tag 和索引身份。可使用现有 legacy 模式的兼容发行桥接；未来下载正式新版安装器覆盖前同样先满足恢复门禁。禁止删除操作记录、伪造重试证明或直接移除备份。新客户端原生封存的 shared 计划包含原始索引摘要与引用，沿用现有 SHA256/大小条件重试；旧客户端这项失败路径必须列入未来原生上线验收。

### 稳定版核心锚点与 APP-only 发现

普通核心／组合发布继续使用 `channels/stable.json`，并成为 GitHub `latest`；新生成的稳定发布计划同时封存 `channels/launcher-stable.json`（同一 release 的单元素数组），让新版桌面在 GitHub 不可达时也能完成国内源检查。两个目录的字节、顺序及摘要都属于原计划，极狐以同一次仓库提交和逐文件 CAS 核验切换。历史已封存的单目录计划仍按原合同续传，不临时追加未封存对象。跨供应商切换分别核验，不承诺跨服务原子提交；SourceForge 两目录失败时按同一封存计划续传并逐项回读。

首次启用组件批次前，先发布一个旧 APP 可识别的普通组合版本：tag 与真实核心版本一致，包含新版 APP、核心查询脚本与独立更新技能。不通过伪造核心升版或改写已发布旧包接入。

后续 APP-only 从经认证的 `coreRelease` 派生发布计划 `coreAnchor:{tag,commit}`，只推进同源固定用途 `channels/launcher-stable.json`（标准 release JSON 的单元素数组），GitHub 发布时明确 `latest=false`。原核心稳定指针及历史不可变目录不改。发布前及切换时核验核心稳定锚点仍与该来源一致；变更或无法核验时拒绝推进。字段、指针和字节纳入原封存计划，续传不能换成另一个锚点。

新版桌面在原“检查更新”中同时读核心锚点与启动器列表。国内源提供完整单元素列表；GitHub 备用读取标准正式 release 列表，最多五页、每页一百条。APP-only 必须绑定当前核心锚点的版本、提交和原平台清单摘要／大小，不能以旧核心的 APP 批次覆盖较新核心；列表不完整或读取失败时，保留已核验的核心更新能力，并明确 APP 检查未完成。诺拉、独立更新入口及旧 APP 不读取启动器列表，因此跳过过渡版的旧用户仍能从原按钮找到普通接入版本。

本轮仅为稳定渠道实现该分流；APP-only Beta 明确拒绝生成发布计划，普通 Beta 沿用原流程。上述源码实现不代表正式渠道已切换；三平台产物、原生接入与发布仍按各自门禁验收。

## 7. 上线验收与证据

正式发布后检查两站目录和通道、GitHub 非草稿状态、版本与 SHA256、三个安装器下载入口、官网/API 映射、缓存及来源策略，以及真实目标机器的生产更新检查。单个 CI 绿色或 HTTP 200 不能代替这些条件。

用户数据保护、实际安装升级、正常关闭重开和必要故障恢复在目标环境记录证据；生产替换前保存受影响运行文件及数据备份，替换后核验健康。发布辅助进程、临时包及远程控制任务按精确归属清理，保留用户要求留存的正式安装包、备份和访问配置。

每次交付记录源码分析、实现、技术验证、用户工作流验证和正式部署分别达到的层级。保存变更计划、原始构建及验收来源、资产清单、固定发布计划、阶段日志、失败检查点和公开验收结果。GitHub artifact 当前保留期有限；需长期保留的已验收包和证明另外归档，不依赖临时 runner。

## 8. 夸克网盘备用下载渠道

每次正式发布还须将已验收的 Windows 安装器、Mac Apple 芯片 DMG、Mac Intel DMG、版本说明及 `SHA256SUMS.txt` 上传到项目方夸克账号。目录按 `诺拉酒馆/正式版本/<release_tag>/` 保存，已分享版本不得覆盖；同名文件发生冲突先核对内容，不能静默替换。

上传必须使用此次封存交付的原始安装包，逐件核对发布清单中的文件名、大小和 SHA256，不能为了网盘另行重打包。上传后检查所有文件均完成、数量及显示大小一致，创建该版本目录的分享链接，并核验分享页包含正确版本和三个平台文件。记录分享链接、有效期、提取码（若有）、来源 run、产品提交和文件摘要，随正式交付结果提供。登录或容量不足时明确报告夸克渠道尚未完成；GitHub/SourceForge 发布成功不能代替网盘交付成功。

夸克用于用户手动下载完整安装包，不纳入启动器的自动更新源、来源白名单或资产协议。首次使用账号需项目方完成登录；没有已验证的官方上传接口时，通过获授权的网页上传，不能将浏览器登录 Cookie 或私有凭据提交仓库、写入 CI 或分享文件。此交付步骤不承诺无需登录的自动化上传。
