# 更新器与启动器的职责合同

状态：2026-10-16 用户已确认采用独立更新器方案，保留原按钮和操作步骤，只做必要收敛。撤回两项设计后的 f622 冻结候选已补验：Mac 实际技能与按钮更新、下载失败同任务重试、程序失败自动恢复与再更新；Windows 实际失败恢复、结束调用方后继续与重启；Linux 原 2.4.2 bootstrap 调用方退出后继续。受检用户数据与模型配置保留，指定范围无剩余流程阻断。当前分支为 `codex/fix-pairing-standalone-update`，未合并、提交、推送或发布；具体证据等级和未验部分见[验收记录](reports/20261016-shared-independent-updater-acceptance.md)。

## 用户结果

诺拉通过更新器更新诺拉与酒馆。更新器能独立执行，不以桌面启动器是否安装、运行、在线或版本较新作为普通系统内容更新的前提。Windows、macOS、Linux 遵循同一产品规则；各平台的进程和文件操作适配留在实现层。

启动器负责启动，并保留现有配置、查看状态、更新按钮等界面。更新按钮调用同一更新器；此次需求不授权删除这些界面。启动器本体替换与系统内容更新分别判断，不因内容更新顺带强制升级启动器。

修改前，受管实例的诺拉请求已经经启动器转入与按钮相同的更新程序。缺陷是请求和执行资格依赖启动器，不是缺少共享的文件更新程序。“两个入口共用更新器”本身不唯一决定两个入口必须采用本轮新增的独立任务提交方式。下文的 Node 接管与 GUI 接入描述当前实现；独立执行、数据保护和更新结果是必须满足的行为，具体进程语言、按钮适配方式及允许更新中关窗均不能反过来冒充用户需求。

## 一条执行流程

1. 诺拉或启动器按钮提出更新请求；用户授权与安装归属核验仍由更新器执行。
2. 更新器取得本实例的互斥锁，固定目标版本，查询、下载并校验资源，在临时目录准备更新。
3. 独立更新任务接管后，才停止需要替换的服务；诺拉会话断开不终止该任务。当前启动器在任务进行中请求退出时提示等待，不另行停止更新器管理的服务；安装、模型保存与目录选择继续受原退出保护。
4. 同一事务完成备份、替换、验证与服务恢复，持久记录实际结果。失败时恢复原程序和用户数据；不能确认恢复时保留现场并给出具体原因。
5. 诺拉重连或启动器重开后读取同一更新结果，不另建一套更新、恢复或任务状态真相。

安装目录、版本协议、并发写入、资源完整性、可恢复性仍需核验。校验更新器及实际安装，不能用桌面 APP 可执行文件或在线会话代替更新器的执行资格。

## 已实现的职责调整

| 位置 | 原有缺口 | 本轮调整 |
| --- | --- | --- |
| `nora/skills/system/tavern-updater/scripts/update.py` | 以桌面安装标记要求 GUI 在线端点 | 调用已安装的 `updater/task.py`；标记仅核验根目录和端口 |
| `launcher/desktop/updater-capability.js`、`updater-task.js` | 系统更新的执行凭据要求 APP 和 Electron | 校验真实 Node/Python、安装归属和发布清单封存的更新器闭包；不要求 APP 文件 |
| `deployment/update/bootstrap.py` | 带桌面标记时拒绝无 APP 的更新 | 官方独立入口将核验后的更新器交给同一任务；不删除标记或伪装安装来源 |
| `launcher/desktop/operation-cli.js` 与 `main.js` | 入口及执行身份归属于 APP | 按钮提交同一独立任务；继续使用既有 OperationController、原生锁、文件事务和恢复结果 |

任务接管后先确认短命提交进程退出，再开始替换。请求目录保存资源快照和总体操作指针；成功、失败和恢复终态仍只有 `installer/operations/<operationId>/operation.json` 一处权威记录。诺拉调用方断开不取消任务，也不要求 GUI 心跳；启动器不再新增“更新中主动退出”的放行。已是同一版本时仍检查真实程序字节和运行事实，不制造更新事务或重启服务。

查询必须结合真实写锁与总体操作：`settled=false` 时即使原始记录暂为 failed，也不能报告更新已结束；`settled=true / busy=false` 才能判定终态。无法核验时保留任务并明确报告，不静默重试更新。新技能可用完整校验的当前查询代码读取旧任务，不能改写旧快照来兼容；查询角色不等于原 Node 写者身份，写入仍需完整资格核验。

原生验收额外发现独立 Native 更新的旧停服代码只枚举 `/proc`，在 Windows/macOS 不能据此证明进程离线。本轮改用既有跨平台 NativeRuntime 归属核验和停服机制，确认进程结束后再替换；不新增一套杀进程规则。该项源码与真实流程验收分别记录。

上一轮 Linux 原生历史版本的实测，只证明该部署路径的更新和回退。它不能证明“任意安装来源都不依赖启动器更新”。此前报告仍作为历史场景证据，不能认证本合同已完成。

## 保留与调整范围

- 保留：来源与摘要校验、安装归属、互斥与子进程生命周期、持久事务、用户数据保护、失败恢复、日志诊断；已验证的配对重试修正。
- 调整：更新任务的入口及所有权从 APP 移到更新器；诺拉和启动器都作为调用者；成功、失败、恢复结果由同一任务提供。
- 不执行：移除现有启动器功能、重装或清空用户数据、把有启动器标记的安装伪装成另一种安装、整体回退到旧版源码、正式发布。

## 必须直接证明的验收

| 场景 | 通过条件 |
| --- | --- |
| 没有桌面启动器的安装 | 诺拉调用同一更新器完成更新，保留聊天、角色、世界、模型配置和凭据 |
| 经启动器安装、启动器关闭 | 诺拉仍可检查及执行更新，无需打开 APP |
| 桌面 APP 缺失或较旧、核心运行环境完整 | 不因 APP 身份检查阻止普通系统内容更新；更新结果可通过诺拉或更新器查询 |
| 启动器按钮发起 | 进入同一更新器；两个入口竞争时只有一个写者，另一方得到明确状态 |
| 任务中诺拉断开 | 独立执行者持续工作，任务有终态，重新连接后可读同一结果 |
| GUI 退出安全 | 更新忙碌或状态待确认时提示等待，不另行停止更新器管理的服务；安装、模型保存、目录选择继续受原有退出保护 |
| 新程序启动失败与替换中断 | 恢复原程序和数据，任务结束；后续能启动并重新更新 |
| 历史版本 | 按入口、数据和服务协议逐类验收，不以少量版本结果承诺所有历史版本兼容 |

以上规则同时适用于有桌面启动器与无桌面启动器的安装来源。此前 Mac 候选已取得真实按钮更新、更新中退出 GUI、关闭 GUI 后执行已安装诺拉技能、同版本无替换核验、重开正常操作及旧任务查询迁移的证据；最后还直接验证程序替换后的自动回退及同一任务再次更新。Windows、Linux 已完成真实失败恢复、调用方退出续跑、后续更新及公共查询补验，自动与显式恢复的实际区别见记录。范围复核另复现可选退出分支绕过其他操作保护的问题，已按授权撤回；撤回后定向检查和本机真实锁控制流通过，没有沿用旧候选的 GUI 结果认证新源码。实际候选采用本地固定资源；最终安装包与发布不属于本次撤回任务，相关未验部分和整仓检查现象单独记录，不冒充本次阻断。
