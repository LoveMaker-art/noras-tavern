# 核心维护合同

本仓维护诺拉智能体、酒馆、MCP、核心首装、服务控制与核心更新。核心任务由诺拉授权或明确的本地命令提交，保存固定目标、实例身份、操作记录、首次原因及真实执行与恢复结果。

## 共享执行输入

`tooling/maintenance-input.lock.json` 固定外部源码作者、已发布资产来源、大小、SHA256、186份输入文件与生产依赖锁。57份共享源码与外部作者修订逐文件一致；桌面应用的package.json不进入核心输入；现有执行协议需要的原始依赖锁仅作为只读来源证据进入临时交付。输入约3MiB，封存依赖只有 fs-native-extensions 和 semver，不安装 Electron。

首次运行 `node tooling/maintenance-input.mjs fetch`；验证用 `verify`。源码投影只使用固定缓存，缺失、损坏、非普通文件或成员冲突明确失败。重新固定版本要复核协议、文件摘要、实际原生依赖及跨语言消费者，不以版本号相同代替兼容性。

## 数据与恢复

保留用户模型密钥、配置、世界、会话、账本、偏好、记忆及现有数据恢复规则。程序回滚不自动等同于服务已恢复；实际写者和所有子任务关闭后，才能确认操作结束。状态未知时保留证据，不允许新写者绕过旧效果。

核心自更新始终不依赖桌面窗口。历史交付中的 `ops/installer/desktop` 字样属于兼容路径，不能据此删除核心更新任务仍调用的资源。新的 Git 源码由本仓和外部作者分别维护，不在两个仓库重复修改共享实现。

## 验证层次

源码合同、实际原生锁与子进程、完整隔离安装、平台文件锁/权限/路径、真实模型账号及外部连接分别验收。所有结论绑定源码/固定输入/解释器和实际用例。平台跳过和缺输入不计通过。涉及全机进程归属检查的用例串行执行。
