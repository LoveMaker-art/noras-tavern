## 四、BUG-01：模型配置重试持续阻断

### 用户影响与触发条件

模型服务临时失败两次后，即使服务恢复，用户使用原配置再次点验证，仍可能直接看到“连续失败，已暂停重试”。等待或重启不能自动解除这条持久记录造成的阻断。该结论针对已复现的配置路径，不代表所有错误或所有操作都会永久锁定。

### 根因链路

1. [`model-config.js`](../../launcher/desktop/model-config.js) 的 `configurationFingerprint` 用服务、模型、Key、基础地址和认证方式生成配置指纹。
2. [`main.js`](../../launcher/desktop/main.js) 的 `nora:model-save-test`（当前约 2307 行）将该指纹交给 `runOwnedTask('model', ...)`。服务从暂时失败恢复，不会改变这些表单字段。
3. [`operation-state.js`](../../launcher/desktop/operation-state.js)（当前约 578 至 586 行）对非 `pair` 操作执行同指纹连续失败门槛：此前失败且 `attempt >= 2`，新提交即写成 `blocked`，不进入模型执行。
4. `main.js`（当前约 1991 至 2004 行）注册了维护及启动类 rechecker，没有模型 rechecker；`operation-state.js`（当前约 673 行）遇到缺少 rechecker 直接返回原记录。普通状态查询也不是模型重试解锁。
5. 因而外部恢复没有进入条件重判，持久化失败计数仍继续拒绝同配置；这里没有已证实有效的时间到期释放机制。

`pair` 已有专门豁免，本报告不是断言旧配对锁定问题在新版按同样路径复发。修改 Key 等字段会改变指纹并获得新的尝试条件，但不应要求用户靠修改本来正确的配置绕过服务临时故障。

### 隔离复现结果

使用真实主进程处理函数、任务控制器和持久记录逻辑，受控替换文件系统／安装适配和模型响应，不调用真实模型：

| 步骤 | 观测结果 |
| --- | --- |
| 相同配置显式提交两次，模型均返回 503 | 实际模型执行次数为 2 |
| 将模型桩改为成功，时间推进一天，重建控制器模拟重开 | 再提交仍为 `RETRY_CONDITIONS_UNCHANGED`，执行次数仍为 2 |
| 调用重查，再次提交 | 仍未发出第三次模型验证 |
| 只改变测试用假 Key 后提交 | 执行次数变为 3，并成功 |

上述路径在 v2.5.4、v2.5.5 及本次工作区相关代码复现。是代码级隔离串联，不是 Windows／macOS 新成品 GUI 实测；复现程序为临时诊断脚本，尚未形成仓库回归用例。

### 修复约束与验收要求

- 按模型配置操作的真实风险修订准入：保留必要限速，允许用户在服务恢复后显式再次验证；不能只累积持久失败次数而没有可用解除路径。
- 不把“重新查询状态”暗中变成模型调用，不自动重放凭据；用户发起的真实验证可能再次计费，应遵守现有用途和授权边界。
- 两次临时 503 后，同配置在服务恢复时能够通过明确重试路径成功；重启不会形成永久锁。记录原始失败，不删除用户数据或历史记录。
- 鉴权失败、网络超时、取消、保存已发生但复核不完整分别验证；后者不能盲目重复写配置。
- 不为解除模型限速而放宽安装归属、未结束写者或未恢复维护修改的保护。

## 五、BUG-02：模型主日志丢失原始错误链

### 用户影响与实际边界

本地模型验证日志可能显示“操作尚未完成，请查看当前状态”及 `UNKNOWN_PROGRAM_ERROR`，缺少真正的 HTTP 状态和失败原因，给排障造成误导。**这不等于诊断未上传，也不等于界面和后台所有字段都只剩 unknown。**

### 根因链路

1. [`model-config.js`](../../launcher/desktop/model-config.js)（当前约 217 行）将模型服务非 2xx 响应构造成带 `status`、`source=model_service`、`site=model.test` 和经处理消息的错误。
2. [`operation-state.js`](../../launcher/desktop/operation-state.js) 的失败处理保存结构化技术字段；没有显式业务错误码时可以落到 `UNKNOWN_PROGRAM_ERROR`，但 HTTP 状态仍可单独保存。
3. [`main.js`](../../launcher/desktop/main.js) 的 `requireOperationResult`（当前约 195 行）根据 guidance 重新 `new Error(...)`，仅附加操作编号、错误码和操作对象，没有保留原错误的 `status` 或 `cause`。
4. 模型主入口之后记录的是这个重建错误。因此完整送达的一份本地主日志，也可能缺少原始模型故障信息；传输完整和诊断内容完整是两回事。
5. [`operation-result.js`](../../launcher/desktop/operation-result.js) 仍能读取操作中的 `primaryFailure.technical`，故 UI／后台可保有 HTTP 401。不能从本地主日志泛化为所有错误字段丢失。

另已排除两项误判：界面 `errorCopy` 会合并 `guidance.next`，不是简单丢失下一步；[`fault-packet.js`](../../launcher/desktop/fault-packet.js) 对模型错误使用通用上报消息是既有隐私策略，不应以直接上传服务商原始响应修复日志。

### 隔离复现结果

在 v2.5.2 至 v2.5.5 及本次工作区的对应路径，以受控 HTTP 401 串联模型错误、任务失败、`requireOperationResult` 和 `failureResult`：重建错误没有原始 `status/cause`，而 UI 技术字段仍为 401。未使用真实服务商凭据，不是提供商兼容验收，也尚未新增正式回归测试。

### 修复约束与验收要求

- 在重新封装前保留本次原始结构化技术原因，关联同一操作；用户文案、日志技术原因和故障上报隐私策略分层处理。
- 本地日志至少能区分鉴权、HTTP 状态、超时、连接拒绝和解析失败；保留可用的错误码、来源及失败位置，缺失字段明确缺失，不伪造原因。
- 保持现有 UI 的可理解提示和技术状态，不能为修本地日志而退化界面；后续失败以附加原因记录，不能覆盖首个业务失败。
- 自动上传不得新增 Key、配对码、请求／模型正文、配置全文或未经审查的服务商响应体；本地记录也应进行必要脱敏和长度限制。
- 针对 401／403／503／无效 JSON／超时分别核对：原始错误、任务结构、UI、主日志和上报摘要。接收成功不作为业务成功条件。
