## 第二次 CI 源码门禁诊断

运行 `39189753539` 的 preflight 通过，三个原生任务均在源码门禁停止，尚未构建 Hermes 或安装包。Mac ARM 的 JavaScript 874／897 通过，23 项均在测试解释器的 `descriptor(python)` → `privatePath` 所有者／可写位检查处拒绝。Windows 的 891／897 通过，6 项分为两类：

- 测试将全局 `x64/python.exe` 当作虚拟环境解释器，`dirname(dirname(executable))` 不具有 `Scripts/python.exe` 的 venv 布局，受控后台执行报 ENOENT；Mac 的全局解释器也未满足该组测试使用的私有文件约束。仅将 CI source gate 改为自己创建的 `venv --copies`，依赖仍固定 psutil 7.0.0、PyYAML 6.0.2；保留全部产品权限检查与拒绝用例，原全局解释器的元数据在新步骤记录。
- `-I -S` 忽略环境编码设置后，技能输出中文 JSON 可在 Windows cp1252 管道报 UnicodeEncodeError。这是产品输出协议问题；Node 查询显式按 UTF-8 解码，技能 JSON 输出改为默认 ASCII 转义，解析后的 Unicode 值不变。新增两个回归先复现原错误，修正后技能环境检查 16／16 通过，工作流与文档检查 29／29。

日志下载曾遇本机至 Azure 日志存储的 TLS 连接失败；只对该只读请求使用已配置本机代理及完整主机名解析，并保持原 Host 与 TLS 验证，取得原始三个任务日志。未修改系统代理、访问用户 Windows 测试机或将下载失败认作构建原因。

本机按新步骤创建 `venv --copies`，实际解释器为当前用户所有、权限 0755；完整独立任务能力检查 24／24 通过，包括私有快照、写权限拒绝、调用方退出续跑、重试与后续操作。该结果不能代替 Windows CI 对新布局的实际验证。
