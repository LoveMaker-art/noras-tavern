## 范围和交付状态

分支为 `codex/fix-pairing-standalone-update`。本次只落实已确认的更新规则：诺拉更新核心不依赖桌面启动器；桌面仍使用原按钮；两项有更新时一次提交；有明确兼容依据时保留成功部分；失败可恢复、可重试；用户数据保留。没有扩展 Hermes、配对产品设计、卸载器或界面布局。

没有合并、推送、触发远端 CI 或正式发布。下述批次 `v2.5.3`、`v2.5.4` 仅为私有本地协议验收目录，不能当作已经发布的版本。核心实际版本仍为 2.5.2，目标 APP 实际版本为 2.2.2。

## 本轮原生实测发现并修正的缺口

1. **窗口桥接漏传“两项更新”标志**：实际只完成核心。现已透传，并以真实 preload → main 调用链回归。
2. **APP 优先路径变量作用域错误**：准备核心 bootstrap 时引用了另一个函数内的 `networkPolicy`，替换前报错。改用本次调用自己的来源上下文；真实 main 路径回归由同一 ReferenceError 失败变为通过。
3. **重试读到前一次终态**：新重试尚未接管就沿 canonical 请求找到旧 rolled-back，界面先报失败，后台稍后成功。改为等待该重试 worker 发布其 admission 引用；初次提交的中断关联仍保留。直接查询回归覆盖“旧终态”和“其他 canonical 观察不能代替本次接管”。
4. **批次标签被当作核心版本比较**：显式选择批次 v2.5.3、核心实际 2.5.2 时独立入口错误拒绝。现按已核验的 publication tag 比较，并保留核心版本独立检查。
5. **Windows 新计划落盘使用了只读句柄**：在替换前 fsync 返回 EPERM。成品 Windows Electron 的真实探针确认 `r` 失败、可写句柄成功，故不是用户目录权限或安全软件的已证故障。改为创建 request.json 的独占写句柄完成 write/fsync/close，再发布指针；没有吞掉落盘异常。新增回归先复现 EPERM，再通过；同机直接执行修正后的 create/load 也已通过，随后才生成后续测试 APP。
6. **Windows 更新引导的命名空间路径被误拒绝**：APP 更新成功后，引导核心更新所用路径带 `\\?\`，Node 对命名空间驱动根自身的 `lstat` 返回 `EISDIR C:`，导致只读代码身份检查拒绝，尚未建立核心写任务。真实父目录链证伪了“越过根目录”的初步猜测；最终只对驱动根用等价普通 `C:\` 检查，后代保留原路径、摘要和归属检查。普通/命名空间同目录 verifyReader，以及按真实引导参数形状执行的 stage→validate，均已在 Windows Node 24.21 原生通过，之后才构建后续测试 APP。没有改注册表或关闭保护。

7. **2.4.2 已提交旧事务误判为待恢复**：真实旧记录只有 schema/status/version/backup 四字段，现代恢复加载器拒绝其缺少 recoveryPlan。独立后端现仅接受这一个已提交旧格式，且必须完整验证当前发布字节、世界、服务归属与健康、版本及记录读取稳定性；不使用旧备份执行恢复，不删除旧记录。prepared、restored 或带有现代字段的损坏记录仍走严格恢复路径。回归先复现 unknown，再验证允许更新和拒绝边界；真实 2.4.2 已成功更新到私有快照 `3aa31b835899`，375 个保护文件不变。
8. **部分完成后重试被后来的停机任务遮挡**：Windows 正常关窗产生新的 shutdown 记录，重开时全局最新任务不再是失败核心，按钮的 ID 比较提前返回。控制器现从当前两项更新引用读取其失败组件的规范任务，再执行原权限、忙碌和后端序号检查；没有把任意旧任务变成可重试。真实形状的窗口测试先复现“点击未提交”，修正后再验收。
9. **普通 Python 调用技能生成缓存后被代码核验拒绝**：同一个 Hermes 解释器不经过重启分支时，导入 bootstrap 会生成未声明的四个 pyc；真实 Linux 已捕获这些路径。技能在导入前禁用 bytecode 写入，子任务原有 -B 保持；没有允许未知代码文件或放宽摘要检查。无 -B、无 PYTHONDONTWRITEBYTECODE 的独立回归先复现缓存，再验证不生成。
