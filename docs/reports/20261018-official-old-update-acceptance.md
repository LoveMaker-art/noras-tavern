# 真实线上旧版本更新验收

状态：本轮实测与原始证据核对已结束；**未全部通过，仍有两项要求未满足**。独立分支 `codex/fix-pairing-standalone-update`，未合并、推送、运行远端 CI 或正式发布。

## 范围与来源

按产品基线 PB-06/PB-09 验收：启动器原按钮一次发起两项更新；诺拉核心更新不要求桌面 APP；聊天、角色、世界和用户配置保留；失败可恢复、任务可结束、之后可重试。保留现有按钮，不改旧安装的技能来冒充旧入口成功，不删除或改写恢复记录。

真实基线来自 GitHub `LoveMaker-art/noras-tavern` 的 **v2.5.2**：核心 **2.5.2**、启动器 **2.2.2**、提交 `ea1e35d83f3cfd2ee16b682a7363cdef74d0a22b`。Mac ARM 与 Windows x64 分别按原平台发布清单核验全部 12 项闭包；原 OPS 的 185 项文件逐一验 SHA。用原 first_install 初始化隔离实例，用原公开 APP ZIP 中的程序操作真实窗口。测试驱动是当前测试工具，生产执行代码仍是经过认证的旧代码。

本轮先测私有目标 `29d3ca052dc9`（核心 2.5.6／APP 2.2.3），发现问题后保留失败证据。最终测试目标为 `92498f650d3e0f49e00bb93a7bb4147fb286284a`（核心 2.5.8／APP 2.2.5）。这些号码仅用于触发隔离升级，**没有作为正式版本发布**。目标经既有本地验收传输接入，原校验、执行器、交接及恢复逻辑不变；不据此声称未发布新版已完成公网分发验收。

## 本轮发现与改动

### 1. 已获准的恢复重启仍被普通关窗保护阻止

真实旧版交接到新 APP 后，恢复按钮已设置 `quitReady=true` 并准备退出，窗口关闭回调却仍因为 `activeRun=true` 阻止退出，弹出“任务尚未结束”。助手等原 APP 退出，最终超时。

本轮在 `launcher/desktop/main.js` 的窗口关闭回调先放行 `quitReady`。普通任务中手动关窗仍受原保护。新增回归在修改前失败、修改后通过；实际 Mac 新 APP 已正常退出，未再出现该模态拦截。

### 2. 恢复交接前先确认相关后台停止

隔离实例中只剩崩溃报告子进程时，停止该实例酒馆后，这些子进程自行退出。这支持后台进程延长报告器生命周期的判断，但**不足以证明停止后台就能保证恢复助手立即通过**。

本轮在原恢复上下文仍持维护锁、已核验需要替换 APP 后，调用已有 `stop all`，确认诺拉与酒馆均停止才交接；停止不确定时不启动恢复助手，原本未修改程序的取消路径不额外停服。实际 Mac 日志确认 stop 已完成、再启动助手，但助手仍可能在子进程退出完成之前拒绝。故这项顺序防护已实现，完整恢复问题仍未解决。

### 3. 尚未收敛：Mac APP 恢复的离线判断

原绑定助手的 `require_launcher_offline` 会把 APP／备份目录内仍存活的进程直接视为 APP 未退出。本轮在已无主 APP 的场景，实际观察到 `chrome_crashpad_handler` 残留；最终助手仍报“启动器仍在运行”。现有证据不能把具体的退出延迟与句柄继承比例完全分开。

未改写原 job 的脚本、清单或快照，未忽略进程检查。原自带离线命令在相关进程退出后真实恢复成功。后续需要在保留原身份与恢复校验的前提下处理该退出判定，重新通过界面恢复按钮验收，才能解除本项阻断。

本轮额外生产源码只改上述 `main.js` 两处，并在原 `launcher_shutdown.test.cjs` 补对应回归。与本轮开始时封存的源码逐文件比较，其余生产文件未改。相关源码检查 52 通过、2 跳过；跳过的是需要实际独立 Python helper 的两项，未计入通过，也不替代本轮实机结果。

## 数据与证据边界

- 两个平台的正常升级保留原 908 个用户文件；最终 Mac 恢复及重试也逐项核对原文件，聊天、角色、世界和设置没有被删改。
- 酒馆重启可新增 settings 备份；本轮只允许内容 SHA 与原 settings 完全相同的新增备份，没有把任意新增／改动直接忽略。
- `.env`、模型配置凭据和用户偏好保留。Mac 更新器会更新其管理的 `mcp_servers.nora.command` 路径；这与覆盖用户模型、Key 或自定义偏好分开核对。
- 世界与会话经过实际 HTTP 读取；模型使用隔离配置样本，未把它声称为真实外部模型或 ClawChat 账号完整回归。
- 本轮实测公开 v2.5.2 的两个平台，不推断全部历史版本、所有安装路径或 Mac Intel 均已通过。旧原技能关闭 APP 会拒绝，需要一次通过新版官方独立入口接入；不能说所有旧原入口已经自动获得新逻辑。
- 本轮没有证明旧客户端的 APP-first 路径具备新版组件序列“保留已成功部分”的全部行为；其安全恢复结果单独记录。
- Mac 五组隔离测试最终均无残留进程、测试端口均无监听，真实 writer lock 探测均为 `busy=false`。失败证据与恢复记录保留，没有删除日志来消除错误状态。
- Windows 两案结束后，APP、更新工作进程、酒馆进程及测试保活父进程均无残留，60239／59869 均无监听，writer lock 空闲。更新完成的就绪界面 task/error 为空；正常关窗后保留最后一条“正在停止诺拉与酒馆”进度文字，但 shutdown 已确认成功、任务锁已释放，没有把这条文字当成仍在执行。

## 未满足的要求

1. **Mac 界面恢复按钮尚不能可靠完成恢复。** 原离线命令可恢复并继续更新，不等于原按钮已经通过。
2. **旧版诺拉原更新入口仍依赖启动器。** 新独立入口在 Mac 可实际更新真实旧核心，但必须先取得这个新入口；未更新的旧命令不会自动变成新命令。这是旧入口接入限制，不能宣布“所有旧版自主更新均通过”。

另有覆盖缺口：Windows 的新独立入口尚未在本轮真实公开旧核心上运行；Mac Intel、全部历史版本和公网新版分发不在本轮已取得的证据内。

正式发布仍暂停。技术验证、实机结果和正式部署分别记录；正常升级通过不消除上述阻断和覆盖缺口。
