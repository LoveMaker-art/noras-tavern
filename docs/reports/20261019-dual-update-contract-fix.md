# 双更新声明与重开标记修复

状态：两处源码修订及针对性技术验证完成；整包原生用户流程尚未重新验收。独立分支 `codex/fix-dual-update-compatibility-20261019`，基点为 `cfec1b97457508f83a9cd6af2773b76c48ed26fb`。用户随后明确授权将本分支与 `codex/fix-retained-data-copy-20261019` 合入本地主分支；本次先提交既有修复，再验证两项集成结果，通过后合入 `main`。不推送、构建正式安装包或发布，不访问正在工作的 Windows 测试机。

## 本次范围

依据产品基线 PB-06、PB-09，仅修正：发布可遗漏双更新兼容声明；自更新重开参数持续影响后续更新请求。保留原按钮、两项更新顺序判断、核心独立更新器、APP 替换助手、失败恢复、用户数据保护和退出规则。不访问正在工作的 Windows 测试机，不修改正式安装或线上资产。

验收要求：正常启动和自更新续接结束后，相同的两项更新请求进入同一固定目标序列；自动重开继续原序列；后续请求不再绕过兼容检查。兼容声明由源码内明确审阅的文件提供，遗漏或无效时在构建前、正式资源放行前阻止。失败恢复及重试使用原任务，聊天、角色、世界和配置保留；未确认的恢复不能当成成功。

## 已确认原因

- v2.5.4 的公开根清单缺少 `updateCompatibility`。正常启动的 2.2.3 在 `update-sequence.create` 拒绝两项更新，尚未替换文件。
- `SELF_UPDATE_JOB` 是进程生命周期常量，而 `runAction` 使用它选择更新路径。上一轮自更新重开后，即便任务完成，下一轮更新仍绕过组合序列。
- 本机真实记录确认 2.2.3／2.5.3 → 2.2.4／2.5.4 在旧续接进程中成功，操作 `e0797c55-e83c-408e-b79e-1f5d9eff7b47`。这与正常启动失败可以同时发生，区别是请求路径，不是 Mac 与 Windows。

## 验证记录

### 实际改动

1. **兼容声明随源码维护并自动接入。** 从工作流和直接包装命令共同读取 `tooling/release/compatibility/v<核心版本>.json`；显式输入仍可选同目录内其他已审阅文件。正式输入要求已提交且与固定源码相同，候选允许本地未提交文件。缺失、非法、与核心／APP 版本不符或协议不符，在导出、npm 或构建前拒绝。当前文件只声明 2.5.4／2.2.4 和 2.5.3／2.2.4 组合，即 APP 优先；没有把其他旧版本推定兼容。未来版本必须提供自己经过核验的声明。
2. **分发放行再检查成品消费者。** 从最终 ZIP 提取实际 `update-sequence.js`，核对其 payload 哈希并执行目标兼容判断，不能只通过安装／下载选择器就放行。APP-only 使用当前产品的声明，不要求被引用的旧核心文件重写；旧于组合更新协议的原 APP 可继续按原合同复用，现代 APP 缺少组合模块仍拒绝。
3. **续接标记不再决定新请求归属。** `runAction` 中普通核心／双更新请求不再受启动参数影响；启动时仍直接恢复原任务，续接回调结束后清除内存标记。成功、已恢复失败、未知结果或无可续接计划均消耗该次标记，但不改写／删除操作记录、恢复依据或备份。活动任务、未确认的恢复和原有退出保护继续生效。
4. **必要接线。** 新 JSON 在现有发布计划中登记为产品元数据，在环境复用检查中登记为不改变运行环境的输入；否则它会被识别成未知源文件，阻断原有构建和 APP-only 路径。没有引入新的构建／发布模式或扩大复用范围到其他文件。
