| 把所有原生功能逐项重写到Electron，或直接嵌入Hermes整套后台 | 前者看似界面完整，后者看似开发省事 | 前者重复维护协议／认证；后者扩大设置权限和生命周期，且没有自然满足先验证再切换。均不选 |

共用模块是两个真实调用方需要的实现归属，不增加配置副本、同步守护进程、通用表单平台或另一套业务任务数据库。

### 4. 模块职责与文件归属

| 模块 | 职责 | 禁止承担的职责 |
| --- | --- | --- |
| 启动器UI／IPC | 显示当前配置和所需字段，收集输入，展示授权、进度、取消、失败和结果 | 不推断协议，不自行刷新令牌，不直接写配置，不把未知服务映射成另一服务 |
| 诺拉技能 | 理解目标，补齐信息和当次授权，调用同一执行入口并解释结果 | 不猜字段，不打印凭据，不另写保存或回滚逻辑，不要求桌面APP打开 |
| 共享Python配置模块 | 实例检查、能力与字段描述、流程编排、精确配置补丁、验证、并发控制、提交和配置恢复 | 不实现服务商协议，不变成任意系统配置或命令执行平台 |
| Hermes原生能力 | 服务身份、模型规范化、认证、凭据生命周期、运行路由、请求构造和传输 | 不自动决定本产品的用户授权、数据范围和界面默认行为 |

建议保留`deployment/shared/model_config.py`作为兼容入口；把技能的原生执行与最小探测提取为该目录下少量内部实现文件。技能`configure_provider.py`变为薄入口；两个入口都调用同一份交付后的实现。具体内部文件数服从职责，不按每个服务建立一个文件，也不恢复此前整个已撤回方案。

执行采用当前实例已有Python，进程级隔离Hermes全局状态，继续使用现有stdin／stdout、Electron IPC和任务通知。不上新本地HTTP端口，不启动整套Hermes管理网页。原生导入、私有函数适配与能力探测集中到一个位置，不散落到UI、技能和维护检查。

### 5. 能力与字段合同

共享模块返回三类信息：服务身份与别名；该认证模式实际需要的输入／依赖／操作；当前实现与验证能力。目录发现、字段可输入、原生可解析、账号调用通过分别记录。

只读操作建议为`describe`（目录、字段和能力）、`inspect`（脱敏当前选择、认证条件及验证事实）、`list-models`（仅服务支持时）。列表可包含真实目录网络请求，不能称全部离线；状态轮询不发模型生成请求，不自动安装依赖或登录。

修改通过同一个`configure`流程完成，使用现有任务标识。它根据需要发出结构化的`需要输入／需要授权／等待授权／验证／提交／完成`事件；输入通过受控通道回复，取消使用现有任务通道。接口包含版本、实例、操作编号和阶段；不把Key或原生完整输出放进事件与任务历史。不新建通用工作流引擎。

字段模板按API Key、免认证本地、OAuth／设备码、云凭据、外部客户端和必要高级配置分类，并允许服务的明确差异。不要只由`auth_type`决定表单：同一服务可有多种认证，注册表的类型也不等于完整原生流程。字段元数据集中维护显示与输入合同，实际协议、端点、刷新仍由Hermes负责。官方默认地址不作为固定覆盖写回；只在用户明确设置时提交地址覆盖。

建议固定的接口最小内容如下；字段名可在接口冻结时确认，不能把示例直接当已实现协议：

| 对象 | 必需内容与约束 |
| --- | --- |
| 能力描述 | `contractVersion`、Hermes源码身份、`providerId`／别名、`authModes`、`fields`、依赖、模型列表能力、验证传输及明确限制；字段包含类型、必填条件、敏感性、允许值和来源。不得只返回单一`authType`假装完整 |
| 配置请求 | 本实例、操作编号、预期配置修订、明确provider／model／认证方式、本次字段补丁和当次验证授权；不接受UI任意指定实例目录或后台命令 |
| 状态／结果 | 当前选择、配置是否完整、认证来源与条件、最近验证事实、本次执行阶段和下次会话生效方式；不返回Key、token、请求头或原生配置全文 |
| 错误 | 失败阶段、稳定错误码、安全原因、适用HTTP状态／服务商安全错误码、是否已保存、认证是否发生变化、允许动作及日志编号；不靠泄漏原始SDK响应来保留根因 |
| 并发版本 | 修订绑定与主模型有关的持久设置，不绑定会自动轮换的短期token；相同操作重复查询不能产生新调用，迟到事件不能覆盖更新的任务或草稿 |

原生交互若仅有TTY界面，优先调用其底层认证／设置函数并把输入输出转为上述结构化交互；不能靠匹配英文提示或ANSI画面驱动正式GUI。原生缺少可调用入口时，将最小适配集中在Hermes适配位置并按锁定源码测试；无法稳定承接的流程如实列为未完成，不用“打开终端自行配置”替代本次用户目标。

对未识别版本或未知插件服务：保留当前配置与只读显示，明确缺少的适配，不能默认另一服务、假装无须认证或静默改走别的协议。完整覆盖目标仍保留，未接通项算未完成，不以目录可见充当已支持。

### 6. 界面保留与变化

保留模型设置入口、服务选择、模型名称、已有模型列表功能、提交、返回、日志、重查，以及适用的同步和重启操作。保留原安装页布局锚点、字段对齐和现有按钮样式，不增加常驻解释文字或新导航层级。

- API Key及显示／隐藏：只在相应认证方式显示；已有凭据不回填，允许用户明确沿用当前凭据或替换。
- 获取Key入口：只有该模式确实使用Key且有真实申请地址时显示；OAuth切为对应登录操作。
- 地址：只在该服务支持覆盖或必须输入时显示；不要求普通用户猜官方地址。
- 模型列表：有真实支持时保留；不支持时允许按原生模型名输入，不能把“不提供列表”误判为配置失败。
- OAuth：在原位置呈现登录、本人授权、等待、取消、超时和重试；网址由后台核验后交系统浏览器，界面不接触服务商密码或完整令牌。
- 云服务：按选择展示地区、项目、租户／认证方式等必要字段；凭据文件在本机选取，路径及内容不上传诊断。
- 外部客户端：显示真实缺项，由后台衔接原生客户端；安装外部软件或改变共享登录必须另有用户授权，不能把任意CLI输出解析成稳定产品接口。

打开设置页只读取，不自动保存／迁移。切换服务清理本次敏感草稿和过期异步结果，保留非目标高级设置；取消不修改原选择。表单与技能通过相同后端字段校验，不能各维护一套接受标准。

### 7. 配置、认证、验证与生效流程

1. 检查当前实例、固定Hermes能力和真实认证来源，读取脱敏当前选择；无可用模型时也能从启动器进入。
2. 收集本次服务、模型、认证及必要字段，建立仅含目标修改的候选。使用现有互斥，等待本人授权有明确超时和取消路径。
3. 按原生方式处理认证。API Key新值先放受保护候选；既有OAuth刷新使用其原生权威凭据来源和原生锁，不复制同一刷新链让候选独立刷新。
4. 先完成所有字段合并、范围约束及原生规范化，得到最终拟提交配置，再用这份配置验证；验证后不能删除必要字段或改变路由。
5. 最小请求只发送固定诊断内容，无聊天／人格／世界，无工具、无模型回退；明确授权和可能费用。验证目标与实际provider／model／endpoint／protocol一致。MoA等原生多请求不得说成一条请求或固定费用。
6. 提交前复核当前选择及目标配置修订；发现他人修改则保留其结果并拒绝覆盖。认证令牌正常轮换不简单等同“用户改变模型”，也不以旧令牌快照覆盖新链。
7. 提交受管目标配置和非秘密验证记录，再回读同一原生运行路由。配置、认证、酒馆初始化和任务终态分别报告；未取得结果不能再次自动提交。
8. 两入口随后从同一来源刷新。新会话采用新默认，当前会话不暗中中断；保留启动器现有显式“重启诺拉”，不自动重启酒馆或网关。

验证记录只能记录当前选择与验证事实，如目标、协议、非秘密认证引用、验证时间和配置修订；不成为第二份可编辑配置，不保存或散列短期访问令牌充当永久身份。旧`installer/model.json`按已有记录兼容读取，不能为了兼容填假Key。历史有配置但缺真实验证证据时，如实标记未验证，不抹去原配置、不强制停止已经工作的实例。

### 8. 必须先解决的工程风险

| 风险及证据 | 执行约束和处理方式 |
| --- | --- |
| OAuth令牌可轮换，复制凭据到候选刷新后，正式旧文件可能已过期。原生`auth_codex.py`明确refresh token单次使用；Qwen可写`~/.qwen`，Nous可受`HERMES_SHARED_AUTH_DIR`影响 | 认证与模型选择分开处理。保留原生最新凭据链，失败只撤回本次模型选择及确实能安全撤回的凭据修改，不整体恢复旧`auth.json`。登录与外部账户操作已发生时单列结果。若原生不能在保留当前可用认证的前提下完成该模式，先解决或明确阻断该模式，不能承诺无缝 |
| 候选验证后剔除字段。当前`native_config.py`白名单缺`vertex`／`bedrock`；Vertex向导写顶层项目和地区，提交重新组装可丢掉新增章节 | 按选定服务定义精确允许路径，包括真实必要顶层章节；先完成最终合并再验证同一配置。该项是源码推演，不冒称云账号已复现 |
| 原生目录不是完整表单schema，且内部函数随版本变化 | 服务身份与字段／流程适配分开；锁定revision并做签名和原生合同测试。版本变化时按受影响认证类别复验，不猜字段继续 |
| 原生网页保存可直接改主配置或启用其他设置 | 只复用所需函数；所有写入经过本模块范围与候选规则，不直接暴露或嵌入完整管理后台 |
| 桌面已持维护锁，再进入技能原有`_writer`会竞争自己 | 复用现有已验证的操作委托，避免重复获取。技能独立持有同一实例锁，不通过APP转发；不以任意布尔值跳过锁。长授权等待需有取消和释放证明 |
| 多文件逐个替换不等于整体原子事务，强杀可能留下部分提交 | 复用现有任务记录，对短暂本地提交保存最小受保护检查点；先识别所处阶段，再恢复可恢复的配置修改。认证刷新不纳入旧字节整体回滚。无未恢复修改不得长期锁住启动、更新或卸载 |
| 密钥、授权链接或原生错误可能被日志转发 | UI不回显凭据，输入不进命令行／长期任务记录；结构化错误保留阶段、类型、HTTP状态和安全原因，不原样转发SDK正文。覆盖平台文件权限、日志和异常分支 |
| 某些原生传输不能安全作最小验证 | 当前`codex_app_server`等要补目标可核验、禁止私有上下文及工具的验证路径；不能偷偷换传输通过。无法接通时明确为完整目标阻断 |
| 不同入口／版本组合加载不同helper或验证记录 | 共用模块只交付一份权威实现，按核心组件交付；APP和技能先查能力版本。保留旧入口兼容层，不以新版APP作为技能前提；实际交付必须覆盖混合版本组合 |

“旧配置不变”不单独证明“旧认证可用”。刷新已有认证后的失败恢复必须再次用原模型验证或取得等价原生证据。对服务商撤销账户、磁盘损坏、外部CLI全局行为和断电后的远端状态，不能承诺本地文件备份必然解决。

### 9. 酒馆同步、启停和维护边界

诺拉、酒馆、MVU分别配置。已有酒馆模型零覆盖；首次空白酒馆仅对确实可转换的服务沿用现有初始化。不能转换的订阅／云认证，保留已经验证并保存的诺拉配置，酒馆独立设置，不把它伪装成通用Key。

这涉及现有首次同步阻断行为的变化，实施前应把“诺拉已配置、酒馆待独立设置”的页面及完成条件写入L-08／09，与用户此前“无法同步时保留诺拉配置”的要求对齐。不能悄悄跳过已有完整版模型／配对要求，也不自动挑选或购买另一个酒馆模型。

只修依赖旧模型读法的状态与维护收尾调用点，不借本任务重写安装、更新或卸载。原服务健康与配置证据分开，临时断网或服务商额度不足不当作程序损坏；没有未恢复写入时，不因配置失败永久限制后续合法操作。

### 10. 分阶段实施和每阶段退出条件

| 阶段 | 必要改动及交付 | 退出条件 |
| --- | --- | --- |
| 0 范围与原生合同 | 核对最新main与既有技能未提交工作，保存完整归属；确认设计变更，整理每类服务输入、认证来源、副作用、必要配置路径及探测能力 | 当前安装和锁定Hermes均有可追溯覆盖矩阵；OAuth链、云字段与锁委托三个关键设计有可重复证明，不以改UI先行掩盖 |

| 2 启动器交互 | 原页面接相同目录／字段／执行模块，补原生认证交互，撤掉重复的固定名单和网络测试实现 | 首装、日常修改、取消、错误重试和双向读取一致；不存在未知服务默认成OpenRouter |

| 4 目标环境验收 | Windows x64、Mac ARM、Mac Intel按实际受影响原生依赖和交互验证；正式实例不用作隔离试验 | 下列验收矩阵有实际结果、证据及未验项；缺真实账号不记通过，不把Mac结果当Windows |
| 5 交付准备 | 按发布流程确定核心组件、APP及首装包的必要产物，核对源映射、依赖与兼容记录 | 后续独立授权后才构建、安装正式实例、合并／推送／发布；没有授权时停在当前验收阶段 |

不能为提速先完成全部界面再补认证和恢复，也不在第一阶段新增通用代理／认证服务器。当前分支存在早期方案撤回及未提交技能工作，实施分支要从明确基点整理净差异，不能直接把当前HEAD的全部旧提交合入主线。

共享实现归核心运行文件，不能让新技能导入APP资源内部脚本。APP随包的旧helper兼容入口与已安装核心模块需要能力协商：支持的新核心优先同一权威模块；旧核心组合不得绕回第二套新实现，可保留受支持的旧Key能力并明确升级条件。新技能依赖相应核心模块是交付依赖，不等于要求新版APP。旧APP读取新的OAuth／云状态是否兼容必须单独验证，不能用写假旧记录解决。共享实现提取后，应删除技能中已迁移的重复实现，并核对卸载离线检查等实际导入者的依赖闭包；不改变卸载产品行为。

最终交付涉及启动器与核心技能的实际字节变化，分别更新相应版本与兼容描述。固定Hermes／Python／Node运行环境未变且摘要及依赖等价有证据时复用，不因本模块变化自动重建全部环境包；有新增运行依赖时重新评估。源码／隔离UI阶段不反复构建安装包，最终目标组合按授权完成成品验收。
