# 安装、核心更新与启动器自更新

本文说明当前源码的安装维护与两类更新机制；产品职责见[共同更新与恢复规则](product/README.md#shared-update)，任务范围及特定制品的验收证据见[可靠性交付执行与证据导航](launcher-reliability-plan.md)。历史发布包仍按各自协议运行，存量联合任务的兼容合同在下文单独说明。

## 执行边界

APP 与独立核心任务共用适用的操作记录格式、策略和原生互斥，各自固定目标、操作编号、请求身份及尝试次数。操作记录位于数据目录的 `installer/operations/<operationId>/operation.json`，保存结果和子事务引用；程序、配置、安装记录的真实状态由相应事务和 receipt 决定。共享实现不代表联合授权或共同成败。

| 职责 | 唯一实现 |
| --- | --- |
| 总体准入、持久次数、终态和允许的用户动作 | `operation-state.js` |
| 原生文件互斥、受管进程与创建身份确认 | `os-lock.js`、`operation-lock.js`、`operation-delegate.js`、`deployment/shared/operation_control.py` |
| GUI / CLI 共用恢复策略 | `operation-policy.js` |
| 固定发布、兼容校验、缓存及有限下载尝试 | `deployment/update/releases.js`、`release-network.js` |
| Hermes 环境准备、交换及恢复 | `runtime-transaction.js` |
| 首次安装的准备树、配置、receipt 和恢复 | `deployment/install/first_install.py` |
| 独立核心任务接管、程序更新与恢复 | `deployment/update/task.py`、`task_backend.py`、`launcher/desktop/updater-task.js`、`update.py`、`recovery.py` |
| APP 自替换、助手运行资源及交接 | `launcher-update.js`、`replace-launcher.py`、`app-helper-runtime.js` |
| 原始失败的限定安全证据与故障投递 | `evidence-store.js`、`operation_evidence.py`、`fault-packet.js`、`telemetry.js` |

用户在诺拉对话中授权后，更新技能通过 `deployment/update/task.py` 提交独立核心任务；桌面与无 APP 部署采用同一职责，不经过桌面双更新接收器。官方独立接入入口 `deployment/update/bootstrap.py` 可取得并校验执行代码，再交给同一任务。APP 关闭、缺失或过旧本身不取消核心更新资格；实例、依赖、可信资源及实际竞争写入仍须核验，边界见[部署规则](product/README.md#deployment-support)。

启动器检查时分别展示 APP 与核心版本，安装更新只提交 APP 目标。`deployment/update/system-update.js` 等旧事务模块保留受支持历史记录的读取和恢复，不作为新联合任务入口。

<a id="maintenance-locks"></a>
### 总体维护锁与内部生命周期锁

总体原生锁由根执行者取得，GUI 与技能维护入口共用原生互斥。子执行者先通过真实 PID、创建时间、操作编号、epoch 和单次 job 的握手，再领取委托；不会重复取得总体锁。桌面退出后尚在写入的子进程仍持有互斥，必须确认实际关闭。历史 PID、环境变量或锁文件存在都不足以授权修改。

实例内部生命周期锁由 `deployment/shared/runtime_lock.py` 维护，酒馆安装、注册和服务停止使用同一实例锁；内层业务不再次获取外层总体维护锁。公共模块的源码归属见[仓库职责表](REPOSITORY.md#implementation-owners)。

## 安装与下载

1. 查询当前通道的完整发布，固定同一份清单及平台，不在中途重新挑选“最新”。新版执行协议不匹配时，保留当前安装，提示使用新版完整启动器。
   首装先验证固定 tag 的平台系统清单，再按 `files['release-manifest.json'].asset` 读取并核验原文字节。实体仅允许历史通用名或当前平台前缀名；不能换成其他平台、其他版本或根清单冒充。系统更新继续读取根组件清单。共享资产索引只改变已冻结业务资产的传输来源，控制清单仍在当前 tag。
2. 下载和校验在停止旧服务、替换文件之前完成。哈希一致的包内资源和缓存可以复用；网络尝试有上限，断点续传必须核验范围与最终哈希。
3. 在隔离准备树中完成运行时释放、依赖实体化及安装准备，封存程序内容和目录身份后才交换。启动产生的受管备份目录属于可变数据；未知程序文件或链接变化仍拒绝继续。
4. 文件提交后仍检查真实程序和连接。相同操作可继续验收已提交内容，不能重复安装或重新授权未知代码。
5. 未配置模型、未配对表示等待设置，不表示程序安装失败。本地可用与外部 ClawChat 连接分别记录。

只有查询最新发布因网络或服务不可用而失败，才提供“取消”或“安装已校验的包内版本”选择，默认取消，不将包内版本称为最新版。平台不支持、协议不兼容、下载损坏和无效清单不会自动改装旧包。

界面展示实际阶段。只有下载连续三分钟没有有效字节增长时显示网络与代理提示；解压、拷贝、校验的安静期不会显示 GitHub 下载故障。心跳或重复零进度不算字节增长。

## 核心更新与恢复

准备阶段不破坏现有服务。独立核心任务记录原服务状态，并将程序、必要配置和 receipt 变更关联到同一操作。文件交换成功不等于更新成功；必须核验目标版本、适用运行结果和任务结束。调用方或诺拉断开后，已接管任务继续；重连读取同一结果。

停服前后的配置检查按归属执行。用户配置、任务定义和未知字段继续要求与准备时快照一致；只有已核实的无限次 cron/interval 任务运行字段可以在停服核验后单独封存派生状态。原准备备份不改写，恢复使用经哈希及定义核验的停服快照。配置冲突日志只记固定相对路径、归属、类型和摘要，不记配置内容或密钥。

更新器记录成功配置写入的摘要。恢复遇到不属于原快照或已确认写入的变化时保留当前文件及备份并停止覆盖；因此写者部分写入、尚未记录成功就被中断的现场可能需要进一步诊断，不能承诺自动恢复。旧 schema 1 事务保持既有恢复合同。阶段标签变化仅表示进入下一阶段，不再自动上报上一阶段成功；总体终态由实际提交及运行验收决定。

配置恢复在移动当前文件之前保存逐文件意图，绑定失败现场的目录身份、内容摘要和旧备份摘要。归档后再次中断，只有归档证据匹配才允许在目标缺失时继续复制；先复制到临时路径，再原子替换。重试遇到新建用户配置、归档内容变化或身份替换时拒绝覆盖；已恢复的项目不再次覆盖后来修改。旧 schema 1 事务也使用这些恢复检查点，不追认未知写入归属。

<a id="recovery-closure"></a>
### 恢复执行代码与快照绑定

`deployment/update/recovery.py` 保存恢复计划和文件恢复检查点，桥接器提供停服、恢复运行及验收操作。恢复模块随桌面资源和增量更新器交付；默认数据布局的恢复只需标准库，外置数据目录通过验证闭包内的实例解析组件及既有 PyYAML 核对绑定。恢复不依赖可能在目录交换中缺失的已安装 operations 文件，修改前先核验路径、身份和备份。单文件旧入口只做取得已验证执行器所需的路径发现，不复制完整写入准入规则。

目标卷目录命名、归属和校验复制由恢复模块内的文件存储函数维护；Journal 保存原恢复计划、文件身份和持久检查点。备份清理复用同一归属判断，不构造假的恢复事务，也不改变旧记录格式。

外置数据目录的恢复绑定从本次事务已校验的原配置快照解析，不依赖正在被自身交换的当前配置文件。首装先核对快照索引、身份和摘要，更新恢复先核对原配置备份摘要，再交同一个实例解析器；来源不符时保留现场。这些校验约束本次恢复来源，不据此冻结维护结束后的用户数据或自管备份。

回滚只恢复更新前实际运行的服务。若旧快照明确网关原本运行但未连接 ClawChat，恢复要求确认受管网关仍运行，不强制把原断连状态升级为已连接；原已连接或旧快照缺少连接字段时，连接验收仍严格。正常启动与新版本更新验收不采用这一恢复例外。这是原运行状态合同的修正，不能据此推断某次线上配置变化的写入者。

错误时先保存首因，再恢复、清理或记录次因。恢复过程中又断电，下一次按目录身份、原事务和备份内容重新核验，不能仅凭旧阶段文字判断可覆盖。状态查询只读，不自动修复程序或改写安装状态。

| 已确认的事实 | 用户可执行的动作 |
| --- | --- |
| 下载 / 准备失败，原安装未改变 | 按明确原因调整条件；允许范围内重试 |
| 有可核验的未完成核心事务和完整备份 | 由独立核心任务处理对应恢复；执行前重新核验并保留失败现场 |
| 文件已恢复，但服务验收失败 | 明确显示文件恢复事实；允许有限的“启动已恢复的旧版本” |
| 历史记录未保存服务状态 | 不猜测此前是否运行；先恢复文件，再由用户明确启动 |
| 进程、目录、记录或备份身份无法确认 | 保留现场，只提供重新查询、日志及相应处理说明 |

程序维护的相同目标、相同条件连续失败后暂停直接重试；重开窗口或改用技能不能重置次数，“重新检查条件”必须取得新的可核验事实。日常服务启停采用有界冷却：连续实际失败后等待30秒，再允许显式重试，仍核验服务归属及未结束的程序写入。缺少模型或配对时进入相应设置，不以冷却代替设置。新模型配置／配对提交按各自条件规则判断，不自动重放凭据；模型条件指纹不保存或上传Key、地址及模型正文。详见[共同状态与重试](product/README.md#state-and-retry)。

恢复版本、恢复数据和较新的失败现场分别说明。旧快照恢复不会悄悄合并两份聊天 / 世界，也不将“文件恢复了”说成“已经可以使用”。

## APP 自更新与恢复

APP 更新固定自身操作、目标和发布计划，自带所需助手运行资源。替换、回退及结束任务不以核心目录、模型可调用、ClawChat 在线或核心健康为额外前提；实际竞争写入仍受维护互斥约束。

新 APP 的启动确认和固定目标核验用于完成自身交接。成功只报告 APP 版本。失败时，确认原 APP 未改，或已恢复旧 APP，并确认相关写者退出后，才能结束原任务；替换、恢复或写者状态未知时保留对应查询、恢复入口，只限制冲突动作。独立核心／服务问题分别呈现。APP 交接重开不下载、提交或续接核心更新，也不将核心升级作为自身任务成功条件。

## 历史联合更新合同

旧协议曾要求新 APP 启动确认后，继续核验系统交付并进行联合提交，在此之前保留旧 APP 及系统备份。这解释存量交接、结果及备份的来源，不再作为新任务的执行顺序。

已有联合任务保留真实结果、失败和未恢复效果。APP 只按原记录处理已开始的 APP 替换恢复，核心及联合任务事实在 APP 侧保持只读；核心效果交由对应核心执行器处理。不自动续接旧计划中未执行的另一组件，不删除记录或将部分结果整体标为成功。后续重试通过对应单项入口授权，详见[存量双更新规则](product/README.md#shared-update)。

## 日常启动和保留数据更换新版

日常启动读取既有安装事实及当前进程健康，不对用户修改的技能、模型或定时任务重新执行首次安装。停止前再次核验真实进程身份；不依据历史 PID 强行结束其他程序。

旧 APP 无法运行或不支持新协议时，可按[用户更新说明](update-nora-tavern.md#启动器完全版)通过完整安装器覆盖更换 APP。分别核对原 APP 安装位置与原核心／数据目录，保留安装记录；只更换 APP 不代表核心也已升级。聊天、世界、配置、密钥、安装事务和诊断证据继续保留，不要求清空 NoraTavern 或删除恢复记录来绕过阻挡。

保留数据卸载和彻底卸载仍由同一卸载模块处理。原生锁的稳定技术目录会保留，用来避免旧进程与新进程锁到不同文件；这个技术目录不表示卸载后的程序仍在运行。真实旧 APP 覆盖安装是否满足数据保护，需要在对应安装器和目标环境单独验收。

## 发布与验证

ClawChat 开场白补丁先应用到受审核的插件源码，再生成运行时文件哈希和补丁版本摘要。整合包拒绝混用旧运行时与新补丁；用户安装时不需要 Git 来应用预置补丁。补丁或封存运行时内容变化时，不能只替换启动器 UI 或 Python 脚本后继续复用旧运行时包；未变环境仍按发布流程核验复用依据。

按[发布流程](release-process.md)判断本次核心、APP 与运行环境的交付范围，固定来源和资产身份后分别验收。已发布的 2.4.2 / 2.0.2 等历史资源保持不可变；旧客户端接入、新组件组合和完整安装包各自取得对应证据，不因新入口源码存在就宣称旧安装已可升级。

`tooling/run.mjs` 统一源码投影；`launcher_product_refactor_smoke.cjs` 使用实际原生准入和受管子执行者进行隔离安装 / 更新，不再维护裸安装入口 smoke。`launcher_packaged_app.test.cjs` 检查真实 electron-builder APP 的 ASAR 模块、外置资源及 JS / Python receipt。缺少打包产物时跳过该门禁不算打包通过。

源码检查、合同测试、真实候选流程、用户视觉验收和线上部署分别记证据。Windows x64、Mac arm64、真实 Intel Mac，以及 APP 重启交接、保留数据覆盖安装、故障实际入库均是独立验收项；其他平台、Rosetta、队列为空或查询接口返回 200 不能代替这些结果。
