# 诺拉酒馆产品设计基线

版本：1.9。整理日期：2026-10-19。适用范围：酒馆、诺拉、启动器、更新、集成、分发与维护。

本文件是项目唯一的产品设计基线。第一至七节规定已确认的用户体验、操作边界和模块责任；第八节登记本轮决策及尚待确认事项，附录登记当前实现、差异与证据。**产品规则已确认、代码已实现、流程已验收、版本已发布分别记录。**

阅读顺序：先理解产品组成，再看用户流程、状态与允许动作、更新恢复、数据保护和模块交接；本轮三项决策见[第八节](#八-已确认决策与待确认事项)，实施范围和验收要求见[技术实施方案](design/update-release-alignment.md)。PB-01 至 PB-09 保留原编号供任务追溯，不代表九个缺陷或九个实施阶段。术语的精确定义沿用 [CONTEXT.md](../CONTEXT.md)。

## 一 产品目标与组成

### PB-01 用户目标与取舍

主要用户是普通角色扮演玩家。核心结果是：能够创建故事、与角色互动、保存进展，并在下次继续同一个故事；诺拉可以陪伴用户并按授权协助管理这些内容。

默认流程通过现有界面完成安装、配置、使用和维护，进阶能力可选。普通用户不需要理解部署脚本、进程或事务目录。发生故障时，产品应说明影响和可执行动作；手工删除记录、清空数据不作为日常维护步骤。

发生取舍时，先保护用户内容和本实例的操作边界，再完成维护目标；对已经证实可以安全使用的部分保持可用。复杂扩展、自主运维和上游组件升级均服从这个默认体验。恢复能力受实际文件和备份条件限制，不承诺磁盘损坏或数据与备份同时丢失后必然恢复。

### PB-02 产品组成与使用形态

酒馆是进行角色扮演和保存世界的应用；诺拉是运行于 Hermes 的智能体；启动器是桌面安装与管理客户端。三者在同一项目协作，职责按用户结果划分，源码所在仓库不决定它们是否必须一起更新。

| 对象 | 负责什么 | 与其他部分的边界 |
| --- | --- | --- |
| 诺拉 | 与用户对话，按授权协助管理世界、角色、记忆及应用，检查并请求核心更新 | 通过酒馆业务接口和独立更新器执行；自动提醒与自主更新不接管桌面启动器本体 |
| 酒馆 | 角色扮演界面、世界和会话的持久业务、故事运行与数据保存 | 提供界面和 MCP 共用的业务结果；世界身份和用户内容不归启动器窗口所有 |
| 桌面启动器 | 安装、配置、启停、日志与维护结果呈现；检查核心及自身更新，执行自身替换 | 保留原控制和操作入口；内容维护交给同一独立更新器，桌面 APP 不成为核心更新前提 |

ClawChat 是当前配对和对话平台，Hermes 承载诺拉，MCP 连接酒馆业务，独立更新器执行核心维护。它们的交接责任见第六节；本轮没有新增运行服务或拆分源码。

| 使用形态 | 用户获得的能力 | 首次入口与边界 |
| --- | --- | --- |
| 完整版：诺拉＋酒馆 | 酒馆游玩、与诺拉对话及其应用管理能力 | 桌面整合包走第二节的完整设置；已有源码／服务器部署按各自安装文档进入，不因没有桌面 APP 失去普通内容更新资格 |
| 单独酒馆 | 世界、角色和故事游玩 | 按酒馆独立安装文档设置；不包含诺拉的管理能力 |

完整版首次要求配置诺拉并配对，是已确认的产品选择。单独酒馆的存在不改变这个选择；两种形态遵守相同的数据保护要求。支持的安装包平台、来源和历史版本范围由对应发行及验收记录说明，不由形态名称推断。

“云端／本地”是部署场景，“完整版／单独酒馆”是使用形态。没有桌面启动器的云端也可以包含诺拉和酒馆；适用维护范围根据实际安装确定，不用操作系统或桌面窗口代替判断。完整安装包是给新用户组合交付程序和必要环境的产物，不是另一套世界数据或强制所有安装追随的核心版本。

## 二 用户完整流程

### PB-03 完整版首次设置

默认路径：**安装诺拉与酒馆 → 配置并验证模型 → ClawChat 配对 → 启动检查 → 日常使用。**

| 阶段 | 用户操作 | 可以进入下一阶段的依据 | 失败后的去向 |
| --- | --- | --- | --- |
| 安装 | 确认位置并开始安装 | 本实例程序、依赖和安装结果通过适用检查 | 留在安装／恢复流程，说明修改范围；保留已存在的用户内容 |
| 模型 | 选择服务、模型并提交配置 | 配置保存及规定的模型验证成功 | 回到本次模型配置，说明保存和调用各自的结果；不重复安装 |
| 配对 | 获取连接码并显式提交 | 配对执行返回有效成功结果 | 显示原失败原因；允许按重试规则重新提交，包括新连接码 |
| 启动检查 | 按现有流程启动并等待检查 | 各项必需检查有实际结果 | 区分本地服务、模型及外部连接问题，进入对应处理路径 |
| 日常使用 | 打开酒馆、与诺拉对话 | 本地游玩与诺拉连接分别具有可用证据 | 受影响部分按第三节处理 |

首次必须配置诺拉并完成配对。ClawChat 是当前适配平台，不承诺任意 IM 都可直接接入；其不可用会影响首次设置完成。程序已安装、模型已配置、已经配对和当前在线分别判断，后一个失败不自动抹去前一个事实。

### PB-04 日常使用与退出

下次使用沿用原安装、世界和配置，无需重走首装。用户打开已有世界或创建新世界，进行故事互动并保存，下次仍能继续原世界和会话。基础游玩与增强能力的可用性按第三节分别表达。

| 日常动作 | 确定的产品行为 |
| --- | --- |
| 查询状态 | 读取安装、配置、配对及当前服务事实；查询不隐式重新安装、迁移用户数据或启动更新 |
| 启动／停止 | 保留现有独立控制；只作用于当前确认的实例，停止结果须能核验 |
| 修改模型／重新配对 | 进入现有表单，处理相应配置；不重置世界、聊天或无关配置 |
| 日常关闭启动器窗口 | 保留现有关闭行为，不新增两平台统一关窗停服要求；实际触发停服时核验相应结果 |
| 停服失败或无法确认 | 保留可见说明及适用的检查／重试入口，不以窗口消失证明停服 |

用户已取消“两平台日常关窗统一停服”的要求，不再作为待实施项。本轮不改变现有关闭代码，也未另行确定统一的后台常驻或退出策略。维护任务进行中的关闭规则见第四节；服务器及无桌面部署按对应部署方式管理进程。

## 三 状态判断与允许的操作

### PB-07 按事实判断状态，按影响限制动作

产品判断分别回答五个问题：程序是否安装、配置是否完成、是否已配对、相关服务现在是否可用、是否存在仍在执行或尚未恢复的维护修改。本节是行为对照，不要求新增页面、持久化状态系统或第二套任务管理器。

| 已知情况 | 用户应看到什么 | 允许的下一步与限制范围 |
| --- | --- | --- |
| 没有安装，或安装确实未完成 | 安装进度／缺失的安装条件 | 安装或适用的继续／恢复；已有目录先核验归属和数据 |
| 程序已安装，模型或首次配对未完成 | 明确缺少哪项设置 | 进入对应设置；完整版尚不算首次设置完成，不把它报告为程序安装损坏 |
| 设置完成，服务已停止 | 当前停止状态 | 正常启动；保留配置与故事 |
| 已完成首次设置，本地酒馆可用，外部连接中断 | 本地与外部连接分别显示 | 保持已证实可用的本地能力，检查或重试连接；不强制重装或清空配对配置 |
| 模型验证／调用失败 | 哪个用途的模型失败、保存是否成功、调用结果是什么 | 修正对应配置或重试；模型尚未返回与程序损坏分别诊断 |
| 世界有效，某项脚本／MVU 等能力未就绪 | 世界可用及具体能力状态 | 继续基础故事或重试该能力；不因能力失败删除、回滚或重新创建有效世界，不宣称完整玩法已经正常 |
| 任务仍在执行，或恢复和写入尚未结束 | 当前任务、阶段及等待原因 | 查询同一任务，使用该阶段已有的合法动作；不启动竞争写入 |
| 原任务失败，已确认无未恢复修改 | 失败原因、原安装是否可用 | 按第四节重试或继续使用；历史失败次数不构成永久锁定 |
| 无法确认安装归属、真实进程或未恢复修改 | 具体无法核验的对象及其影响 | 保留现场，查询／诊断并执行适用恢复；限制会触及该风险的操作，不把未知状态写成成功或授权删除 |

**状态查询与完整验收分工：** 日常查询核对适用的安装记录、当前进程和健康事实；安装／更新验收核对相应组件、绑定及运行结果。日常轮询不全量哈希用户自定义内容，也不以历史验收记录替代当前服务状态。

**重试规则：** 可保留必要限速；输入或相关条件改变后，应允许合法的新提交。配对码由用户显式提交，不自动重放，不把原码写进日志或长期重试记录。原始失败、重试被限速和执行尚未开始分别呈现，重启也不应留下无法解除的合法操作锁定。

**阻止操作的证据边界：**

| 证据类型 | 判断规则 |
| --- | --- |
| 实例身份、用户配置、发布清单／待装资源校验、服务归属、恢复来源 | 是相关修改的依据；不匹配时停止对应修改，并说明缺少的证据 |
| 已发生但尚未恢复的目录替换或外部平台变更 | 按真实剩余影响阻止相冲突的启动／更新／保留数据卸载，进入恢复 |
| 已准备但未应用的资源、已证实完成恢复的历史事务 | 没有相应未恢复效果时，不因“曾经失败”永久阻断下一次操作 |
| PID 提示、下载缓存、失效的运行提示 | 按已有规则重新发现进程或重取已校验资源；这些文件自身不等于有效进程或危险写入 |
| 无法读取或验证的记录 | 不擅自改写、删除或视为有效；先确定它是否影响本次操作的必要证据，报告该处缺口 |

阻止操作的说明须交代失败位置、数据／程序是否改变、被限制的动作、现有可用动作。恢复错误保留原始原因；需要额外诊断时列出缺少的证据，不让用户反复猜目录或删除日志碰运气。上述判断依据沿用 [ADR 0014](adr/0014-repair-derived-operational-state.md)。

## 四 更新、关闭与失败恢复

### PB-06 两个入口，一份独立任务结果

本基线将诺拉受管规则／技能、酒馆应用程序及适用的共用维护组件统称为“诺拉酒馆核心”，其更新不等于桌面 APP 替换或重装全部环境。环境依赖只在目标确有需要时按适用计划处理，Hermes 不自动追随上游最新版。

| 入口 | 已确认的检查与更新范围 | 约束 |
| --- | --- | --- |
| 诺拉定时检查／更新提醒 | 仅适用于本实例的核心更新 | 只发布启动器时不提醒核心更新；不需要先探测用户电脑有没有桌面启动器 |
| 用户让诺拉更新 | 同一核心范围，交给独立更新器执行 | 不包含桌面启动器本体替换；沿用用户授权，检查或提醒本身不授权静默安装 |
| 启动器“检查更新／安装更新” | 核心更新及启动器自身更新 | 内容使用同一独立更新器；APP 使用已有本体替换机制。两者都有适用更新时，一次点击依次完成，结果按本节第 4 项分别核验 |

诺拉自主更新和启动器原按钮在执行核心更新时调用同一独立更新器，保留现有按钮和步骤。普通核心更新不以桌面启动器是否安装、打开、在线或版本较新为执行资格；真实安装、依赖、授权和资源校验仍然有效。启动器关闭、APP 已移除、安装记录残留是不同事实，但都不应成为核心版本提醒的先决判断。

**既有部署权限（2026-10-19 用户确认）：** 核心更新器不因文件或目录的所有者、组可写或其他用户可写权限位而额外拒绝更新，不自动修改部署权限，不增加用户组或 ACL 审查。实际读写仍服从操作系统权限；安装路径绑定、文件类型与符号链接检查、发布资源校验、维护互斥及失败恢复继续保留。这不是对共享主机上的其他系统账号提供隔离保证。

#### 1 更新的完整过程

| 阶段 | 更新器承担的责任 | 调用入口承担的责任 |
| --- | --- | --- |
| 提交并接管 | 核验授权、实例和目标，确认任务接管；同实例只有一个合法维护写者 | 传递请求；得到接管依据前不宣称任务已独立运行 |
| 查询、下载和准备 | 固定适用目标、获取并核验资源，准备恢复所需条件；保留当前可用安装 | 呈现同一任务的进度与错误，不另起第二套更新 |
| 停服与替换 | 准备通过后停止需替换的服务，确认离线，再修改受管程序 | 服从更新任务的服务管理，不并行停服或写配置 |
| 验证或恢复 | 检查目标及要求的运行结果；失败按真实修改恢复 | 不凭进度结束或重连成功推断更新成功 |
| 结束与再次使用 | 记录最终效果，完成必要恢复并释放维护占用 | 重连／重开读取同一结果；能按结果进入正常使用、重试或恢复 |

上表规定的是同一核心更新任务；桌面 APP 替换具有单独的程序交接和恢复责任。“两个入口共用核心更新器”与“桌面一次发起两项更新”分别成立，不要求两类程序处于同一个底层文件事务。

成功的依据包括目标正确、规定的运行验证通过、用户内容符合保护约定以及维护任务已经结束。数据保护的验收不要求日常查询或每次更新全量遍历、哈希所有聊天；具体检查依据由相应模块和场景确定。

#### 2 失败结果与下一步

| 已核验结果 | 可以告诉用户什么 | 下一步 |
| --- | --- | --- |
| 未替换原程序 | 本次未改动程序，并说明失败阶段 | 原程序经相应检查仍可使用时继续使用；修正条件后重试 |
| 已恢复并验证健康旧版 | 更新没有完成，旧版已恢复可用 | 继续使用旧版，或对原固定目标重试 |
| 文件已恢复，运行验证失败 | 程序文件恢复与服务可用是不同结果 | 处理具体运行阻断，再验证；不宣称旧版已正常 |
| 修改或恢复事实无法确认 | 明确未确认的效果，数据与证据保持原状 | 使用对应恢复／诊断路径；相冲突修改等待安全条件，不默认清空数据 |

重试保留原任务的真实失败和已确认目标；更换目标按新的目标重新准备与核验。原写者或恢复仍在工作时，读取到一条失败记录不代表任务已经结束。确认结束后，旧失败记录不应继续把后续合法操作锁住。

#### 3 关窗与调用方断开

| 场景 | 已确认行为 |
| --- | --- |
| 日常空闲关窗 | 按 PB-04 保留现有关闭行为，不新增统一停服动作 |
| 安装、模型保存、目录选择、更新或恢复期间请求退出 | 沿用现有等待保护，说明任务尚未结束；只提供当前阶段原本支持的取消动作，不新增“更新中主动关窗”功能 |
| 更新已接管，诺拉停止、调用方异常退出或连接中断 | 独立任务继续，随后可读同一终态；这不等于日常关窗按钮主动放行 |
| 维护结束后正常退出／重新打开 | 先确认任务不再占用，再按日常退出／查询规则操作 |

#### 4 桌面一次发起与部分完成

用户保留原来的检查和安装更新按钮。两项都有适用新版时，一次点击提交本次已确认的目标，依次完成核心更新与 APP 替换；需要重开 APP 时自动交接并续接结果，不要求用户再次查找、点击安装另一项。只有一项有变化时只执行该项；诺拉入口仍只处理核心。

执行前核验资源、实际安装及各阶段需要的兼容组合，固定本次两项目标和恢复依据。先核心还是先 APP 由适用协议和可恢复组合决定，不作为永久产品规则；不能只因某一顺序代码较短就跳过兼容校验。调用方退出后的续跑、维护互斥与原退出保护继续有效，受控 APP 重启不等于新增日常关窗放行。

| 两项执行结果 | 用户结果与后续 |
| --- | --- |
| 本次需要更新的项目均成功并通过验证 | 报告全部完成，显示实际核心及 APP 版本；任务结束后可正常使用 |
| 一项成功，另一项失败并已恢复，保留下来的程序组合有明确兼容依据且实际验证通过 | 保留成功部分，报告“部分完成”，说明失败项、实际版本和重试动作；不把部分完成报告为全部成功 |
| 失败后形成的组合不兼容或兼容性未知 | 不按兼容部分完成放行；使用已核验的恢复路径回到可用程序组合，保留用户数据；恢复未确认时明确受影响动作及原因 |
| 写者、替换效果或恢复仍未确认 | 保留任务和证据，查询同一结果或执行对应恢复；不凭单项成功解除尚存的危险修改 |

兼容部分完成结束后，重试只补失败项，并重新核验保留项和固定目标仍适用；不重复替换已经成功且仍有效的核心或 APP。兼容声明、当前文件身份、实际运行和恢复结束分别举证，版本号较新或进程能启动本身不足以证明组合兼容。两项协调复用既有任务与恢复事实，不另建一套相互矛盾的权威记录。

启动器程序、诺拉／酒馆内容和基础运行环境分别识别版本，按实际变化分别交付，内容更新不顺带强制重装全部环境。具体进程语言、交付目录和凭据格式由实现方案管理。

历史安装以保留数据迁至当前支持版本为目标；来源版本、入口与数据形态分别验收。旧二进制已经损坏的更新入口，不会因新版源码修改自动改变；救援工具、保留数据覆盖更换启动器和普通在线更新分别记录适用范围与结果，不凭几个旧版本推断全部兼容。

### PB-05 故事身份和内容归属

世界具有稳定身份，打开方式、临时进程和兼容引擎的头像／聊天文件名变化不改变其身份。资料库原件、世界运行副本和所属会话分别管理；修改一个世界不悄悄改动另一个世界或库原件。采用既有世界权威记录及隔离规则，不引入新的数据模型。

| 内容 | 普通更新、修复和保留数据重装的处理 |
| --- | --- |
| 聊天、角色、世界与会话、个人设置、模型凭据、记忆、Story Profile | 保留其内容、归属及适用身份，不以清空作为正常维护步骤 |
| 诺拉、酒馆和 MVU 模型配置 | 分用途管理；只按既有规则初始化空白酒馆，后续修改诺拉模型不覆盖已配置的酒馆模型 |
| 项目管理的规则、技能、Hook 与模板 | 按[受管文件规则](launcher-managed-files.md)更新；其中 AGENTS 全文受管，自定义人格、问候等各按已有策略处理 |
| 备份、恢复记录和诊断证据 | 按保护、保留和清理规则处理；维护成功不自动授权删除未知或受保护文件 |
| 缓存和可重建运行提示 | 按第三节及对应模块规则处理，不能借清理缓存修改用户内容 |

用户长期私人内容应放在受保护的位置，不引导用户写入会被整份替换的项目规则文件。故事档案和剧情账本按其用途管理，不把虚构故事经历直接当成现实个人事实。

### PB-08 两类备份职责与三种卸载选择

聊天滚动备份是辅助回退副本，失败、超时或容量不足时明确提醒；正常聊天保存及版本、归属、并发校验成功的合法操作仍可继续。不能把备份失败报告成聊天保存失败，也不能虚报备份成功。具体保留参数与删除边界见[聊天备份规则](verification/chat-backup-retention-safety-20261008.md)。

| 用户选择 | 删除与保留范围 | 执行前提与失败处理 |
| --- | --- | --- |

### PB-09 分发、验收和隐私

#### 1 版本、发布批次和更新提醒

发布必须能区分核心、桌面 APP 和必要环境的真实变化，不把“仓库有新 Release”直接当成每个实例都需要核心更新。已有核心版本和启动器版本不是同一个数值；源码仓库、发布批次、组件版本和完整安装器也不是同一个对象。

| 实际变化 | 诺拉的自动提醒／自主更新 | 桌面启动器的检查结果 |
| --- | --- | --- |
| 只有桌面 APP 改变，核心没有适用变化 | 不提醒或执行核心更新 | 提示自身更新，保留已有核心 |
| 只有核心有适用变化 | 提醒／按授权执行核心更新 | 提示核心更新，沿用现有 APP |
| 核心与 APP 都有适用变化 | 仅处理核心部分 | 一次点击依次完成两项；兼容部分完成及失败恢复按 PB-06 判断 |
| 没有适用变化 | 不制造更新提醒或安装动作 | 报告对应组件已是最新 |

无桌面 APP 的安装依照相同核心规则运行；不为了消除提醒错误新增全盘 APP 探测或引入桌面执行资格。实现、实测与正式渠道的状态见附录 A。

#### 2 按变化交付与正式发布

| 变化类别 | 交付与验证要求 |
| --- | --- |
| 核心变化 | 准备变化组件，验证适用安装和既有客户端兼容；原 APP／环境未变时不默认全量重建 |
| APP 变化 | 准备受影响平台的桌面产物与替换验收；不伪造核心变化，未变内容按证据复用 |

| 文档、测试或发布工具变化 | 核对实际产品输入是否变化；发布工具修正与已封存产品身份分别处理，不因传输重试重新打产品包 |

完整安装包用于首装，是否重新生成取决于实际输入变化和首装交付合同；既有用户的组件更新与新用户整包交付分别验收。不把避免重建当成跳过新依赖、程序变化或目标平台验证的理由。

国内用户的版本查询与完整下载应有实际可用渠道、来源切换、适用的断点续传及文件完整性核验。发布只交付与验收身份一致的资源；相同版本号、不同文件字节不能共用验收结论。具体主源供应商和上传工具在附录／发行方案维护，不进入长期产品规则。

#### 3 验收与隐私

验收围绕第二至五节的用户结果，按实际源码、资源、平台和入口记录：安装包能打开、服务健康、配置保存、外部模型可调用、配对成功、世界数据可读以及更新／恢复结果，各自的证据不能互相替代。测试数量和上传成功不作为用户能够使用的证明；一个局部任务只承担与本次改动直接相关的验收。

基础统计和详细诊断按既有[诊断协议](launcher-install-diagnostics.md)分别处理；详细诊断遵守用户选择及脱敏边界。故障诊断不包含聊天／世界正文、模型回复、Key 或配对码，不把私人内容放入公开分发资源。用户配置的模型调用本身会按用途发送必要内容给其选择的服务，此行为与故障上报分开说明。
