<a id="error-presentation"></a>
## 错误呈现与可执行动作

已知错误展示三部分：问题名称、当前影响、下一步建议。例如：

> 无法确认酒馆进程归属。
>
> 启动器没有接管或结束这个进程。
>
> 请保留当前进程和日志，勿按提示中的 PID 强行结束程序。

> 模型已验证，酒馆同步未完成。
>
> 配置已保存，尚需完成酒馆同步。
>
> 请选择“继续同步”，无需重新填写 API Key。

操作失败卡片把第一行作为标题，其余行作为说明；模型反馈和状态提示保留换行。退出停止失败对话框也使用同一套说明，原有选择不变。更新检查仍保留版本、可更新状态及阻止安装的兼容性要求，包括要求的最低启动器版本。

这些说明依赖固定业务错误码、系统错误码、HTTP 状态及来源，不从任意日志文字猜测根因。已知分类不代表已覆盖所有故障。未知错误显示“原因尚未确认”，保留安装和数据并引导查看日志；不会断言已回滚、权限不足或缺少依赖，也不建议反复卸载重装。

<a id="progress-and-download-wait"></a>
### 阶段进度与下载等待提示

安装与更新任务显示后台提供的当前步骤、本阶段耗时和整次操作耗时。下载显示实际已接收字节；总大小已知时显示百分比，总大小未知或本地解压、初始化、校验尚无精确进度时保留不定进度条，不编造百分比。补齐启动器自更新下载的阶段、字节进度和下载后校验事件；组件更新在等待响应头之前即记录初始下载进度。

仅在 `download` 阶段连续三分钟没有新增数据时，显示检查网络及确认代理工具覆盖启动器下载的建议，并说明先取消、待任务结束后再重试。心跳、普通日志和重复的相同字节数不掩盖停滞；收到新增下载数据后提示立即撤去。进入下一组件、校验或本地文件处理时清除上一下载的提示。已接收全部声明字节时不再以网络停滞引导用户。取消获接受后显示等待后台任务结束，迟到进度不覆盖取消状态。

该提醒不认定 GitHub、磁盘或安全软件是故障根因，不自动取消、重试或切换资源，不改变原有下载、校验、授权与失败上报行为。基础阶段和心跳中的 `progress_age_ms` 继续记录等待情况；等待提醒本身不记为失败。实际下载失败仍走既有错误及已授权的详细诊断上报。

### 错误分类与真实来源

<a id="technical-errors"></a>
18 类技术情况：

|证据类别|用户说明或建议|
|---|---|
|权限拒绝|检查所需文件访问权限及明确的安全软件拦截提示|
|文件或目录不存在|检查安装盘、目录及安装包完整性|
|磁盘空间不足|清理安装盘和系统临时目录所在磁盘|
|DNS 失败|核对网络、地址和代理|
|连接被拒绝|检查目标服务是否运行及地址、端口|
|连接中断|检查网络和代理后重试|
|TLS 证书错误|检查日期和证书，保留安全校验|
|超时|先确认当前运行状态，保留安装和备份|
|取消|确认状态后决定是否继续|
|HTTP 401|模型服务检查 Key；更新服务反馈访问问题，无需修改模型 Key|
|HTTP 403|模型服务检查账号及模型权限；更新服务检查访问限制|
|HTTP 429|稍后重试并检查服务配额|
|其他 HTTP 异常|服务异常；5xx 明确建议稍后重试|
|无法识别的响应|核对接口，持续异常时保留日志|
|空响应|核对接口和模型名称后重试|
|响应过大|核对接口，持续异常时保留日志|
|完整性或兼容性校验失败|使用对应系统的完整包，保留安装和数据|
|窗口意外退出|重新打开并确认后台任务和服务状态|

|固定码|用户说明或建议|
|---|---|

|`GATEWAY_IDENTITY`|无法确认 Nora 后台身份，没有启动第二个后台；重启后复核|

|`MODEL_SYNC_PENDING`|配置已保存，可继续酒馆同步，无需重填 Key|

<a id="status-unavailable-and-log-open"></a>
### 日志打开反馈与状态未知

- “查看日志”失败时，在原恢复页显示中文反馈并保留原始原因链、恢复说明、备份位置和按钮；成功只表示已请求系统打开文件，不证明文件已经对用户可见。
- 状态查询失败返回 `statusUnavailable`，不能合成“已停止”“离线”或“安装需修复”。首次安装缺运行环境时继续原安装探测；已有酒馆但缺查询所需 Python 时属于查询失败。
- Gateway、Windows 包装器子进程或状态写入者的进程信息被拒绝访问，也进入状态未知并保留 `EACCES` 原因链，不据此启动或结束进程。已确认不存在、PID 复用和重启前旧记录仍按原归属规则处理。
- 保留最后确认的安装信息，将当前服务标为“状态未知”并提示自动重新查询。暂时禁用服务控制、酒馆打开和 ClawChat 运行入口，保留更多与安装信息入口，不用旧快照自动启动或升级。
- 原五秒轮询不变，查询恢复后恢复日常状态与按钮；模型表单、未保存输入和恢复页内容不会因轮询异常清空。原实施及验证范围保留在[2026-10-01 记录](#history-status-feedback-20261001)。

<a id="local-logs"></a>
## 本地日志与原始证据

<a id="evidence-and-display"></a>
### 原始证据与展示分离

主进程在向界面转换说明前保留原始异常及原因链，已有本地诊断器负责脱敏、限制大小和日志轮转。错误说明不会改写原始 Error。Electron 的 `ipcMain.handle` 抛错只向界面传递 message，因此在该边界前完成分类。依据：[Electron 官方 IPC 文档](https://www.electronjs.org/docs/latest/api/ipc-main#ipcmainhandlechannel-listener)。

更新检查返回失败结果而没有抛错时，也先保存 `diagnosticError` 再转换提示。状态轮询的同一错误只记录一次；正常状态恢复后再次出现会重新记录，避免持续刷日志。旧界面接收到未转换的英文异常或堆栈时，使用保守中文提示，不把技术转储直接作为主说明。

### 自动诊断不足时提供本地日志

1. 安装失败后，先不要删除安装目录或反复卸载。
2. 在启动器的「更多」中找到现有的日志入口，打开日志文件。
3. 提供完整 `install.log` 文件；同目录如果存在 `install.log.1`、`install.log.2`，请一起提供，并说明安装包版本、失败时间和当时进行的操作。只截图最后一句错误通常不足以定位原因。
4. 可以附上同目录的 `state.json`。不要发送 `.env`、`config.yaml`、`auth.json`、密钥文件或配对文件。

通常日志位于 **实际安装数据目录** 下的 `installer/install.log`，不是启动器 EXE 所在目录。自选安装目录时，以实际选择的位置为准。

例如数据目录为 `D:\NoraTavern`，日志就是 `D:\NoraTavern\installer\install.log`。

### 窗口打不开，或者安装盘不可访问

启动异常和正常日志无法写入时，会尝试保存到独立的备用目录：

| 系统 | 备用日志 |
| --- | --- |
| Windows | `%APPDATA%\NoraTavern\diagnostics\install.log` |
| macOS | `~/Library/Application Support/NoraTavern/diagnostics/install.log` |
| Linux | `${XDG_CONFIG_HOME:-~/.config}/NoraTavern/diagnostics/install.log` |

Windows 用户可按 `Win + R`，输入 `%APPDATA%\NoraTavern\diagnostics`，回车打开文件夹。

如果正常目录和备用目录都有本次失败的记录，请同时提供两个文件。磁盘写满、系统强制结束进程、两个目录都无写权限等情况，仍可能造成日志不完整。

### 日志记录什么

- 每次操作的编号 `runId`、开始和结束时间、耗时、操作类型。
- 启动器版本、发布通道、操作系统版本和架构、Node/Electron 版本，以及 Python 实际路径和版本。
- 实际数据路径、Hermes 路径、酒馆路径、所选运行时包和校验值。
- 安装阶段、进度、启动命令、工作目录、进程编号、退出码、终止信号、是否超时或取消。
- 子进程提供的完整逐行输出，包括没有换行符的最后一行；界面错误摘要的长度限制不影响这些记录。Python 桥接器内合并的标准输出和错误输出标记为 `combined`。
- JavaScript 异常堆栈、底层错误码、系统调用、失败路径、嵌套原因；Python 异常调用链。
- 原始安装错误和后续回滚、清理错误。Node 安装器不会再用清理异常取代原始异常。

`install.log` 采用一行一条 JSON 的格式，便于关联阶段、筛选 `runId` 和还原异常。错误堆栈中的 `\n` 是换行符的 JSON 表示，并非省略内容。重试和重启继续追加日志，不会主动清空历史；超出保留容量时淘汰最早的记录。

### 容量与轮转

- 每份日志上限为 10 MiB（10 × 1024 × 1024 字节）。每个日志目录最多保留三份：当前的 `install.log`、上一份 `install.log.1`、更早的 `install.log.2`，合计不超过 30 MiB。
- 新记录即将超过上限时自动轮转，删除最旧一份。正常目录和备用目录使用同一规则，若两处都产生记录，合计最多约 60 MiB。
- 已有的超大旧日志在下一次写入轮转时保留最近的完整行，并写入 `log.history-trimmed` 标记。容量限制内的旧文本不改写。
- 单条记录超过 10 MiB 时，先脱敏，再分段写为 `log.fragment`。按相同 `id` 的 `index` 顺序拼接 `data`，进行 Base64 解码，即可还原原 JSON 记录；`total` 用于检查分段是否齐全。分段也受总保留容量约束，较早的分段可能被淘汰，因此出错后应及时收集三份文件。
- 轮转失败仍会尝试写入备用目录，不会用日志异常替换安装本身的错误。两处都无法写入时仍可能无法保存完整记录。

### 隐私与边界

日志对本次输入的 API Key、配对码，以及常见令牌、认证头、URL 查询值做脱敏；不记录输入 JSON、完整环境变量或配置文件。日志仍包含本机文件路径，公开发布前请检查用户名及第三方程序可能输出的其他私人信息。

日志只能保留程序实际提供的诊断信息。底层工具已经截断的输出、在进入启动器前已经乱码的文字，以及断电或强制结束前尚未输出的信息，不能从日志中恢复。

本地日志是尽力记录；磁盘不可写、强制退出或底层工具未提供内容时，可能没有完整证据。详细诊断与基础统计分别处理，授权及投递边界集中在[故障投递](#fault-delivery)，不因展示中文说明而扩大采集。

<a id="fault-delivery"></a>
## 故障投递与查询

当前设计：启动器上报 → Cloudflare Worker 接收 → D1 存储 → 开发者定时调用受鉴权保护的查询接口。不新增监控页面。本文说明当前源码；旧安装包不会自动获得新增诊断能力，需要发布包含改动的新启动器。

当前源码在详细诊断开启时，为失败或异常中断的启动器操作投递脱敏故障包及整次执行日志；正常成功操作不上传详细日志，日常服务、聊天和模型回复不在采集范围。整次日志与受限故障包是不同证据，不能把下文旧版本“只发限定故障包”的合同外推为全部版本的现行日志行为。客户端采集、服务端接收和特定安装包是否生效分别核验。

<a id="operation-evidence"></a>
<a id="待发布重构的故障证据"></a>
### 操作证据与故障包预算

安装、更新、恢复和配置变更共用持久操作编号。首次失败先冻结脱敏程序证据，再执行恢复；恢复、清理和重新启动失败作为次级原因追加，不能替换首因。重开窗口、CLI 和技能入口读取同一记录。恢复成功仍保留原安装错误，但恢复请求的结果根据实际恢复验证判定。

本地证据位于 `<NoraHome>/installer/operations/<operationId>/evidence`，仅接收经过审核的程序异常投影，不读取整份服务日志、配置或聊天。JavaScript 和 Python 使用同一份受封存的 `operation-budget.json`：单份 JavaScript 证据预算 256 KiB，Python 证据文件预算 64 KiB；正式证据文件 `metadata.json`、`events.jsonl`、`python.json` 的总保留容量为 50,315,264 字节。另为最多 4100 条操作各预留 4096 字节的独立 `delivery.json`，证据和投递确认合计上限为 64 MiB。正式证据的写入受同一维护锁约束，迟到投递确认只更新独立文件，不改写首次错误。此上限不包含原子写入临时文件、事务记录、发布清单原文或恢复备份。超过预算或保存失败会记录缺失原因，不能用诊断错误覆盖原始操作错误。

最多保留 256 份完整操作详情，安全终态详情最长保留 30 天。达到容量时，可提前压缩最旧的安全终态详情；保留至多 4096 条轻量操作事实及额外停止操作空间，原操作编号、目标摘要、条件摘要和累计尝试次数不会因压缩而清零。未完成事务、未核实进程、待确认投递、恢复依据和备份不能作为普通日志删除。清理失败作为次级诊断保留；仅当可安全回收的记录不足时阻止新的普通变更，停止和原操作恢复仍有入口。

故障包使用 `fault.schema=2`，在原脱敏原因链、源码位置和环境之外，携带原操作编号、快照序号、当前及目标版本、固定计划摘要、首次失败阶段、实际变更状态、恢复结果、验证状态与尝试次数。`evidence.missing_reasons` 明示信息缺口；`truncated` 明示裁剪。包仍限制在 24 KiB 内，不声称上传了完整原始日志。

基础事件仍始终上报；详细诊断默认开启并保留已有主动关闭选择。详情关闭时基础阶段和最终结果继续投递。待报队列按操作轮转，部分 ACK 仅移除已确认事件；队列为空不能单独证明服务端入库。必须查询相同操作编号，确认实际首次入库字段和时间线。启动器中没有接收端读密钥。

### 独立APP更新诊断补报（2026-11-02实施记录）

独立替换／恢复助手将首因冻结在原操作的`evidence/python.json`，同时保存失败检查点。GUI遥测在交接时将原操作编号和当时的诊断授权留在既有`telemetry.json`，重开或新的界面操作不丢弃这项待补诊断。只读助手核对原操作、封存计划、当前APP归属及执行者身份，读取有界证据；不会执行恢复、终结业务任务或改动程序。已知异常的`interrupted`保留技术错误码；没有原始异常时明确缺失，不按正常完成处理。

补报使用现有故障包、日志队列和精确ACK；断网或ACK丢失后沿用原事件身份重试。读取暂时失败时先报告证据缺口并保留待补查项，避免每次刷新重复报同一个缺口；恢复可读后继续补查，保留期按现有日志投递的七天限制。队列最多64项；未补查的操作证据不能因基础事件已送达而提前归档。授权关闭或撤回后的旧交接只提供基础技术结果，不补采详细错误；之后重新开启不为旧操作增加授权。

故障包在现有`output`中保留受限的`launcher_step`／`launcher_status`、程序效果、恢复结果和验证状态；文件对象使用固定角色，如`launcher-app -> launcher-backup`，不发送绝对目录、用户名或任意数据文件名。旧记录没有具体失败检查点时明确标为未知。当前源码不采集占用者，不保证所有崩溃均能还原原始异常；记录损坏、权限或磁盘故障会明确缺失。相关范围和实际验收见[本次任务](launcher-reliability-plan.md#detached-update-diagnostics-20261102)。这项诊断修复不等于解决文件占用、更新恢复业务或已部署到用户机器。

### 既有版本诊断合同（v2.4.0 / 启动器 2.0.0）

本小节保留该版本的限定故障包接口、授权及查询合同；其中的版本特定采集限制不替代上面的整次失败日志说明。实施和部署结果统一保留在[历史交付记录](#diagnostic-delivery-history)。

本地 `install.log` 仍保留详细诊断。自动诊断不读取或上传整份日志；详细诊断开关开启时，从实际启动器操作和限定安装子进程中生成脱敏故障包。

- 正式打包启动器始终自动上报基础操作阶段、耗时、运行状态和白名单技术错误码，不受详细诊断开关控制。按 2026-10-02 用户确认的新要求，「自动发送详细故障诊断」采用紧凑勾选框；新诊断选择默认开启，已有 v3 主动关闭选择保留。开启时，新操作报错会持续自动发送脱敏故障包，不逐次弹窗或要求用户手动提供日志。开发、Beta、普通本地候选包不采集；使用 `--candidate-telemetry` 的隔离接收端测试包允许采集。旧版状态迁移时清除未授权的待报故障包，并为尚无当前诊断选择的环境应用新默认值，不给已经开始的操作补采详细证据。
- 基础统计与详细诊断仍是独立行为；首页只保留紧凑开关及「仅上报脱敏程序错误，不收集聊天内容、模型回复或密钥。」这一短说明。保存中与保存失败使用独立状态区域，不覆盖说明；失败恢复已保存值，成功清除旧错误提示。关闭详细诊断时立即取消当前上传、清除待报事件中的故障包；事件编号、阶段记录、进行中的操作及最终结果保留，基础统计继续上传。不能撤回已经接收的数据。重新开启不会补采关闭期间的详细证据，也不为已经开始的操作追加详细授权；旧异步操作仍上报基础结果。
- 本地 `<NoraHome>/installer/telemetry.json` 保存随机安装标识、序号、详细诊断开关及有界待报队列。安装目录变更时迁移这份状态；不取机器码、账号或用户名作为标识。
- 向 `https://noratavern.com/api/launcher/events` 发送阶段、耗时、产品及启动器版本、系统和架构、白名单错误码。只采集启动器负责的安装、更新、模型连接配置、进程启停和界面操作；不采集酒馆聊天、MVU、插件或 Hermes 内部运行日志。
- 当前 v3 事件包含固定来源和发生位置、系统错误码、HTTP 状态码、子进程退出码和信号、异常类型及请求尝试次数。详细诊断开启时，故障事件额外附带经过独立筛选和脱敏的错误文本、源文件调用位置、原因链、技术系统调用、阶段经过、系统及 Node/Electron 版本和启动器文件指纹。绝对目录、用户名、URL、已知密钥及配对码被隐藏；不发送聊天、配置全文、模型回复、供应商响应正文或 Hermes 日常内部日志。未知错误仍保留 `unknown`，同时保留可用于定位的安全错误详情，不解析中文文字猜原因。
- 服务启停、重启、配对及状态检查的程序异常由桥接器输出独立结构化诊断，保留异常类型、源码位置和原因链。服务模式只接受桥接器自身的诊断标记；子进程不能冒用该标记，原始服务输出不进入故障包。配置解析器、子进程命令和外部请求异常使用固定技术摘要，不复制配置行或响应正文；停止过程的主错误与次级错误在有界预算内保留，状态查询不覆盖停止失败。安装/更新仍可保留限定的脱敏工具输出。此改动兼容现有接收端协议；需要发布新的启动器后才会在用户端生效，过去已经丢失的远端原因链无法补回。
- 示例：检查更新收到 HTTP 403，记录 `release_service / release.request / http_forbidden / 403`，不再与配置模型被拒绝混在一起。文件不存在记录 `file_not_found / ENOENT`，不直接认定为缺少依赖。
- 接收端在 `nora-landing` 仓库中，独立 D1 表 `launcher_events`，安装标识经服务端 HMAC 后保存。公开采集接口不使用统计查询密钥，客户端不含该密钥。
- 安装成功只表示安装验证通过；首次实际可用要求安装完整、酒馆和 Gateway 已运行、ClawChat 已连接。新环境和既有环境分组，不把老用户升级计作新安装。
- 模型测试、模型保存、连接配对、运行时释放/初始化/校验、组件下载/校验、服务启动和更新事务分别标记阶段。更新事务内部未提供稳定阶段标识的步骤仍显示 `update_apply`，不解析中文日志猜测子阶段。
- 有任务时每30秒记录心跳。超过5分钟的阶段标记慢；当前下载提示在实际下载连续3分钟没有有效字节进展时显示，不将本地解压或拷贝的安静期判为网络故障。超过2分钟无新心跳为失去联系，不等于崩溃。等待模型、配对或启动单独列为等待用户。
- 一次最多20条且序列化后不超过60,000字节、每次上传10秒超时，退避最多5分钟；待报队列最多500条、最长7天、序列化后最多1 MiB，先淘汰心跳。持久化失败只停用统计，不中断安装。服务器停收后清除队列并暂停一小时。上传失败只在本地记为延迟，不递归生成上报故障。
- 用 `event_id` 和安装序号去重，迟到事件不能倒退最新状态。启动器重启将未完成任务记为中断；启动器自更新交接保留任务编号，不能视为成功更新。
- `install.log` 中的 `telemetry.operation.operationId` 可用于受保护的查询接口追踪单次任务。网络重试错误保留在 `errors` 中，用 `operation_outcome` 关联最终结果；只有最终失败的操作计入 `failed_operations`。中途错误不替换任务状态，取消也不计作失败。没有最终结果时，不能推断已经恢复或必然失败。
- 检查更新和读取模型列表使用独立操作编号，不抢占正在安装的任务记录。关闭再开启详细诊断后，关闭前尚未完成的异步检查继续上报基础终态，不补报详细故障包。
- 这里只提供可关联的去标识化诊断，不是完全不可关联的匿名数据。安装标识与操作编号用于去重和串联同一环境的故障，不代表用户真实身份。

#### 仍然存在的诊断边界

- 本轮待发布源码统一使用公共异常投影，并补齐酒馆 CLI 到桥接器的可信诊断传递。日常启动失败保留限定的 Node 错误码、源码位置和原因链，仍不上传服务原始输出。投影阶段发生裁剪也会传递到故障包的 `truncated` 标志；正式包发布前，旧客户端仍使用原逻辑。
- 故障包是限定范围内的脱敏证据：最多四个错误节点、每个十二条调用位置、十二条安装/更新输出和十六条阶段记录；最多 24 KiB，超限标记 `truncated` 并裁剪。它不是完整原始日志；超出范围或第三方工具未提供的信息仍可能需要补充。
- 遥测初始化前的错误只能尝试写本地日志。断电、进程被强杀或磁盘不可写可能没有完整记录；捕获到主进程异常也只尽力入队，不能保证退出前上传。
- 不监控用户在酒馆中调用的模型；模型错误指的是用户在启动器中执行模型列表获取或连接测试的错误。
- 独立窗口故障及退出停止失败可以单独上报，但没有对应终结事件时，其 `operation_outcome` 为 null，不能视作整次安装失败。

#### 开发者定时查询

接收和查询接口复用落地页仓库的 Cloudflare Worker、D1 表 `launcher_events` 和现有读密钥。开发者从自己的受信任脚本或服务定时请求 `/api/launcher/stats`，不需要新增管理页面。读密钥不进入启动器、公开网页、日志或版本库。

- 常规查询返回失败分布、阶段耗时、主流程最新状态 `current` 和各操作状态 `operations`。
- `errors[].fault` 返回已授权上传的脱敏故障详情；`operation_outcome` 关联该次操作的最终结果。中途重试错误不等于最终失败。
- 按 `operation_id` 查询 `timeline`，用 `next_offset` 继续取后续记录；`timeline[].fault` 保留同一操作的故障证据。
- `issues` 按故障指纹聚合受影响操作数和安装环境数。
- 首次安装漏斗查询复用既有事件，其接口、观察窗口和当前交付状态由落地页仓库 `docs/launcher-funnel.md` 维护。接口权限及响应字段由该仓库 `docs/analytics-api.md` 维护，本文不重复定义。

采集失败、磁盘不可写或上传失败不改变启动器操作结果。这里的数据是客户端自报的安装环境样本，不是实名人数；断网、停收、队列淘汰或客户端未启动会导致缺失。服务端数据保留期限尚未确定，当前没有服务端自动清理任务；本地操作证据采用上文的有界保留规则。

### 原日志增强阶段的交付边界

### Windows 系统 tar 缺失时的 ZIP 释放

Hermes 的 Windows 发布归档为 ZIP。优先调用系统目录中的 tar；仅在该程序启动返回 `ENOENT` 时，用系统目录的 Windows PowerShell 和 .NET ZIP API 解压同一份已通过 SHA-256 校验的归档。文件路径通过独立环境变量传入，不插入脚本文本，也不执行 PATH 中的未知解压器。回退在安装临时目录中进行，检查 ZIP 条目不越出目标目录，不接受符号链接；保留原有校验、旧目录备份与失败回滚。

原工具的权限错误、超时或归档损坏直接报告，不换工具重试。回退也失败时保留两次错误；两个系统工具均不能启动时提供专用中文提示。该段实施时的验证范围仅为开发机隔离模拟缺少 tar；当时尚未执行受影响 Windows 实机首次安装，也未替换运行中的应用或发布。后续制品验收及交付状态按对应记录另查。

### 待发布 2.1.0：模型配置输出与原生崩溃证据

模型配置助手的标准错误和非协议标准输出按行写入同一操作日志，保留空行、缩进、异常原因链与调用位置。Python 助手将异常链输出到标准错误；标准输出中的配置 JSON 只供执行结果使用，不写入日志。每次助手调用记录开始、退出码、终止信号、耗时、超时及输出读取失败。4000 字符限制只用于界面错误摘要，不再限制保存的执行日志。重开后由现有操作日志读取、脱敏和分片上传，不增加另一套日志或上传接口。

启动器在创建窗口与 Electron Node 维护进程前启用本地 Crashpad，使用 [Electron 38 的本地采集模式](https://github.com/electron/electron/blob/v38.0.0/docs/api/crash-reporter.md)。转储保存在当前启动器数据目录的 `launcher/diagnostics/native-crashes`，按最新十份、单份64 MiB、总计128 MiB限制保留，在启动与后台采集时清理超限转储。只遍历该专用目录，不读取系统崩溃目录或其他应用数据。已有转储按检查点去重；主进程崩溃后重开会补录，存活主进程每30秒检查其维护进程的新转储。

自动上报只提取异常码、线程编号、崩溃时间和可识别的模块及指令偏移；窗口/子进程退出还记录实际原因与退出码。原始二进制转储、栈内存、环境、命令行和转储注释不上传。转储缺少异常流、损坏、超大或无法读取会明确标记缺失；模块偏移不是完整的函数调用栈，完整原生调用栈需要匹配符号进一步解析。该采集覆盖 Electron 主进程、渲染进程及 Electron-as-Node 维护进程；不宣称覆盖独立 Python/Node 服务的所有原生崩溃、断电或系统强杀。

本轮已在 Mac 的独立 Electron 38.8.6 夹具中触发三类真实原生崩溃并验证重开读取、位置提取和去重；故障及日志投递沿用现有授权开关，关闭时不发送详细证据。Windows 原生转储实机验证及正式发布仍待执行，现有安装包不会自动获得这些改动。

### 已知问题：Windows 启动诺拉时只显示 `(pid=...)`

用户提供的 2026-09-29 诊断显示：启动诺拉时，`launcher_services.start_gateway` 从 `gateway_state.json` 取出 PID，再读取命令行；Windows 拒绝访问，`psutil.AccessDenied` 未被处理，桥接器只返回 `(pid=5560)`。日志能证明这条异常路径，不能证明该 PID 当时属于哪个程序，也不能仅凭权限拒绝判定记录过期。Gateway 日志中的模型、会话和工具错误不用于推断这次启动前的进程身份。

修复将状态中的 PID 作为发现线索：Windows 重启前的状态、重启前的受管进程记录，以及文件写入之后才创建的新 PID，不再被认作旧进程。时间证据明确时继续正常启动；证据不足且进程信息不可读时，保留记录、禁止重复启动，显示「无法确认安装记录中的后台进程是否属于诺拉」及重启后重试的说明。识别为其他方式启动的 Gateway 时仍拒绝接管，不结束其进程。修复不重命名或删除原状态文件；新启动的 Gateway 按正常流程写自己的状态。

该已知拒绝访问错误通过桥接器传递固定技术码 `EACCES`。错误说明优先于随后到达的标准错误输出，用户主提示不会重新变成 PID 或 traceback；完整异常类型、原因链及输出仍保存在本地日志。

旧启动器尚未发布修复时，重启后仅重命名 `gateway_state.json` 并保留不覆盖的备份仍是临时办法。不要删除整个数据目录，也不要按这个 PID 强行结束进程；它不是聊天、世界、模型配置或密钥文件。源码修复并不代表用户机器已经恢复，新启动器仍需 Windows 打包实机验证后发布。

2026-09-30 隔离验证：服务归属、启动复核与桥接异常协议 43 项通过；主进程诊断与退出流程 24 项通过。回归先复现原 `AccessDenied` 和错误说明被迟到 stderr 覆盖，再验证过期 PID 不阻塞受管测试子进程、当前或未知记录仍禁止重复启动、不会向提示 PID 发送信号、原因链与 `EACCES` 保留。测试在开发机执行，Windows 权限拒绝和重启时间由隔离夹具模拟，没有操作用户安装、替换托管运行文件或发布启动器。

### 已知问题：Hermes 重启后启动器丢失后台归属

2026-10-02 本机日志证据：00:01:40 的 Gateway 在 00:04:30 退出，退出码为 75；同一安装随后启动带 `--replace` 的新 PID。10:29、12:57 更新之前已有「其他方式启动的 Hermes」错误，更新后的错误相同。可以确认进程发生过交接，不能只凭退出码确定触发重启的操作；现场没有文件删除审计，不能确定 `installer/gateway.json` 丢失的确切时间。

旧实现只识别初次启动的 PID、出生时间与参数。后台重启后，状态查询会误报离线；停止路径未找到后继进程却删除归属记录，更新也会按错误的停止状态恢复。隔离测试可完整复现该链条。

修复为新启动的 Gateway 添加仅保存在本机的归属凭据，Hermes 自重启继承该凭据。状态、启动、停止共用后继识别：凭据、安装目录、可信解释器、Hermes PID 与状态文件、出生指纹及限定重启命令必须一致。状态查询不写记录；启动可原子刷新已经核实的后继记录。无法读取身份或出现未知活进程时，停止保留记录并报错；更新预检查也会拒绝继续，避免假停服。Windows venv 包装器与实际 Python writer 分开检查，Linux 使用进程启动 ticks，Mac/Windows 使用出生时间厘秒。

旧记录继续支持精确 PID 识别；没有新凭据的孤立后台不会自动认领。本机恢复需明确授权，并交叉核实实例绑定、用户、解释器、目录、活进程出生时间与 Hermes 状态后重建记录。随后通过修复后的启动器正常重启一次，才具备自重启后的归属延续能力。该修复不改模型、配对、世界或聊天数据。

### 已知问题：正常运行的 Node 酒馆被旧归属记录挡住
