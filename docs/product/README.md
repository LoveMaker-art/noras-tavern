# 诺拉酒馆产品设计文档

整理日期：2026-10-19。用途：让产品负责人和开发者能查明产品为谁服务、应该怎样工作、需求怎样验收，以及设计如何变更和归档。

这套文档整理当前已确认的产品，不重新设计界面或新增功能。[产品设计基线](../product-baseline.md)仍是唯一的当前产品规则来源；本目录的需求说明是按用户目标组织的阅读视图，归档保存当时的设计结论。实现和上线情况由带日期的验收与发行记录证明。

## 一 从哪里开始

| 要回答的问题 | 对应文档 | 作用 |
| --- | --- | --- |
| 产品给谁用，解决什么问题，包含什么 | [产品需求说明](requirements.md) | 产品定位、使用形态、功能范围和用户流程 |
| 当前哪些规则已经确定，哪些取消或仍未决定 | [产品设计基线](../product-baseline.md) | 唯一现行规则、模块责任和设计选择；附录只索引实施证据 |
| 每项功能做到什么才算满足需求 | [功能要求与验收标准](requirements.md#四-功能要求与验收标准) | 用户结果和验收依据；不是测试通过记录 |
| 想改需求时，应先说清楚什么 | [需求变更模板](change-request-template.md) | 前后行为、影响、保留范围、验收及决策记录 |
| 当前更新与发布遵循什么规则 | [产品设计基线](../product-baseline.md)的 PB-06／PB-09 | 更新入口、组件范围、失败结果与按变化交付的现行约定 |
| 某个日期确认过什么设计 | [更新发布设计归档](archive/20261019-update-release-design.md) | 2026-10-19 的设计快照及当时的证据入口 |
| 实际代码怎样实现，如何执行发布 | [仓库职责](../REPOSITORY.md)、[开发约定](../../CONTRIBUTING.md)、[发布流程](../release-process.md) | 技术实现和操作步骤，不独立改变产品规则 |
| 某版本实际验证、交付了什么 | [基线附录的证据索引](../product-baseline.md)及对应修复／发行报告 | 按日期、源码、制品和环境区分已实现、已验收与已发布 |

产品负责人可先读需求说明，再按问题进入基线的对应条款。开发者开始改动前仍须按项目 AGENTS 读取基线，不能只读摘要或归档。

日常使用顺序：**开发前找到适用规则 → 判断是修正实现还是改变设计 → 按用户结果验收并记录实际状态。** 产品负责人确认行为和取舍；开发者负责提出实现与证据，不能反过来让既有代码决定产品应怎样工作。

## 三 文档状态和归档

| 状态 | 含义 | 后续如何处理 |
| --- | --- | --- |
| 待讨论 | 新建议或尚未确认的选择 | 明示假设与取舍，不能当成实施授权 |
| 已确认设计 | 用户已确认的产品行为 | 写入现行基线，关联需求及验收标准；实施另按授权执行 |
| 设计归档 | 保存某日期已确认的设计版本 | 作为历史依据保留，后续变更建立新记录；当前规则仍查基线 |
| 实施与验收记录 | 某份源码、制品和环境上的实际结果 | 引用证据和限制，不以设计已确认推断已验证或已发布 |

已归档设计：[更新与发布产品设计，2026-10-19](archive/20261019-update-release-design.md)。本文只登记归档身份，不在此跟踪后续开发进度；实现、验收和发行查对应报告。

当前产品功能、平台支持和历史版本兼容结论沿用对应证据。本次没有重新验收全部产品，不用“文档覆盖齐全”代表全部实现已经通过。

## 四 后续维护方法

新增或改变产品行为时，先用[需求变更模板](change-request-template.md)在既有任务记录中说明结果和范围，再按基线第七节评审、确认、实施和验收。修正代码以满足已确认行为时，在修复报告登记问题、规则、改动、实际验证和未验范围；不为每个 Bug 新增产品规则或设计归档。

已确认规则只改基线一处，随后同步需求说明和入口；设计归档保留原结论，新增设计版本指向后继方案。技术方案、运行手册、验收报告分别维护各自内容。只有链接、标题或分类整理的文档任务不触发产品打包发布。

最近的[文档整理记录](../reports/20261019-product-documentation-review.md)说明本次清理范围及两项修复的登记依据，不构成另一份产品设计。
