## 二 产品目标与组成

<a id="pb-01"></a>
### 用户目标与取舍（PB-01）

主要用户是普通角色扮演玩家。核心结果是：能够创建故事、与角色互动、保存进展，并在下次继续同一个故事；诺拉可以陪伴用户并按授权协助管理这些内容。

默认流程通过现有界面完成安装、配置、使用和维护，进阶能力可选。普通用户不需要理解部署脚本、进程或事务目录。发生故障时，产品应说明影响和可执行动作；手工删除记录、清空数据不作为日常维护步骤。

发生取舍时，先保护用户内容和本实例的操作边界，再完成维护目标；对已经证实可以安全使用的部分保持可用。复杂扩展、自主运维和上游组件升级均服从这个默认体验。恢复能力受实际文件和备份条件限制，不承诺磁盘损坏或数据与备份同时丢失后必然恢复。

<a id="pb-02"></a>
### 产品组成与使用形态（PB-02）

酒馆是进行角色扮演和保存世界的应用；诺拉是运行于 Hermes 的智能体；启动器是桌面安装与管理客户端。三者在同一项目协作，职责按用户结果划分，源码所在仓库不决定它们是否必须一起更新。

| 对象 | 负责什么 | 与其他部分的边界 |
| --- | --- | --- |
| 诺拉 | 与用户对话，按授权协助管理世界、角色、记忆及应用，检查并请求本机适用更新 | 桌面版一次交给现有双更新流程，核心与APP分别由原执行器完成；无桌面APP的源码／云端仍使用独立核心更新器 |
| 酒馆 | 角色扮演界面、世界和会话的持久业务、故事运行与数据保存 | 提供界面和 MCP 共用的业务结果；世界身份和用户内容不归启动器窗口所有 |
| 桌面启动器 | 安装、配置、启停、日志与维护结果呈现；检查核心及自身更新，执行自身替换 | 保留原控制和操作入口；内容维护交给同一独立更新器，桌面 APP 不成为核心更新前提 |

ClawChat 是当前配对和对话平台，Hermes 承载诺拉，MCP 连接酒馆业务，独立更新器执行核心维护。它们的交接责任见[模块交接](#module-handoffs)。

| 使用形态 | 用户获得的能力 | 首次入口与边界 |
| --- | --- | --- |
| 完整版：诺拉＋酒馆 | 酒馆游玩、与诺拉对话及其应用管理能力 | 桌面整合包走[启动器首次设置](launcher.md#first-use)；已有源码／服务器部署按各自安装文档进入，不因没有桌面 APP 失去普通内容更新资格 |
| 单独酒馆 | 世界、角色和故事游玩 | 按酒馆独立安装文档设置；不包含诺拉的管理能力 |

完整版首次要求配置诺拉并配对，是已确认的产品选择。单独酒馆的存在不改变这个选择；两种形态遵守相同的数据保护要求。支持的安装包平台、来源和历史版本范围由对应发行及验收记录说明，不由形态名称推断。

“云端／本地”是部署场景，“完整版／单独酒馆”是使用形态。没有桌面启动器的云端也可以包含诺拉和酒馆；适用维护范围根据实际安装确定，不用操作系统或桌面窗口代替判断。完整安装包是给新用户组合交付程序和必要环境的产物，不是另一套世界数据或强制所有安装追随的核心版本。

## 三 模块交接与支撑能力

每项结果由执行该业务的模块给出依据，调用入口负责如实展示。下表明确交接责任，不另外建立业务实现或新增用户入口。

| 模块 | 本模块负责的结果 | 对接边界与结果责任 |
| --- | --- | --- |
| 酒馆与 World Core | 世界、会话、角色和故事的业务操作与持久保存 | 向界面及 MCP 提供同一业务结果；库原件、世界副本与会话的归属在这里判断 |
| 诺拉 | 对话及按用户授权提出管理请求 | 桌面维护请求交给现有双更新入口，无APP部署使用独立核心入口；不自行替换APP，不另行维护一套世界或更新真相 |
| Hermes 及基础环境 | 诺拉模型执行与网关运行 | 生命周期模块确认实例、进程和服务结果；上游更新不自动改变产品规则 |
| Nora MCP | 将授权操作连接到酒馆能力 | 校验实例和目标，复用酒馆后端；不承诺任意命令工具或操作系统沙箱 |
| 故事档案与剧情账本 | 偏好、故事档案及适用的长期故事辅助 | 与酒馆共享适用业务和数据边界，不以一次模型回复代替保存结果 |
| 启动器与生命周期管理 | 桌面首次设置、日常管理及核心／APP 更新入口 | 收集相应后端证据推进页面；APP 本体由既有替换机制核验交接，实际停服未确认不宣称停服完成 |
| 独立更新器与恢复 | 整条内容更新／恢复的最终结果，包括资源、程序替换、运行验证及约定的数据保护校验 | 统一提供给诺拉和按钮读取；只有真实写者及恢复结束后解除维护占用 |
| ClawChat／Liveware 公共集成 | 配对、连接、身份核验、应用入口注册与验证 | 配对成功、本地健康和外部入口可达分别举证；不以历史地址充当当前有效入口 |
| 分发与故障接收 | 可信资源、版本查询和脱敏诊断接收 | 向更新器提供可核验资源；接收端确认的是日志送达，业务终态仍由执行端确认 |
| 卸载与历史救援 | 按已确认范围停止、保留、删除或修复 | 使用相应实例、进程与恢复规则；救援工具按验收范围使用，不变成普通用户每次更新的必经步骤 |

源码归属、共用业务与实现接口继续由[仓库导航](../REPOSITORY.md)和[共享逻辑边界](../launcher-shared-logic.md)维护。

<a id="data-and-models"></a>
## 四 共同数据、模型与备份规则

### 内容保护（PB-05）

| 内容 | 普通更新、修复和保留数据重装的处理 |
| --- | --- |
| 聊天、角色、世界与会话、个人设置、模型凭据、记忆、Story Profile | 保留其内容、归属及适用身份，不以清空作为正常维护步骤 |
| 诺拉、酒馆和 MVU 模型配置 | 分用途管理；只按既有规则初始化空白酒馆，后续修改诺拉模型不覆盖已配置的酒馆模型 |
| 项目管理的规则、技能、Hook 与模板 | 按[受管文件规则](../launcher-managed-files.md)更新；其中 AGENTS 全文受管，自定义人格、问候等各按已有策略处理 |
| 备份、恢复记录和诊断证据 | 按保护、保留和清理规则处理；维护成功不自动授权删除未知或受保护文件 |
| 缓存和可重建运行提示 | 按[状态与重试](#state-and-retry)及对应模块规则处理，不能借清理缓存修改用户内容 |

用户长期私人内容应放在受保护的位置，不引导用户写入会被整份替换的项目规则文件。故事档案和剧情账本按其用途管理，不把虚构故事经历直接当成现实个人事实。

世界身份和内容隔离的细则只在[酒馆设计](tavern.md#world-and-library)维护；首次模型表单由启动器负责，各用途模型执行结果由对应模块负责。

### 两类备份职责（PB-08）

聊天滚动备份是辅助回退副本，失败、超时或容量不足时明确提醒；正常聊天保存及版本、归属、并发校验成功的合法操作仍可继续。不能把备份失败报告成聊天保存失败，也不能虚报备份成功。具体保留参数与删除边界见[聊天备份规则](../verification/chat-backup-retention-safety-20261008.md)。

程序替换前所需的恢复准备是维护前提。其来源、归属或完整性无法核验时，暂不覆盖现有程序；该限制与聊天辅助备份分别判断。

卸载的删除范围和保留数据重装由[启动器设计](launcher.md#uninstall)维护。诺拉经接口操作内容时也遵守上述数据与备份边界。

### 配置修改的恢复职责

配置保护由实际写入入口承担，设计和结果须明确是持久备份、普通异常回滚，还是尚未确认恢复，不能统称“已经备份／保证恢复”。[本地诺拉模型配置](nora.md#model-configuration)沿用其现有专用合同；其他获授权的手工配置修改仍先备份，程序替换仍满足上文的恢复准备条件。智能体不额外复制专用工具未要求的凭据文件，也不以模型配置的内存恢复替代程序维护事务备份。增加断电／崩溃恢复或变更备份留存属于另行明确范围的实现工作，不能靠改说明文字声称已有。

<a id="model-use-and-cost"></a>
### 模型调用、内容发送与费用

**沿用的边界：**只读查询、查看已存内容及操作状态不授权发起生成、学习或整理。保存成功、连通性检查、真实生成成功和费用是不同事实；第三方调用是否收费由实际服务及用户账户决定，不宣称免费、不编造价格。必要上下文只发送至该用途实际配置的模型服务，不把此授权扩大为故障日志上传或其他用途。

以下为**已确认设计T-Q03**，批准依据见[四项决策](#tavern-policy-decisions)。设计已获批；本轮独立分支的代码、隔离业务验收及未验范围见[三项实施记录](../reports/20261020-tavern-design-coverage.md#import-model-consent-fix)。

| 调用类型 | 用户授权与反馈要求 | 范围变化时如何处理 |
| --- | --- | --- |
| 用户主动发送、重生成、生成新候选、智能回复、手动整理或复盘 | 沿用原动作名称和处理流程，主动操作授权本次用途，普通每轮聊天不额外弹费用确认；不加回已撤回的说明或候选改名 | 不把一个按钮扩大为另一个未授权用途；“填写草稿”和“发送／生成”分开 |
| 额外MVU模型、账本自动整理等附随能力 | 通过原设置开关记录本用途选择，之后按选择运行；MVU保留原直接开关，账本保留原启用确认，不新增说明或确认弹窗 | 新用途、新默认开关或扩大内容发送范围时再确认；已有同范围选择保留，不能擅自重置模型、变量、账本或聊天 |
| 额外MVU／账本的旧安装没有对应选择 | 保留原设置和数据，暂停该项新的额外请求，由用户在原设置位置决定是否开启；不把历史默认开启直接视为明确选择 | 基础世界／故事及基础MVU仍可用，不虚报额外能力已启用，不加回已撤回说明 |
| 后台Story Profile偏好复盘 | 按用户最新确认的[N-Q01自动复盘规则](nora.md#automatic-reflection-policy)默认开启，设置保留用途／费用说明和关闭入口；已有明确关闭保留 | 不把默认策略记作用户主动同意；不扩大到MVU、账本或其他用途，读档案／状态本身不触发生成 |

一次用户动作可能包含正文、已启用的变量更新或上下文整理等多次请求，不能宣传为一次API调用或固定金额。只呈现有可靠来源的模型用途、执行结果及实际返回的用量；本轮不设计价格抓取、精确预算、计费账户或新增用量仪表盘，也不把没有用量回执当作未计费。

取消和超时不保证服务商未处理或未计费。优先续查原任务或补保存；不因页面重连、状态刷新或读不到结果而另起未批准的生成。用户明确重试可能再次调用模型时，应说明这一事实；本地内容已生成但保存失败遵守[只补保存](tavern.md#save-and-retry)规则。

验收要求：纯列表／既有内容／状态读取不产生新的生成请求；已有候选翻阅不产生新请求；主动生成和已启用附随请求均有用途依据；拒绝或关闭某项后台调用后该项请求数为0，其他功能不被清空；未知与失败不冒充免费、未执行或已退款。该清单是验收标准；本轮已执行的隔离场景与未验范围见[实施验收记录](../reports/20261020-tavern-design-coverage.md#import-model-consent-fix)，不代表已部署或全部第三方模型已验证。

<a id="state-and-retry"></a>
## 五 共同状态、重试与操作边界（PB-07）

产品判断分别回答五个问题：程序是否安装、配置是否完成、是否已配对、相关服务现在是否可用、是否存在仍在执行或尚未恢复的维护修改。本节是行为对照，不要求新增页面、持久化状态系统或第二套任务管理器。

| 已知情况 | 用户应看到什么 | 允许的下一步与限制范围 |
| --- | --- | --- |
| 没有安装，或安装确实未完成 | 安装进度／缺失的安装条件 | 安装或适用的继续／恢复；已有目录先核验归属和数据 |
| 程序已安装，模型或首次配对未完成 | 明确缺少哪项设置 | 进入对应设置；完整版尚不算首次设置完成，不把它报告为程序安装损坏 |
| 设置完成，服务已停止 | 当前停止状态 | 正常启动；保留配置与故事 |
| 已完成首次设置，本地酒馆可用，外部连接中断 | 本地与外部连接分别显示 | 保持已证实可用的本地能力，检查或重试连接；不强制重装或清空配对配置 |
| 模型验证／调用失败 | 哪个用途的模型失败、保存是否成功、调用结果是什么 | 修正对应配置或重试；模型尚未返回与程序损坏分别诊断 |
| 世界有效，某项脚本／MVU 等能力未就绪 | 世界可用及具体能力状态 | 继续基础故事或重试该能力；不因能力失败删除、回滚或重新创建有效世界，不宣称完整玩法已经正常 |
| 任务仍在执行，或恢复和写入尚未结束 | 当前任务、阶段及等待原因 | 查询同一任务，使用该阶段已有的合法动作；不启动竞争写入 |
| 原任务失败，已确认无未恢复修改 | 失败原因、原安装是否可用 | 按[更新与恢复](#shared-update)重试或继续使用；历史失败次数不构成永久锁定 |
| 无法确认安装归属、真实进程或未恢复修改 | 具体无法核验的对象及其影响 | 保留现场，查询／诊断并执行适用恢复；限制会触及该风险的操作，不把未知状态写成成功或授权删除 |

**状态查询与完整验收分工：** 日常查询核对适用的安装记录、当前进程和健康事实；安装／更新验收核对相应组件、绑定及运行结果。日常轮询不全量哈希用户自定义内容，也不以历史验收记录替代当前服务状态。

**重试规则：** 可保留必要限速；输入或相关条件改变后，应允许合法的新提交。配对码由用户显式提交，不自动重放，不把原码写进日志或长期重试记录。原始失败、重试被限速和执行尚未开始分别呈现，重启也不应留下无法解除的合法操作锁定。

**阻止操作的证据边界：**

| 证据类型 | 判断规则 |
| --- | --- |
| 实例身份、用户配置、发布清单／待装资源校验、服务归属、恢复来源 | 是相关修改的依据；不匹配时停止对应修改，并说明缺少的证据 |
| 已发生但尚未恢复的目录替换或外部平台变更 | 按真实剩余影响阻止相冲突的启动／更新／保留数据卸载，进入恢复 |
| 已准备但未应用的资源、已证实完成恢复的历史事务 | 没有相应未恢复效果时，不因“曾经失败”永久阻断下一次操作 |
| PID 提示、下载缓存、失效的运行提示 | 按已有规则重新发现进程或重取已校验资源；这些文件自身不等于有效进程或危险写入 |
| 无法读取或验证的记录 | 不擅自改写、删除或视为有效；先确定它是否影响本次操作的必要证据，报告该处缺口 |

阻止操作的说明须交代失败位置、数据／程序是否改变、被限制的动作、现有可用动作。恢复错误保留原始原因；需要额外诊断时列出缺少的证据，不让用户反复猜目录或删除日志碰运气。上述判断依据沿用 [ADR 0014](../adr/0014-repair-derived-operational-state.md)。

<a id="shared-update"></a>
## 六 共同更新与恢复规则（PB-06）

本基线将诺拉受管规则／技能、酒馆应用程序及适用的共用维护组件统称为“诺拉酒馆核心”，其更新不等于桌面 APP 替换或重装全部环境。环境依赖只在目标确有需要时按适用计划处理，Hermes 不自动追随上游最新版。

| 入口 | 已确认的检查与更新范围 | 约束 |
| --- | --- | --- |
| 诺拉定时检查／更新提醒 | 仅适用于本实例的核心更新 | 只发布启动器时不提醒核心更新；不需要先探测用户电脑有没有桌面启动器 |
| 用户让诺拉更新 | 桌面版一次授权提交本机适用的核心与APP更新；无APP的部署只更新核心 | 诺拉提交请求和读取结果，复用现有执行器；不自行替换文件，不要求云端安装APP，不因检查或提醒静默安装 |
| 启动器“检查更新／安装更新” | 核心更新及启动器自身更新 | 内容使用同一独立更新器；APP 使用已有本体替换机制。两者都有适用更新时，一次点击依次完成，结果按[桌面双更新](launcher.md#desktop-update)分别核验 |

诺拉自主更新和启动器原按钮在执行核心更新时调用同一独立更新器，保留现有按钮和步骤。独立核心更新器本身不以桌面启动器是否安装、打开、在线或版本较新为执行资格；桌面统一请求的接入能力另行核验，真实安装、依赖、授权和资源校验仍然有效。启动器关闭、APP已移除、安装记录残留是不同事实，但都不应成为核心版本提醒的先决判断。

桌面请求须核验本实例APP的真实身份与能力。仅检查版本在后台读取并返回结果，不唤起启动器、不提交安装任务，也不覆盖已有更新请求；用户明确授权更新后才可按需唤起已核验的启动器，交给其现有双更新入口。APP关闭、损坏、旧版不支持和确实没有APP分别反馈，不能静默只更新核心却报告整套成功。旧版首次接入及缺失运行依赖按[诺拉接入边界](nora.md#autonomous-update)处理。APP替换与核心更新仍有各自事务，按固定兼容计划顺序执行；一项成功后重试只补失败项。无APP部署不增加桌面依赖。外部核心更新后，仍运行的启动器必须安全更新核心绑定，再完成单项APP更新；不能用旧描述符把合法更新误报成APP损坏。

**既有部署权限（2026-10-19 用户确认）：** 核心更新器不因文件或目录的所有者、组可写或其他用户可写权限位而额外拒绝更新，不自动修改部署权限，不增加用户组或 ACL 审查。实际读写仍服从操作系统权限；安装路径绑定、文件类型与符号链接检查、发布资源校验、维护互斥及失败恢复继续保留。这不是对共享主机上的其他系统账号提供隔离保证。

### 更新任务的完整过程

| 阶段 | 更新器承担的责任 | 调用入口承担的责任 |
| --- | --- | --- |
| 提交并接管 | 核验授权、实例和目标，确认任务接管；同实例只有一个合法维护写者 | 传递请求；得到接管依据前不宣称任务已独立运行 |
| 查询、下载和准备 | 固定适用目标、获取并核验资源，准备恢复所需条件；保留当前可用安装 | 呈现同一任务的进度与错误，不另起第二套更新 |
| 停服与替换 | 准备通过后停止需替换的服务，确认离线，再修改受管程序 | 服从更新任务的服务管理，不并行停服或写配置 |
| 验证或恢复 | 检查目标及要求的运行结果；失败按真实修改恢复 | 不凭进度结束或重连成功推断更新成功 |
| 结束与再次使用 | 记录最终效果，完成必要恢复并释放维护占用 | 重连／重开读取同一结果；能按结果进入正常使用、重试或恢复 |

上表规定的是同一核心更新任务；桌面 APP 替换具有单独的程序交接和恢复责任。“两个入口共用核心更新器”与“桌面一次发起两项更新”分别成立，不要求两类程序处于同一个底层文件事务。

成功的依据包括目标正确、规定的运行验证通过、用户内容符合保护约定以及维护任务已经结束。数据保护的验收不要求日常查询或每次更新全量遍历、哈希所有聊天；具体检查依据由相应模块和场景确定。

### 失败结果与下一步

| 已核验结果 | 可以告诉用户什么 | 下一步 |
| --- | --- | --- |
| 未替换原程序 | 本次未改动程序，并说明失败阶段 | 原程序经相应检查仍可使用时继续使用；修正条件后重试 |
| 已恢复并验证健康旧版 | 更新没有完成，旧版已恢复可用 | 继续使用旧版，或对原固定目标重试 |
| 文件已恢复，运行验证失败 | 程序文件恢复与服务可用是不同结果 | 处理具体运行阻断，再验证；不宣称旧版已正常 |
| 修改或恢复事实无法确认 | 明确未确认的效果，数据与证据保持原状 | 使用对应恢复／诊断路径；相冲突修改等待安全条件，不默认清空数据 |

重试保留原任务的真实失败和已确认目标；更换目标按新的目标重新准备与核验。原写者或恢复仍在工作时，读取到一条失败记录不代表任务已经结束。确认结束后，旧失败记录不应继续把后续合法操作锁住。

日常关窗与维护等待的具体规则见[启动器设计](launcher.md#close-and-disconnect)；桌面两项更新及兼容部分完成的规则见[桌面更新](launcher.md#desktop-update)。

<a id="version-rules"></a>
## 七 版本与交付规则（PB-09）

### 版本、发布批次和更新提醒

发布必须能区分核心、桌面 APP 和必要环境的真实变化，不把“仓库有新 Release”直接当成每个实例都需要核心更新。已有核心版本和启动器版本不是同一个数值；源码仓库、发布批次、组件版本和完整安装器也不是同一个对象。

| 实际变化 | 诺拉的自动提醒／自主更新 | 桌面启动器的检查结果 |
| --- | --- | --- |
| 只有桌面 APP 改变，核心没有适用变化 | 桌面主动检查可报告APP更新，授权后仅更新APP；无APP的部署不制造核心提醒 | 提示自身更新，保留已有核心 |
| 只有核心有适用变化 | 提醒／按授权执行核心更新，保留当前APP | 提示核心更新，沿用现有 APP |
| 核心与 APP 都有适用变化 | 桌面授权后一次依次完成两项；无APP部署仅核心 | 一次点击依次完成两项；兼容部分完成及失败恢复按[更新恢复](#shared-update)和[桌面双更新](launcher.md#desktop-update)判断 |
| 没有适用变化 | 不制造更新提醒或安装动作 | 报告对应组件已是最新 |

无桌面 APP 的安装依照相同核心规则运行；不为了消除提醒错误新增全盘 APP 探测或引入桌面执行资格。实现、实测与正式渠道的状态见[带日期的证据索引](../reports/20261020-product-design-modularization.md#implementation-evidence)。

<a id="delivery"></a>
### 按变化交付与正式发布

**目标是让普通小优化快速交付，同时保持更新可用、失败可恢复和用户内容安全。** 构建多少内容、生成哪些完整安装包、执行哪些验收、上传哪些资源分别判断；不能因为同仓发布、版本号变化或改动行数少，就直接决定整套重建或跳过检查。

| 变化类别 | 构建与交付 | 本次必须证明的结果 |
| --- | --- | --- |
| 普通核心业务、规则或技能变化，维护机制与依赖未变 | 准备变化组件，复用有依据的原 APP 和环境；不默认重新生成三个完整安装包 | 相关功能正常，适用的首装与既有客户端升级组合可用，用户数据保留 |
| APP 局部变化 | 准备实际受影响平台的桌面产物及替换资源；未变核心和环境按证据复用，不伪造核心升版 | 相关界面／功能、安装或本体替换和启动正常，原核心与用户数据保留 |
| 安装、更新、恢复、实例归属或数据迁移机制变化 | 按实际封装关系准备组件或 APP，不据此默认重建全部环境 | 受影响平台的正常操作、失败恢复、重试、任务结束及后续合法操作通过；数据保护符合 PB-05／PB-08 |
| Hermes／Python／Node／原生依赖等环境变化 | 重新准备变化环境及受影响安装包，复用证据充分的未变部分 | 目标平台完整安装、运行、升级及必要恢复通过，不凭版本标签推断环境等价 |
| 不交付的文档、测试或发布工具变化 | 核对产品输入和已封存字节是否变化；相同产品可单独验证工具，不为流程修改制造产品新版本 | 相应文档／工具行为正确，不能改变原产品来源或冒用旧验收 |
| 影响未知，或缺少可信基线／来源证据 | 先核对影响，不能进入未经证明的快速路径；必要时采用保守构建 | 缺失证据已补齐，相关质量条件满足后才允许交付 |

完整安装包用于首装，是否重新生成取决于实际输入变化和首装交付合同；既有用户的组件更新与新用户整包交付分别验收。不把避免重建当成跳过新依赖、程序变化或目标平台验证的理由。

**验收选择与复用：** 每次产品发布均须有最终制品身份、适用更新入口、实际目标版本、运行健康、维护任务结束和用户数据保护的相应证据。直接受本次变化影响的场景必须重新验证；对未变部分，只有相关源码、依赖、平台环境、测试及执行条件的等价性有依据，才能复用历史结果。新产物或新的组件组合仍需本次目标环境验证，不能用旧包成功证明新包可用。公共维护机制、运行环境、数据迁移或无法确定影响的变化应扩大回归；完整回归也定期保留，不能用以后再测替代本次相关检查。

独立检查可以并行，但实例目录、端口、进程和系统设置必须按检查需要隔离；存在相互影响时保留顺序或使用独立环境。失败、跳过、超时和未执行分别登记，不因追求耗时目标将其记为通过。每次说明重跑／复用理由及实际耗时；具体分钟目标和测量记录在发布流程维护，不能反过来要求删减必要验收。

**资源复用与失败续跑：** 未变资源只有在来源、大小、完整摘要和客户端解析兼容均已核验时才能引用；被仍受支持版本引用的历史资源须保留。旧入口兼容迁移未验证前继续采用兼容分发方式，不通过提高最低版本、删资源或改写历史文件来掩盖接入问题。复用旧安装器时，须验证其联网取得目标核心的新安装组合；离线底包版本如实显示，不把旧底包标为已包含最新核心。

已验收的平台产物和恢复依据在输入有效时保留。构建或验收失败优先重跑失败部分；工具修正后重新验收同一产品时，须重新绑定产品、测试及环境证据。实际产品输入变化则重建受影响内容。上传失败按原固定计划检查并续传，不因传输故障重新打全部产品包；资源字节变化必须建立新的资源身份，不能覆盖原已发布文件。

源码暂时保持同一仓库，分别管理核心与 APP 的版本和更新信息，由发布批次引用确切产物；本轮不拆仓。具体版本目录、标签命名及清单结构由技术方案验证，采用这项产品策略不授权立即改标签、覆盖旧资产或切换入口。新目录及协议须有旧入口兼容迁移，不能让现有安装因改名失去更新路径。

国内用户的版本查询与完整下载应有实际可用渠道、来源切换、适用的断点续传及文件完整性核验。发布只交付与验收身份一致的资源；相同版本号、不同文件字节不能共用验收结论。具体主源供应商和上传工具在发行方案及结果报告维护，不进入长期产品规则。

正式发布沿用[发布执行流程](../release-process.md)：识别本次变化，固定源码和验收产物，准备并核验分发资源，取得正式发布授权后切换并检查用户入口。构建、暂存、上传成功不等于正式发布；失败按原制品及传输记录恢复，不用重建来代替发布续传。

构建前须完成“改动 → 受影响入口与共用合同 → 既有测试及夹具 → 本次执行结果”的核对；核对缺失或本机必需检查失败时不派发产品构建。夹具修订保留等价或更强的保护断言。按本节核对改动影响、完整源码检查的适用范围与夹具修订依据，构建及验收步骤见[发布流程](../release-process.md#2-构建与验收不发布)。

基础统计和详细诊断按既有[诊断协议](../launcher-install-diagnostics.md)分别处理；详细诊断遵守用户选择及脱敏边界。故障诊断不包含聊天／世界正文、模型回复、Key 或配对码，不把私人内容放入公开分发资源。用户配置的模型调用本身会按用途发送必要内容给其选择的服务，此行为与故障上报分开说明。

## 九 开发执行与设计变更控制

2026-10-22用户先确认1.32更新职责调整：桌面端一次请求适用组件，无APP端保持核心独立。随后确认1.33交互：检查版本不打开启动器，明确同意更新后才唤起；同步旧版接入与文档追溯，回归通过后合并本地main，不发布。保留数据、原按钮、现有执行器和逐项结果。设计批准、实现、验收、合并及发布分别留证，见[当前任务](../launcher-reliability-plan.md#nora-unified-update-20261022)。

1. **开工前核对**：读取本总览、决策状态及受影响模块，核对当前设计版本、工作分支、最新授权和无关改动。在既有任务记录写明适用 PB／PR、预期用户结果、允许改变与必须保留的行为、拟验证方式；小任务可简记，不为此新建平行计划。
2. **区分修复与设计变更**：满足已确认规则的修复按既有授权推进。涉及首次要求、默认入口、关闭行为、数据归属、权限、支持承诺或更新策略的改变，先按[变更模板](change-request-template.md)说明前后差异、理由、替代方案、影响和验收，并取得用户确认。建议、待定项和实施方便不能替代确认。
3. **保持规则同步**：确认产品变化后，在唯一归属处更新设计，登记日期、理由及确认来源，检查受影响模块的引用和验收条件，再实施。用户已明确确认的要求直接据此落实；例行实现细节不重复审批。实现与设计冲突时先核对证据，不能为了让代码或测试通过而倒改要求。
4. **按结果验证**：涉及启动器时对照其全部页面／控件目录和覆盖审计；涉及诺拉时对照其全能力目录及[覆盖核对](../reports/20261020-nora-design-coverage.md)，核对运行规则、技能、MCP 与档案的交接；涉及酒馆时对照其全功能目录及[覆盖核对](../reports/20261020-tavern-design-coverage.md)，核对界面、业务接口和持久化的交接；新增、删除、隐藏入口或改变操作须同步对应设计与验收；检查关联旧用例、执行前提与夹具；产品构建前完成本节的关联测试核对，再按[发布流程](../release-process.md#2-构建与验收不发布)执行。更新／恢复同时证明任务结束和后续可操作，数据变化核对内容及归属；无法建立因果的范围外问题单列。
5. **交付前对账**：将实际差异与开工记录对照，确认无未经确认的行为、数据或支持范围变化。分别报告已分析、已实现、技术验证、目标环境用户流程验证、已部署／发布；明确未验项及直接阻断。按当前授权分别处理提交、合并、构建、推送和发布。

**缺少适用规则、授权、直接相关证据或存在未解决设计冲突时，先补齐本次动作的必要条件；不继续依赖未经确认选择的开发。** 这是一项执行要求，没有新增自动产品策略检测器；现有自动测试和制品门禁继续承担其能证明的条件。

发布任务在既有发行记录中登记设计版本与条款、源码比较范围、变化分类、构建及资源复用、重新验收与复用依据、上传范围和授权。动作前写明选择，交付前补齐实际结果、耗时和未验项；计划变化说明新证据。续接会话或切换分支后重新核对设计、工作区与最新授权，旧批准不自动授权新动作。
