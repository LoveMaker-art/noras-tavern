# 诺拉酒馆产品需求说明

文档修订：1.1。整理日期：2026-10-19。依据：[产品设计基线](../product-baseline.md) 1.12 的 PB-01 至 PB-09；这是文档修订号，不是产品版本。

本文件将现有已确认设计按产品目标、用户流程和功能要求组织，便于需求评审。规则以基线为准；下列验收标准描述“应证明什么”，不是声称本轮已经执行或通过。实现差异、历史验收和上线状态见[基线附录](../product-baseline.md)。

## 一 产品定位与目标用户

诺拉酒馆是以世界为核心的 AI 角色扮演产品。用户应能开始故事、与角色互动、保存故事进展，并在下次继续；可搭配诺拉进行对话和授权管理。其角色卡及扩展能力沿用项目声明的兼容范围，不承诺任意第三方内容均完整支持。

| 用户或场景 | 核心需要 | 设计取舍 |
| --- | --- | --- |
| 普通角色扮演用户，主要服务对象 | 按界面完成配置，能玩、能保存、能继续，维护失败有明确下一步 | 默认不要求理解脚本、进程和事务目录；安全性与可恢复性优先 |
| 希望诺拉协助的用户 | 通过适配 IM 与诺拉交流，授权管理世界、角色和配置 | 完整版首次需配置诺拉模型并完成 ClawChat 配对 |
| 源码或服务器部署的进阶用户 | 自行部署、使用相同核心业务和适用更新能力 | 进阶方式可选；没有桌面启动器不应阻碍适用的核心更新 |

产品成功结果是用户能完成并继续故事，而不只是安装程序能打开。产品设计不以新增部署方式、追随上游最新版本或减少检查数量为目标。

## 二 产品范围与职责

| 组成 | 用户获得的结果 | 职责边界 |
| --- | --- | --- |
| 酒馆 | 创建或打开世界、角色扮演、保存世界与会话 | 世界与故事业务由同一后端负责；不同世界和库原件按归属隔离 |
| 诺拉 | 对话、按授权协助管理内容、检查和请求核心更新 | 通过既有业务接口与独立更新器执行，不接管桌面 APP 本体更新 |
| 桌面启动器 | 安装、首次配置、启停、日志和维护结果呈现 | 提供管理入口；窗口存活不是核心业务和更新任务的资格条件 |
| 故事档案与剧情账本 | 管理偏好、故事档案和适用的故事辅助信息 | 区分现实个人信息与虚构剧情；不能用一次回复代替保存结果 |
| 支撑模块 | 模型运行、MCP、IM 配对、资源分发和故障诊断 | 按基线第六节交接责任；外部服务成功、本地健康和文件保存各自确认 |

用户可选择完整版或单独酒馆。完整版桌面默认走完整首次配置；单独酒馆不包含诺拉管理能力。云端与本地是部署场景，不是两套互不兼容的产品规则。

功能和页面的现有入口按[源码职责](../REPOSITORY.md)及用户指南维护。本次文档不授权新增导航、隐藏控件或重做布局。

## 三 主要用户流程

| 流程 | 用户可理解的步骤 | 成功结果与失败去向 |
| --- | --- | --- |
| 完整版首次使用 | 下载适用包 → 安装 → 配置并验证模型 → ClawChat 配对 → 启动检查 → 使用 | 程序、配置、配对和服务分别有结果；哪一步失败就处理该步，不能把模型错误当成整套安装损坏 |
| 日常故事 | 打开酒馆 → 创建或打开世界 → 与角色互动 → 保存 → 下次继续 | 仍是原世界和原会话；可选能力未就绪不删除有效世界 |
| 修改配置 | 进入模型或配对入口 → 提交相应信息 → 查看保存及调用结果 | 只改变对应配置；无关世界、聊天及其他用途模型保持 |
| 让诺拉管理内容 | 用户提出并授权请求 → 诺拉调用既有接口 → 返回实际结果 | 呈现目标对象和实际效果；诺拉与界面不维护两套业务真相 |
| 更新与再次使用 | 检查适用版本 → 用户确认 → 下载准备 → 替换验证 → 读取结果 | 按[基线第四节的现行更新规则](../product-baseline.md)执行；失败恢复、重试和数据保留分别核验 |
| 退出、卸载或重装 | 按现有退出行为操作，或明确选择保留数据／彻底卸载／取消 | 只影响本实例及所选范围；保留数据重装继续使用原内容 |

详细状态和允许动作以基线第三至五节为准。未知状态应说明具体未确认对象，不用清空数据或反复重装代替诊断。

## 四 功能要求与验收标准

以下编号用于需求与测试追溯，不是新业务模块、开发优先级或已通过数量。功能变更只选择与本次影响有关的标准；不能把这张表变成每次小改动全量执行的清单。

| 编号 | 用户要求 | 应取得的验收结果 | 规则来源 |
| --- | --- | --- | --- |
| PR-01 首次使用 | 按默认步骤完成安装、模型配置、配对和启动 | 各阶段结果可核验；故障显示对应阶段和下一步，重试不重置已确认的无关设置 | PB-03／PB-07 |
| PR-02 日常进入 | 下次使用无需重新安装或创建故事 | 原配置、世界和会话能继续使用；启动／停止只影响本实例 | PB-04／PB-05 |
| PR-03 故事持久保存 | 创建、保存、重新打开同一世界和会话 | 世界身份稳定，实际内容可读回；不能用新建空数据冒充恢复 | PB-01／PB-05／PB-08 |
| PR-04 内容隔离与复用 | 使用资料库内容开展不同故事 | 库原件、世界运行副本、会话归属明确；修改一个世界不改变其他世界或库原件 | PB-05；[隔离设计](../design/world-data-isolation.md) |
| PR-05 模型配置 | 为对应用途配置模型并了解验证结果 | 保存成功与调用成功分别反馈；更改诺拉模型不覆盖已有酒馆配置，凭据不进入诊断 | PB-03／PB-05／PB-07／PB-09 |
| PR-06 配对与重试 | 配对失败后能按条件合法重试 | 原失败原因可见，新提交可执行；旧失败不形成永久锁定，原码不被自动重放或长期记录 | PB-03／PB-07 |
| PR-07 诺拉内容管理 | 授权诺拉管理世界、角色、记忆等内容 | 界面与 MCP 通过同一业务结果核验目标和保存；不因另一个入口而绕过归属与授权 | PB-02／PB-05；基线第六节 |
| PR-08 故事档案与辅助 | 保存偏好与适用的故事信息 | 实际保存及用途可核验；虚构故事不直接被当作现实个人事实 | PB-05；基线第六节 |
| PR-09 状态与可用边界 | 明白当前哪些能力可用、哪些有问题 | 安装、配置、配对、服务和维护事实分开；局部能力失败只限制相关动作 | PB-07 |
| PR-10 核心自主更新 | 让诺拉更新，不依赖桌面启动器 | 正确选择核心，接管后调用方断开任务仍继续；最终版本、数据保护和任务结束有证据 | PB-06／PB-09 |
| PR-11 桌面更新 | 原按钮一次发起本次适用更新 | 正常打开与自更新重开后遵守同一更新规则；仅一项变化只做一项，两项变化自动续接完成；兼容部分结果和仅失败项重试分别核验 | PB-06／PB-09 |
| PR-12 故障恢复 | 维护失败后能恢复或知道具体阻断 | 按实际修改确认恢复、运行健康及任务结束；恢复后可正常操作，不能被旧记录永久卡住 | PB-06／PB-07 |
| PR-13 备份与卸载 | 清楚保留什么、删除什么，按选择执行 | 聊天辅助备份与程序恢复准备分开；保留数据卸载／重装继续原数据，失败保留原内容和必要恢复依据，彻底卸载按确认范围操作 | PB-05／PB-08 |
| PR-14 下载与诊断 | 能取得可信资源，出错时可反馈有效信息 | 核验目标、完整资源及适用续传；上报遵守选择和脱敏要求，送达不冒充业务成功 | PB-09 |

## 五 品质与异常要求

| 维度 | 产品底线 | 证明方式与边界 |
| --- | --- | --- |
| 用户数据 | 普通更新、修复、保留数据重装保护聊天、角色、世界、配置、凭据和适用档案 | 按场景核对受保护内容与归属；不要求日常轮询或每次更新全量哈希用户聊天 |
| 可恢复性 | 修改前准备必要恢复条件，失败后如实区分未修改、已恢复、运行失败和未确认 | 核对真实效果、健康及维护任务终态，不能只验证按钮或进程存在 |
| 使用连续性 | 原故事可继续，已证实可用能力不因无关失败被整体禁用 | 直接演示原场景与受影响场景；不据此放行未知或不兼容程序组合 |
| 信息可信 | 成功、部分完成、失败、限速、未执行分别显示 | 页面／返回结果与执行证据一致；测试通过不等于真实用户流程通过 |
| 分发质量 | 产品身份、适用平台、实际版本和验收来源一致 | 按实际影响选择新验收及可复用证据；不能仅按版本号或改动行数判断 |
| 隐私 | 模型凭据、配对码和私人故事内容不进入故障诊断或公开资源 | 核对采集内容、用户选择和脱敏；模型服务调用与故障上报分开说明 |

没有为整个产品确认统一响应秒数、安装耗时或所有历史版本的兼容承诺。本文件不补写未经确认的数字。发布流程中的耗时目标是工程优化目标，仍需真实测量；具体支持范围以对应产品制品及验收为准。

## 六 已确认取舍

已确认：普通角色扮演用户优先、进阶能力可选；完整版首次需诺拉配置与配对；诺拉只处理核心更新；桌面两项有更新时一次发起；确认兼容才保留成功部分；源码暂不拆仓。

已取消：两平台日常关窗统一停服要求。保留现有退出行为及维护等待保护，不能据此再自行增加后台常驻或主动关窗续跑设计。

这些选择的唯一决策登记仍在基线。更新发布设计的[归档快照](archive/20261019-update-release-design.md)保留当时结论；当前实施与发行结果从基线附录进入对应报告。本文件只定义需求与证明标准，不认证全部功能、外部模型、第三方卡片或历史用户均已通过。

## 七 评审与维护

改变用户行为、功能范围或支持承诺时，按[需求变更模板](change-request-template.md)先说明前后流程、保留范围、风险和可观察验收，再依据基线第七节取得适用确认。被确认的新规则更新基线，需求编号和验收保持关联；实施细节留在模块方案，实际结果留在带日期报告。

文档整理中发现的实现疑点应标为待核验，不能直接扩大本次任务。待决产品选择只在基线第八节登记；发现新冲突时，必须说明影响哪条既有规则和哪个用户结果。
