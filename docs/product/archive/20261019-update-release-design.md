本板块规定：诺拉和启动器各自更新什么，用户怎样完成更新，失败怎样处理，以及开发者怎样构建、验收和发布。按 2026-10-19 已确认的规则归档。

## 一 已确认的设计结论

1. **诺拉更新什么：** 只检查和更新诺拉酒馆核心，不依赖是否安装或打开桌面启动器；只发布启动器时不提醒核心更新。
2. **启动器怎样更新：** 保留原按钮；核心和启动器都有适用新版时，一次点击依次完成两项，只有一项变化就只做一项。
3. **任务中断怎么办：** 独立更新器接管后，诺拉或调用方断开，任务继续；重新连接读取原结果。
4. **失败怎么办：** 确认兼容时保留成功部分，重试只补失败项；未知或不兼容组合走已核验的恢复路径。聊天、角色、世界和配置保留，任务结束后能继续合法操作。
5. **小改动怎样交付：** 核心、启动器和环境分别判断变化；只构建受影响内容，有依据地复用未变资源及验收结果，相关场景仍须验证。
6. **怎样正式发布：** 先固定并验收制品，再准备渠道资源，经授权切换正式入口并回读核对；上传失败从原计划续跑，不因此全部重新打包。

## 二 产品归属、版本与提醒

“核心”包含诺拉受管内容、酒馆程序和适用的共用维护组件；桌面 APP 和基础运行环境分别识别。仓库 Release 是交付批次，不直接等于每个组件的版本。

| 发布内容 | 诺拉的提醒与自主更新 | 启动器检查与更新 |
| --- | --- | --- |
| 只有核心有适用变化 | 提醒／经授权执行核心更新 | 更新核心，沿用现有 APP |
| 只有启动器 APP 有适用变化 | 不制造核心更新提醒，不执行 APP 替换 | 更新 APP，保持原核心与用户内容 |
| 两者都有适用变化 | 只处理核心 | 一次点击依次完成两项，分别核验结果 |
| 没有适用变化 | 不创建更新任务 | 如实报告对应组件已是最新 |

暂不拆仓；分别管理版本、兼容和交付身份。没有桌面 APP 的部署使用相同核心规则，不以操作系统、窗口或全盘 APP 探测决定核心资格。Hermes 不自动追随上游最新版；环境变化另按需要处理。

## 三 用户更新流程

### 诺拉入口

用户让诺拉检查 → 核验本实例适用核心版本 → 用户授权更新 → 同一独立更新器接管 → 准备资源和恢复条件 → 停服、替换、验证或恢复 → 查询原任务结果。

检查和提醒本身不授权静默安装。核心更新不以桌面 APP 安装、运行、在线或版本较新为前提；真实依赖、安装位置、资源完整性及授权仍须核验。任务已接管后，诺拉停止或调用方断开不应终止它，重连读取同一结果。

权限处理沿用 2026-10-19 的确认：不再因文件所有者、组可写或其他用户可写权限位额外拒绝核心更新，也不自动修改部署权限。实际读写服从操作系统权限；路径、文件类型、符号链接、资源完整性、互斥与恢复检查继续有效。

### 桌面入口

点击原检查按钮 → 分别显示核心与 APP 的适用目标 → 点击原安装更新按钮 → 固定本次目标、核验兼容和恢复条件 → 依次执行需要的部分 → 必要时自动交接重开 → 展示两项实际结果。

核心部分使用与诺拉相同的独立更新器；APP 使用原有本体替换机制。实际先后顺序依照已验证的协议和可恢复组合选择，不固化为永久产品策略。用户不需要再次查找和点击另一项安装，也不为本方案重新设计按钮和页面。

普通空闲关窗保留当时已有行为。维护进行中保留现有等待与退出保护；独立任务能在调用方异常断开后继续，不等于新增“更新中主动关窗”功能。

## 四 成功、部分完成、失败与重试

| 实际结果 | 用户看到的结果 | 下一步 |
| --- | --- | --- |
| 所需两项均成功并验证 | 全部完成，显示实际核心与 APP 版本 | 维护结束后正常使用 |
| 一项成功，另一项失败且恢复；保留组合已证明兼容和可用 | 部分完成，明确成功项、失败项与实际版本 | 保留有效成功项，重试只补失败项 |
| 失败后组合未知或不兼容 | 不能作为兼容部分完成放行 | 沿已核验退路恢复可用组合；不回滚或覆盖用户故事来强行匹配程序版本 |
| 文件、写者或恢复效果尚未确认 | 说明未确认对象及受影响动作 | 保留数据与证据，查询或执行适用恢复；不虚报任务结束 |

目标在本次任务中固定。重试要重新核验成功项与原目标仍适用；另选新版目标属于新的准备与核验，不能在第二阶段自动漂移到另一个 latest。

历史失败次数本身不构成永久锁定。恢复后须确认真实写者结束、维护占用释放、后续合法操作可执行。未知状态只限制会触及该风险的动作；不把缓存、旧 PID 或已恢复历史事务一概当作危险写入。

历史版本按来源、入口和数据形态分别验证。新代码不能直接改变用户仍在运行的旧二进制；普通在线更新、一次接入、保留数据覆盖和独立救援分别声明范围，不能宣称所有历史原入口已经自动修好。

## 五 按变化构建和验收

构建范围、完整安装包范围、验收范围和上传范围分别判断，不用版本号或改动行数代替影响分析。

| 变化类别 | 构建选择 | 相关验收重点 |
| --- | --- | --- |
| 普通核心业务、规则、技能 | 准备变化组件，有依据地复用 APP 和环境 | 功能、适用首装／升级组合及用户内容保留 |
| APP 局部变化 | 构建受影响平台 APP，复用未变核心和环境 | 相关功能、本体替换、启动及原数据保留 |
| 安装、更新、恢复、实例归属或数据迁移 | 按真实封装关系构建相关组件或 APP | 受影响平台正常操作、故障、恢复、重试、任务结束及后续操作 |
| Hermes、Python、Node、原生依赖 | 准备变化环境及受影响制品 | 相应平台完整安装、运行、升级及必要恢复 |
| 不交付的文档、测试和发布工具 | 验证实际影响，不制造产品新版本 | 工具正确、产品身份不变，不冒用旧验收 |
| 影响未知或缺少可信来源 | 补证据，必要时保守构建 | 不在无依据时进入快速复用路径 |

直接受影响场景重新验证；未变部分只有源码、依赖、平台环境、测试和执行条件等价有依据时才能复用。新制品或新组件组合仍需本次目标验证。独立检查可在充分隔离后并行；失败、跳过、超时和未执行不能记为通过。

完整安装包用于首装，是否重建按输入和首装合同判断；旧安装器若继续用于联网安装目标核心，必须验证这个组合，且如实显示离线底包版本。现有用户组件升级和新用户首装分别证明。

## 六 资源分发与发布过程

确认改动及交付计划 → 固定产品源码和制品 → 按影响取得验收证据 → 封存版本、来源、大小和摘要 → 准备所选渠道资源 → 经授权正式切换 → 回读用户入口和真实版本。

未变资源只有在来源、大小、完整摘要和客户端解析兼容都已核验时才能跨版本引用。被受支持版本引用的历史资源保留；旧入口迁移未验证前维持兼容方式。不能通过删历史文件、强制提高最低版本或覆写同名已发布字节来规避兼容问题。

输入仍有效时保留已验收平台产物，失败优先重跑相应阶段。上传故障按原固定计划检查、补传与续跑，不因此重打全部产品包；字节改变建立新身份。产品字节、发布工具修正和传输重试分别处理。

国内版本查询、完整下载、备用源及适用续传都需相应证据。供应商是实现配置：归档时国内主源是极狐，正式渠道为 GitHub 与极狐；未来更换供应商仍须遵守现行规则和授权。

耗时目标仅用于衡量优化，不要求压掉相关验收，也不是对用户网络和 CI 排队的时间保证。发布成功指所选渠道及用户入口均核对成功；上传、草稿或单站成功不能当作全部正式完成。

## 七 数据与隐私底线

保留聊天、角色、世界与会话、配置、模型凭据、记忆和故事档案的内容及归属。程序替换恢复与聊天滚动备份分工不同；普通更新不把全量哈希聊天当固定前提，也不因辅助备份失败谎报聊天保存失败。

受管规则和模板按原合同更新，用户长期私人内容放在受保护位置。卸载的保留／彻底删除／取消选择及确认边界不因更新设计改变。故障诊断遵守用户选择，不包含模型 Key、配对码或私人故事正文。
